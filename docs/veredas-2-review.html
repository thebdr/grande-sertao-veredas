Versioning: how releases work
Decided
Independent versions
After 2.0.0 each component owns its version. The shared workspace version (0.2.1 today) goes away.
Suite releases
A suite release is a manifest that pins a tested set of component versions, shipped and installed together.
Core ripples outward
A MAJOR bump of veredas-core means every dependent is rebuilt and retested before its own next release.
Versioned files
Every plain-text config and project file states its schema version. Portal migrates it or refuses it, and never guesses.
Naming convention
veredas-‹nome›
Portuguese, and it names the role
Aranha, the spider, crawls the network. Ábaco, the abacus, computes. Portal is the gateway.
ASCII ids, accented names
Crates and binaries stay plain: veredas-abaco, veredas-supervisao. Screens say Ábaco and Supervisão, as today.
The exceptions
Core keeps its name. ORCL is a language, not a component. WMS keeps the industry’s acronym. Extensions such as acerto drop the veredas- prefix.
Adding a component: five conditions
01
A role nobody covers. One sentence no existing component already answers, written in docs/‹nome›-plan.md before the code.
02
Generalization first. Anything a second component could use is designed for veredas-core from the start.
03
Through portal. All exchange with the outside world goes through veredas-portal. Exempt: the test tools, maquinar and aranha, and controlador’s real-time path.
04
Fixture first. Any hardware it talks to has a simulator in veredas-maquinar, built before or alongside it.
05
Named and versioned. A Portuguese veredas-‹nome›, starting at core’s current MAJOR (3.0.0 if core is on 3.x).

01 / 08 · the foundation
veredas-core
Every class and library that more than one component needs.
Scope
  • Shared types: tags, values, timestamps, quality
  • Shared protocol layers: TCP telegrams, the OPC UA client
  • Plain-text file schemas, with their version stamps
  • Errors, logging and test-fixture plumbing
Rules
  • New functionality is designed as if a second consumer already existed
  • Component code moves here once a second component needs it
  • A library container, never an executable: no limit on what it holds
  • Depends on no other component
absorbs: veredas-telegram · veredas-opc
02 / 08 · portal, “gateway”
veredas-portal
The single point of information exchange between Veredas and the outside world.
Scope
  • Today’s data plane: tailing, log families, regex capture
  • The DuckDB session store
  • SSE, windowed REST and the gated write surface
  • The desktop shell
Rules
  • Every component exchanges data through portal, except the test tools and controlador’s real-time path
  • Writes stay gated: whitelisted tags, master switch off by default
  • Ships a light, embeddable build for controlador
absorbs: veredas-core (today) · veredas-store · veredas-server · veredas-desktop
03 / 08 · controlador, “controller”
veredas-controlador
A softPLC programmed in ORCL, the Open Rust Control Language, and in ladder later.
Scope
  • ORCL programs in a deterministic scan cycle, with watchdog and safe outputs
  • Direct NIC access for real-time communication
  • PLC Hardware Configuration, built on an embedded aranha
  • Embedded portal-lite for logging and non-real-time protocols
Rules
  • The only production component allowed past portal, and only on the real-time path
  • Everything else goes through its embedded portal-lite
  • ORCL stays a translatable subset of real Rust, with its own SemVer
  • Controlador states which ORCL versions it runs
builds on: orcl-std · orcl-runtime · demos/conveyor
04 / 08 · maquinar, “to machine”
veredas-maquinar
Tools that simulate real hardware, so every consumer meets its plant on a bench first.
Scope
  • Log emitters and a configurable OPC UA server
  • TCP telegram channels, up to a full simulated sort controller
  • Automated replies to incoming data, random or rule-based
  • Controllable pressure: rates, no-reads, full chutes
  • Later: a 2D/3D plant simulator
Rules
  • Fixtures come before the consumer that needs them
  • A test tool: owns its sockets, not routed through portal
  • Speaks the real device’s wire, so a consumer cannot tell the difference
  • Test-only and light: no DuckDB, never portal’s store or desktop
from today: veredas-maquinar · veredas-trajetorias (automated replies)
05 / 08 · aranha, “spider”
veredas-aranha
An industrial network scanner for setup and troubleshooting, never for production.
Scope
  • PROFINET DCP and LLDP first, then EtherNet/IP, Modbus, S7, OPC UA, BACnet
  • Listens before it asks; fuses every protocol’s answer, with provenance
  • Draws the topology and diffs it against a baseline
Rules
  • Used for setup and fault-finding only, not while the plant produces
  • A test tool: owns its sockets, not routed through portal
  • Embedded by controlador as its PLC Hardware Configuration
  • Also runs on its own, for commissioning
from today: veredas-aranha · docs/aranha-plan.md
06 / 08 · comissionador, “commissioner”
veredas-comissionador
A testing platform that runs predefined checks on portal data, live or historical.
Scope
  • Checks run in real time, or replay over historical data
  • Its own designer: one test file, two views, text or flow chart
  • Script boxes, or text functions reused as blocks, for logic like math
  • An acceptance report for every test run
Rules
  • Reads plant data only through portal
  • Drives machinery only through portal’s gated writes
  • Tests are stored as plain text, diff-able in git
plan: docs/comissionador-plan.md
07 / 08 · ábaco, “abacus”
veredas-abaco
A spreadsheet editor for engineering work, where Excel starts to feel too tight.
Scope
  • Built on a fork of IronCalc, modified for engineering tasks
  • Python macros and custom functions
  • Byte-faithful .xlsx edits with no Office on the machine
  • Its own .abaco workspace file
  • Extensions, starting with acerto (plant alignment)
Rules
  • Edits the same engineering workbooks the other components read
  • Fork fixes go back upstream to IronCalc where they fit
  • Accuracy is measured against Excel’s own cached values
from today: veredas-abaco · veredas-abaco-py · ironcalc (fork) · abaco-oracle · acerto
08 / 08 · supervisão, “supervision”
veredas-supervisao
The unified web interface for the whole suite.
Scope
  • Layouts: 2D in SVG, 3D in glTF, sharing object IDs
  • Objects that move live across the layout
  • Dashboards, charts and tables, absorbing today’s dashboard
  • Several sessions served side by side from one machine
  • Editing in the browser or in config files
Rules
  • Configuration is plain text, never binary; 3D models are assets it points to
  • Owns no plant connection: every value arrives through portal
  • Every write rides portal’s gated surface
from today: veredas-supervisao · dashboard/
Arrives later · warehouse management system
To be studied
veredas-wms
A production application for warehouse management, structured for the job.
What we know
  • Production software, not a test tool
  • Complex enough to be studied before it is designed
  • Its own planning and development phase, after the eight
Rules
  • Structure set by its study, not inherited from trajetorias
  • Production storage lives here, never in maquinar
  • Follows the suite rules: portal, core, SemVer
plan: its own, written after the study
