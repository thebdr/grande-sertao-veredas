# C-033 evidence - the bench file and the executable

## The design (2026-11-06)

The last plain-text file of the bench, and the one that holds the others: a bench file lists the
parts by name and points at the device's files beside it (core's channel file, the catalog, the
rules file), never copying them, so a plant's bench is a folder a consumer's test can keep and a
commissioning engineer can edit. The emitters' and the servers' own keys are the modules' own
configs, spelled out in the reference under the bench's tables; the channel's are the bench's.

`load` checks everything before anything starts: every referenced file is read and loaded, every
part validated as its module validates it (the emitter's file pattern and timestamp format, the
server's `validate`, the channel's id field, the rules against the catalog, the messages' fields
against the message), so `--check` can promise that what it printed can start. `Bench::start`
then starts the parts in the file's order and names the first that cannot.

The executable is deliberately small: a bench runs until stdin closes or says `stop` (a terminal's
Ctrl-C ends the process as any CLI, and every part's files and sockets close with it), and
prints one line per part a second. A desktop UI is `docs/questions.md` Q12; the library's handles
carry every knob a UI would need.

One reader trap found by the key walk: serde's `flatten` disarms `deny_unknown_fields`, so an
OPC server's table with the name flattened over the server's config accepted a misspelled key;
the bench's table now spells the server's keys out and builds the config from the defaults.

The worked example is the plant of the other references put together: the scanner's log, the
controller's OPC UA server, the machine listening for the unit; the test writes the referenced
files from the other references' blocks beside the bench file, starts it, sees every part work,
and runs the executable on the same folder.

## Refute round 1 (2026-11-07): refuted

The code held (the parts joined on a failed start through their handles' drops, the OPC table
field for field with the server's, the walk's placements, `out_dir` against the file's folder,
`--check` before any start). One claim was false: "in the file's order" cannot hold across
kinds, since TOML groups a kind's tables under one key; the clause and the reference now say
emitters first, then servers, then channels, each kind in the file's order, pinned on a file
listing a server above a channel above two emitters above a server. Three claims were unpinned
and are now pinned: the seeds (two emitters without seeds writing the same lines run for run and
different lines from each other, another bench seed other lines; the machine's first two items
drawn alike for one bench seed over the rules file's own, differently for another), the emitter
stopped after a server failed to start (its line count still over sixty intervals), and the
executable stopped by stdin closing.

## Refute round 2 (2026-11-07): refuted on three pins

The round-1 pins held (the seeds in both halves catching a dropped index or the rules file's
own seed, the stop over sixty intervals, the orderly `stopped`, the display order in three
places). Three parts of the clause were still unpinned: the start order of servers before
channels, "joined" as against "told to stop", and a channel's own draws under the bench's seed.
Now a channel listed after a failing server never dials the socket the test holds, a server
started before a failing one has its port free the moment the error is back, and a channel's
drawn status field read by a peer repeats under one bench seed and differs under another.

## Refute round 3 (2026-11-07): holds

Each new pin fails on its mutant: a signalled-only drop leaves the first server's port bound
when the error returns (twenty of twenty probes), a channel started before a failing server
leaves a connection queued on the test's listener, a clock-seeded channel draws other speeds.
Three bare runs green. Noted, not a gap: a cyclic field is drawn when due whether or not a peer
is there, so a slow dial could shift what the peer sees and fail the equal-runs pin without a
false pass; the pin's interval is 300 ms for that margin.

## Found by CI (2026-11-08): the seed test read before it could

The seed test failed on the Linux runner (f3934b9: the first two items' weights read as empty)
and once in eight local runs (the peer's recent lines three, not four). It read the machine's
items from the status once two were announced, but an answered item travels for 500 ms in
neither the awaiting nor the ended list, so the read could miss both; and it took the peer's
recent status lines once four were counted received, before the fourth was in the kept list. Both
reads now wait for what they assert: the two items present in the lists, four status lines kept.
Underneath, the controller's one stream for four purposes made later items' weights depend on
the ticks' timing; that is C-031's finding, fixed there (streams per purpose).
