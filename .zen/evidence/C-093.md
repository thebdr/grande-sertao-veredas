# C-093 evidence - the store written to the drive at a fault

## The ruling and what is built (2026-11-22)

`docs/robustness.md`, "The store of a controller's embedded portal": "at a fault the controller
writes the window to the drive with the fault record, so whoever comes later sees the minutes
before the fault" (given with the ruling of 2026-11-19, not objected to). Built: with a folder set
(`SessionConfig::fault_copy_dir`), every fault record the controller source hands in (C-092) has
the session copy its store to the drive, the record's row in it.

- **After the row is stored.** The pump drains the record, flushes its row, then copies, so the
  copy holds the record it was written for.
- **Through the ingest connection** (`DuckStore::copy_to_drive`, the snapshot's `COPY FROM
  DATABASE` on the pump's own connection under an alias of its own, `_vcopy`), so a reader holding
  the query connection holds no copy back, and a shell's snapshot attached as `_vsnap` at the same
  moment does not collide. The pump is busy for the copy's length (a window's stretch: small).
- **A file per fault**, named for the session and the fault's time on the controller's clock, a
  second fault in the same second `.fault-1` and on, never over a file; the folder created; a copy
  that fails is a store error with its text and the fault row stays.
- **Not ruled** (docs/questions.md Q41's proposals): copies limited in number, no more than one per
  shortest gap, the program asking for one. Every fault gets its copy and none is deleted, the
  reversible answer. A power cut or a fault that takes the runtime down leaves no copy: only
  controlador's own fault record remains.

## Refute round 1 (2026-11-22, at b3380d9): refuted on the name

The critic held the copy taken after the flush, never over a file, through the ingest connection,
and a failed copy as a store error. The name was checked by its prefix and suffix only; the test now
reads the record's time off the copy and asserts the whole name. A fault accepted during the stop's
tail had no copy: C-092's gate closes that.

## Refute round 2 (2026-11-22, at 5ff9097): refuted, two gaps in the test

1. **"The counters name the last"** was read after the first copy only. After three copies the
   counters, and now the snapshot, are asserted to name the newest.
2. **The name of a second copy in the same second** was any name holding `.fault-`. Every copy's
   name is now derived from its fault's second, in the order the faults came (read off the copy
   that holds all three), and asserted exactly: `.fault` for the first in a second, `.fault-1` for
   the next.

The gate flagged C-093 as a near-duplicate of C-091: two distinct capabilities (a whole copy at a
fault, a file per fault, no limit; a record of every row in batches, one per run, to a limit).
C-093 now names C-091, and what it stands on: C-092's record, C-041's snapshot, C-090's window,
C-043's pump, held for the copy's length (6c7dbbe). It also found:
- **The snapshot did not carry the copy counters**, so a reader over HTTP (C-095) could not see a
  copy: served now, and checked.
- **No marker on the unruled choice**: `copy_at_faults` carries `DECISION PENDING (Q41)` now.
  That the copies have no limit where the record has one is Q41's open question, not a
  contradiction: only recording was ruled "in files with a size limit".
- **A fault accepted while the session stops** had no test of its copy: three rounds now push
  faults across the stop, every accepted push a file.
- **The name** is the record's stamp on the controller's clock (C-092), worded so.
- **`copy_to_drive`**, a public method that writes a file, is the crate's own now (`pub(crate)`):
  its one caller is the session, and supervisão's list of writers needs no new name.
- **Controlador's plan** still says the embedded portal writes nothing to the drive: sent to the
  orchestrator.

Mutants, each red now: the counters keeping the first copy's name, the second name in a second
`.fault-5`, the snapshot without the copy count, no copy once the feed is closed.

## Refute round 3 (2026-11-23, at e487a86): holds

The critic found no path that passes while the clause fails. Its note, not a gap: the name is
checked against the copy's own record on the controller's clock, and this machine is at +0100, so
a name taken from the arrival clock fails here; on a runner at UTC that mistake would pass.
Verified.

A flake of the test's own (2026-11-27, the whole suite's run before C-036's eighth answer was
pushed): the copy holding the most fault records held two of three. The test's window holds one
second, and under the suite's load the checks between the first fault and the next two took longer:
the first fault's record had left the window when the next two copies were made, as the window
says it should. The test read the three faults off one copy; it reads them off every copy now
(each holds its own fault's record), joined by their sequence. The code is unchanged.
