# C-022: The poll worker: lab notebook

## The port (2026-11-06)

From Veredas 1's `crates/veredas-opc/src/worker.rs` with its inline tests and
`tests/worker_e2e.rs`. They are now `src/opc/worker.rs` and one file, `tests/opc_worker.rs`.

What changed (the first four are hazards in Veredas 1, worth porting back by whoever owns it):
- **No request waits for a connection.** A write asked of a worker with no session (connecting,
  or waiting out its backoff) is answered at once with `NotConnected`, and so is a read.
  - Veredas 1 left both in the queue until the next session existed.
  - So a command pulse asked for during an outage fired whenever the plant returned, minutes
    later.
  - Its caller meanwhile waited with no bound.
- **The worker checks the master switch again just before the wire.** Veredas 1 checked it only
  in the handle, so a write already queued behind a poll still fired after the switch was turned
  off.
- **Every connection attempt is bounded (10 s) and raced against stop.** Veredas 1 awaited the
  connect unbounded and unraced. A peer that accepts TCP and never answers held the worker, and
  a stop with it.
- **A zero poll interval is refused at spawn.** Veredas 1 panicked the worker thread in tokio's
  `interval`.
- **A session abandoned half-way has its event loop aborted.** Veredas 1 dropped the join handle,
  which detaches the task.
- **Errors are typed.** `OpcError` covers the worker's text, and `WriteRefused::Transport` carries
  one. Writes are answered with `WriteRefused`.
- **`TagRead::quality` added.** Good only with a value and a good status; uncertain when the
  server says so; bad otherwise.
- **Jobs and the stop are raced.** Veredas 1 woke a 200 ms sleep to notice the stop.
- **The read constants are public:** `MAX_NODES_PER_READ`, `CALL_TIMEOUT`, `CONNECT_TIMEOUT` and
  the retry bounds.

The chunked read is now proven, not assumed. The demo plant caps a Read at 1 000 nodes and polls
1 200, so an unchunked poll is refused whole (C-023). In Veredas 1 the demo server took any size,
and the chunk test passed with or without chunking.

New tests:
- a queued write disarmed while it waits behind the slow tag, and its armed control;
- the outage write, never landing after the plant returns;
- the silent server, and the stop mid-connect;
- the exact backoff;
- user and password through the worker;
- both clocks;
- a dropped consumer;
- quality;
- per-write statuses in order;
- the zero interval.

## Refute round 1 (2026-11-06): refuted, two code bugs and six test gaps

Code bugs:
- **A stop was not "within tens of milliseconds".**
  - Against a silent link while polling it took 2.04 s (the CloseSession wait).
  - During a host name lookup it took 1.22 s (the runtime joining its blocking task).
  - Now the CloseSession is bounded at 100 ms on a stop and 250 ms on a failure, raced
    against stop. The runtime is shut down in the background.
  - The clause now says "within a fraction of a second". A stop mid-poll and mid-write
    through a frozen relay are pinned under 400 ms.
- **A write that timed out could still land.** The refuter froze a relay, wrote, and got a
  timeout at 10 s; after a thaw the plant read 1.
  - No client can recall bytes already on the wire, so the fix is the truth, not a guarantee.
    The type is now `WriteError`, and its `Unconfirmed` says the write may have reached the
    plant.
  - It covers a failed or timed-out call, and a stop mid-call (`WorkerDropped`). `NotSent`
    covers no session, and a request still queued when the worker ends (now drained and
    answered `WorkerGone`).
  - Any read or write call that fails or times out now ends the session. A wedged one is never
    reused.

Test gaps, each pinned now:
- the read path reconnecting (a frozen relay, Retrying with the read's reason);
- `BadNoData` padding and the value only beside a good status: the assembly is now
  `tag_reads`, a public function pinned on a short, long, bad, uncertain, status-less and
  empty-valued answer;
- the backoff's 30 s ceiling: `retry_delays`, pinned to nine steps;
- its reset after a session (500 ms again after a reconnect and a kill);
- the plant clock on a UTC machine: on Unix the test reruns itself under
  `TZ=Asia/Kolkata`;
- a stop mid-call.

Held:
- the gate order, and the switch checked again before the wire;
- not connected answered at once and never fired after a noticed outage;
- per-write statuses in order;
- the zero interval;
- a dropped consumer;
- measured stops of 23 to 61 ms on a live plant.

## Refute round 2 (2026-11-06): refuted, one safety gap and one test gap

Every round-1 finding is closed. Both questions put to the refuter came back no:
- **Can a write told `NotSent` reach the plant?** No: the job never met a session.
- **Can a request hang its caller?** No: every wait is bounded.

Safety gap: a write whose caller gave up on it still fired.
- **How:** a caller's own timeout dropped the `write_tags` future while the job waited behind a
  slow read. The plant read 1 once the queue drained.
- **Real case:** an operator who pressed again would get two pulses, late.
- **Fix:** the worker now skips any request whose reply channel is closed, just before the wire.
- **Pinned:** a write abandoned by a 50 ms timeout behind the 400 ms slow tag never lands. The
  awaited control lands. Removing the guard makes the test fail (the plant read 1), checked by
  hand.

Test gap: the stop during a host-name lookup was fixed in round 1 but only pinned for the
browser. It is now pinned for the worker too (under 500 ms).

Not counted, recorded: a send landing between the queue's `close()` and its drain could in
theory strand a job. The refuter could not show it.

## Refute round 3 (2026-11-06): holds

Both round-2 findings are closed: the abandoned write, and the stop during a host-name lookup.
No `NotSent` write reaches the plant, and no request hangs its caller.

Noted, not counted:
- **The lookup test has teeth only where a failed lookup is slow.** On this Windows machine it
  measured 1.25 s per attempt. A Linux resolver may answer "no such host" in milliseconds, and
  there a revert to `drop(rt)` would pass. The browser has the same test (C-021).
- **One window remains.** A caller who gives up after the worker has started the call can still
  see its write land. No client can recall bytes already sent; the clause promises only "before
  the worker reached it".

## The host-name tests made to bite anywhere (2026-11-06, the operator: "fix it")

The lookup tests (C-021, C-022) bit only where a failed lookup is slow: about 1.2 s on Windows,
possibly milliseconds on a Linux runner, where a regression to `drop(rt)` would pass. No test can
make the system resolver slow, so the property itself is now pinned, independent of DNS:
- **The helper.** The worker and the browser run their threads through one function,
  `run_on_own_runtime`. It builds a current-thread runtime, runs the task, and shuts the runtime
  down in the background.
- **The test.** It leaves a blocking task that is certainly running (3 s, started before the task
  ends) on that runtime, and requires the call to return in under 1 s. A copy sits in each test
  file, so each clause stands alone.
- **Checked by hand.** Reverting the helper to `drop(rt)` makes both copies fail at 3.0 s, on
  this machine and on any other.

The lookup tests stay as end-to-end checks, and the clauses say they bite only where a failed
lookup is slow.

Also: the worker now drains its queue even if its runtime cannot be built, so a queued request
reads "not sent", not "dropped mid-call".
