# C-054 evidence - writes, gated

## The design (2026-11-09)

Supervisão holds no write path: the binding declares an object's actions (an OPC tag by the node id
text portal's write surface names, and the value), and the page posts them to the session's own
portal route, `/s/<name>/portal/api/opc/write`, where portal's switch and whitelist answer. The
switch is the project's (`writes_armed`) or a shell's in process, never the wire's; the binding
check refuses at load an action on a tag no rule marks writable, so a write the page offers is one
portal would take. The page shows an action in the warn colour, disabled while the session's switch
is off, and asks before posting.

## Verified in the browser (2026-11-09)

Against the demo plant of C-051, writes off: Outlet 3 selected by pointer, its "Release full state"
shown gated and disabled, "Writes go through portal. Its write switch is off." Writes armed by the
project (supervisão restarted): the button enabled, "Its write switch is on."; pressed by pointer
(the browser's confirmation answered in script, the pane having no native dialog), the page read
back "Release full state: written (Good)", and the plant's reaction emptied the outlet (72 % to 0,
filling again from there, the sparkline showing the drop).

Screenshots: `.zen/evidence/supervisao/layout.jpg` (off: disabled) and `write-armed.jpg` (armed:
written, the outlet emptied; taken before the green accent).

## Refute round 1 (2026-11-10, at 70249c7): refuted, one gap

Everything else held (portal answers the switch before it reads a body, so "nothing reaching the
plant" follows from the code's order as well as from the wait; every escape path was tried). The
gap: portal's `Live` exposed its switch (`pub gate`), so a route of supervisão's own could arm it
(`live.gate.set(true)`) with none of the words the test bans; the critic's one-line route did, and
a write landed with the project's switch off. Fixed at the root, in portal: `Live`'s switch and its
handle lists are crate-private, so outside portal the switch is read through `writes_armed` and set
through `Session::set_writes_armed` alone, and the compiler refuses the critic's line. The test also
bans `.gate`, `live.opc` and `live.channels`, sweeps every route of supervisão's own with POST, PUT,
DELETE and PATCH (405) and a GET, then reads the switch still off and a post still refused, and
reads the bundle's write button disabled by the status's switch.

## Refute round 2 (2026-11-10, at 7c4aeb7): refuted, two gaps

The page could post something other than the action pressed and stay green: the fixture had one
action, its value "1", its source the one the object reads, and the test checked only that the
bench read 1. The critic's page sending `{ ...actions[0], source: the object's, value: "1" }` asked
"Write 7 …" and wrote 1. And the switch's start position was still decided in supervisão's reach:
`SessionConfig.writes_armed` and `Project.writes_armed` were public, so `Host::start` could arm a
session the project left off (the critic's one line, behind an environment variable, did, with no
word the scan bans), and the evidence's "set through `Session::set_writes_armed` alone" was not
true at start.

The answers. Outlet 3 now offers a release of 7 to the controller it reads and a hold of 3 to a
second controller of the bench (`aux`), a source the object does not read. The page is pressed for
each: the release lands 7 with the hold's tag untouched, the hold lands 3 at its own controller with
the release untouched; the questions the page asks are captured ("Write 7 to … of plc?" for every
release press, "Write 3 to … of aux?") and the bodies it posts are read from the browser's network
events, each the binding's action. In portal, both start-position fields are crate-private and read
through `writes_armed()` (portal's executable and tests, supervisão's plan printout): the
critic's line no longer compiles. The scan reads every Rust file under `src` however deep, bans
assigning the start position, spawning a worker of its own and pulling a file in by path, and
refuses a build script.

Four page mutations rebuilt and run, each red: the critic's (the first action, the object's
source, value 1), every button posting the first action (the hold never landed), the body posting
value 1 (the release landed 1, not 7), the question naming no source. The critic's host line no
longer compiles (`E0616`, `writes_armed` of `SessionConfig` is private).

From reading only, kept out of the clause: portal's write route checks neither the content type nor
the origin, so while armed a page of another origin open in the operator's browser could post a
write unasked. That is portal's surface, reported as a follow-up.

## Refute round 3 (2026-11-10, at 105a374): refuted, two holes in the scan and one gap

Round 2's scan was a deny-list, and two routes passed it. Supervisão loads the project itself, and
portal's text loader is public: re-reading the file, turning `armed = false` into `armed = true`
and loading that (behind an environment variable, as round 2's mutant) started the session armed,
a post landing at the plant. And core, a direct dependency, has an ungated telegram link: a GET
route of supervisão's own could dial a device and send it a frame with the switch off, the 405
sweep's GETs carrying no query. The gap: the second action's button was never read with the switch
off (only Release was), so a page gating the first button alone stayed green.

The answers. The scan is now an allow-list: every path of core's and portal's that a source names,
its `use` trees written out, its inline paths, and the items it reaches through the one module it
imports whole (`project`), must be one of the twenty-three supervisão reads and serves with, each
seen at least once; nothing of theirs renamed (`as`) or taken whole (`*`); no socket type but
the host's one listener, no file written, no program run. The reader itself is checked on a sample
that names `project::load` and `telegram`. Both buttons are read disabled with the switch off at
start and after the disarm, and enabled while armed.
