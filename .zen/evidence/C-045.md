# C-045 evidence - one header reader

## The design (2026-11-08)

The four readers (the channel file, the catalog, the controller file, the bench file) each
carried the same ten lines: parse the header, match the format, match the version, each
refusal in the same words with the file's own noun. P-010 parked the shared reader until a
second component needed it; the project file is that component. `veredas_core::schema` reads
the stamp before the body with two entry points: `check` for a reader that knows one version
(the four, and the project file today), `stamp` for a reader that knows several and decides what
to do with each (the migration hook the plan promises, with no older TOML version to migrate
yet). The texts are unchanged: each reader maps the shared error onto its own variants, so every
reference's pinned refusal still reads as before, and the four readers' tests are the proof that
nothing moved.

## Refute round 1 (2026-11-09): refuted, two gaps

The critic found the stated order broken by a key of the wrong type: the header was
deserialized in one step into typed options, so `format = "veredas-other"` with `version = "1"`
came back as "not a thing file: invalid type: string" before the format was compared, and
`format = 1` the same, valid TOML reported as not TOML; and `stamp` without a `format` was never
asserted, so a mutation reading a missing format as "" survived the unit test. Fixes: the two
keys are read as TOML values and judged one at a time, the format whole (absent, not a string,
another) before the version is looked at (absent, not a whole number a `u32` holds, another); a
key of the wrong type is refused in the not-TOML form naming the key ("`format` is not a
string", "`version` is not a whole number from 0 to 4294967295"), the form the references pin by
prefix for a fractional version, so no reference moved. A first cut parsed the whole text into a
`toml::Table`: that materializes every body value, and the catalog's reference carries an offset
of 2^64-1 that `i64` cannot hold, which the stamp then refused for a body it never reads. The
header is a struct of two optional values again, every other key skipped unread, and the unit
test holds a body value past `i64` as the reader's own to judge. The unit test grew to both keys
missing, the keys inside a table, the wrong types for each key, the largest `u32`, the stamp
without `format`, of an empty text and of a wrong type; the five readers' tests passed unchanged
(the catalog's 12, the channel file's 9, the controller's 8, the bench's 6, the project's 7).
Held by the critic: the order and the texts for well-typed keys (a version-first mutation failed
the test), both keys missing and the keys inside a table refused for the format, version 0 as an
unknown version in `check` and read as it stands by `stamp`, the five callers' mappings exact and
each of the four readers' tests asserting all five texts.

## Refute round 2 (2026-11-09): refuted, one gap

Both round-1 findings held fixed and both mutations asked for were caught (the version judged
before the format in `stamp`, a negative accepted). One gap: the two keys were read as
`toml::Value`, whose integer is an `i64`, so a `version` of 2^64-1 or 2^64 failed inside the
value type ("u64 value was too large", "invalid type: integer … as i128") before the format was
judged, and a file of another format with such a version was refused for its version, the order
the clause rules out. Fix: each key is read through a visitor of its own that takes a string, a
whole number of any width the parser offers (64, 65 and 128 bits alike) or anything else set
aside, so the key's type is judged by the reader and never by a value type's limits. Probed and
pinned: up to 2^128-1 the parser hands the integer over and the reader names it; at 2^128 the
parser itself overflows and its reason comes first, before any key, as for any text it cannot
read. The unit test grew to the wide versions on both formats, an integer `format` past 64 bits,
an inline table, a date and a nan as versions. Held by the critic: hex, signed and underscored
integers read as the integers they are; a multi-line string and quoted keys read; the body
skipped unread for every value the parser accepts; body syntax errors first, for any format; the
five callers passing the not-TOML reason through unchanged, so the typed refusals reach every
reader with its noun; the readers' tests unchanged and green.

## Refute round 3 (2026-11-09): holds

The critic probed the visitor with every value shape it could think of: `inf`, floats and
exponents, empty and nested inline tables and arrays, an array of tables and a dotted key under
the version, offset and local datetimes (the parser's special map form, drained), hex integers
past 64 bits, the lowest `i128`; octal, binary and hex spellings read as their values; escapes,
literal and multi-line strings, a BOM and CRLF read as the format they spell. Draining a sequence
or a map under a key never changes the order: another format with a version of nested arrays
holding 2^128-1 and 2^64, or of a table of dates, is refused for its format. The saturation at
`i128::MAX` is reachable for 2^127 and above and harmless, far past `u32`. Below -2^127, past
2^128 or with a float past `f64` anywhere, the parser's reason comes first. Each visitor arm
dropped by mutation turned the unit test red; the readers' sources and tests are unchanged since
round 2 and green. Verdict: holds, after three rounds.
