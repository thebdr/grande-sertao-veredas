# C-042 evidence - the engine pinned

## The design (2026-11-07)

Veredas 1's `veredas-store/tests/capabilities.rs`, as it was, plus the engine's version text,
for the same reason core pins the OPC stack (C-023): the store's assumptions about the engine
are listed where a bump will break them by name. Each probe is one assumption: the appender
and the cloned connection (the ingest and query split), the wire types of a sequence and a
timestamp, the nearest-in-time join, the time bucket, `DESCRIBE` as validation, the catalog
functions, the memory figure, the snapshot by `COPY FROM DATABASE`, the file-backed limits, the
shared connection, and the live CSV view.

The bundled engine compiles once per target directory (about six minutes here; the profile
override keeps its library optimised and without debug info, or every test binary that links it
maps a 2.2 GB library, which Veredas 1 found exhausts the page file). The light build
(`--no-default-features`) does not carry it, as C-034's graph walk proves.

## Refute round 1 (2026-11-09): refuted, three pins weaker than the clause and the read side unpinned

Three pins asserted less than the clause said: `DESCRIBE` was shown "without running the query"
over an empty table, which an engine that ran the query would also pass (now a cast that fails
on the row the table holds describes while the same select run errors, and the binder's exact
words); the temp directory was set and never read back and the memory limit checked by a
substring where the store reads the exact text (now both exact); the widened CSV view was shown
through `DESCRIBE` alone, not in its rows (now the row). And the store relies on read-side
behaviour no pin named, so a bump would fail a store test or change results in silence: the
value variants the cells and the listing match on (a date, a time, a decimal, an interval, a huge
integer, a timestamp), the listing's aggregate over a union skipping null cells and typing the
last value, the positional tie-break sorting nulls last under `DESC`, an empty table copied to a
header alone, `EXPORT DATABASE` with its views in the schema and its sanitised file names, the
CSV reader's options (a decimal comma typed, a ragged file padded), the sniffer's outcomes on a
marked, a header-only, an empty and a missing file, and a copy into a foreign database refused
by the engine and detached after. Eight pins added, one per assumption; the clause names them.
Noted for C-041, outside this clause: a ragged file the engine does not collapse to one column
(`a;b;c` with a short row and a long one) is sniffed to the widest row and the others dropped in
silence; the store's recovery covers the collapsed case alone, as its clause says.

## Refute round 2 (2026-11-09): refuted, two pins incomplete

The listing-aggregate pin's only null-valued row had a null key too, so its distinct count came
out the same with or without the filter the store relies on: a pin that proved nothing of the
filter. A new pin holds a keyed row with a null value and shows the filtered count 2 against the
plain count 3. The padding pin covered a short row alone; the engine meets a long row two ways: a
long row inside the sniff sample widens the schema by a numbered column and keeps every row, a
long row past the sample refuses the whole read with the line named. A new pin holds both, and
the clause says so. Held by the critic: every other new pin exact and engine-specific (the
positional order would differ under nulls-first, the export names deterministic and in name
order, the decimal's scale the engine's, the foreign copy's text), the three round-1 fixes.
Noted for C-041, outside this clause and its rounds: charting a text column that holds no number
or a time column meets the engine's cast error (the clause claims a numeric column alone; a time
charted as its epoch milliseconds, as the narrow surface reads it, is a decision worth taking);
and a live CSV view over a ragged file the engine does not collapse loses rows in silence, or
refuses the read past the sample, against the plan's "read live". Both in the hand-over for the
owner.

## Refute round 3 (2026-11-09): refuted, a window misnamed and two assumptions unpinned

The long-row pin named the engine's window "the sniff sample", and it is not: a long row
widens the schema inside the file's first 2 048 lines, the header included, and refuses the read
past them, whatever the sample size (sampling the whole file moves nothing); the pin's row at
line 30 002 was past every candidate window, so a bump that moved it would have passed. A pin now
holds lines 2 048 and 2 049 and the whole-file sample, and the clause names the window. Two
assumptions the coverage walk found unpinned: a view binds when it is created (a forward
reference failing with the catalog's text and leaving no view, a bad column with the binder's
text, the retry succeeding), which the store's fixpoint over view definitions rests on; and the
appender taking the store's typed cells (a text, a null, a microsecond timestamp, a double, nulls
in typed columns) through a slice of `ToSql`, read back exactly. Held by the critic: the
filtered count, the early long row and its `column3` (the engine's zero-based name, the same as
the empty file's `column0`), the attached database left out of the catalog listing (the store
attaches only under the lock the listing takes), and the rest of the store's SQL as plain SQL or
already pinned. With these three, the critic finds nothing in the store a bump could move
without failing a pin by name.

## Refute round 4 (2026-11-09): refuted, the sniffer's ragged outcomes unpinned

The engine's sniffer, the first step the store takes on every linked CSV and the whole of a
plain view's scan, meets a ragged file three ways no pin named: a short row collapses the file
to one column (the one case the store recovers), a long row within the first 2 048 lines keeps
that row alone with no error, one up to line 20 480 (the sample's default) refuses the sniff, and
one past it refuses the read with the line named. A pin holds the four, and the clause names
them. Held by the critic: the 2 048-line window under the store's own options (CRLF endings, a
decimal comma, a tab delimiter), the view binding, the appender's cells (an int cell takes the
pinned path), and the coverage walk otherwise clean. For the store's owner, outside this clause:
the plain path loses rows with no error on such a file and the sniffer gives up on a recoverable
one, both against the plan's "read live"; the hand-over says so.

## Refute round 5 (2026-11-09): refuted, the kept row named and the window's lower edge

The sniffer pin counted the row the engine keeps on a numeric long row without naming it, and
the clause's "keeps that row alone" was true of that fixture alone: a text long row keeps no
row, and a long first data row collapses the file to one column (the case the store recovers).
The sniff window's end was pinned from above alone (line 20 481 read); a bump that lowered it
would have passed. A pin now names the kept row, holds the text and first-row outcomes, and
refuses the sniff at line 20 480; the clause says the three outcomes and names the window as the
engine's default sample size, which `sample_size` moves and the store never passes. The final
coverage walk is clean apart from these.

## Refute round 6 (2026-11-09): refuted, the sniffer's rule misstated

The clause's rule for a long row ("after the first data row keeping that row alone") was true of
the fixtures alone, every one of which put the long row last. What decides the outcome is
whether the long row is the file's last line and whether the file runs past 2 048 lines: in a
file of at most 2 048 lines a long row as the last line is kept alone if numeric and keeps no row
if text, and a long row with any row after it collapses the file to one column, numeric or text
alike (the case the store recovers); in a longer file a long row up to line 20 480 refuses the
sniff and one past it refuses the read with the line named. Three pins hold the cases the rule
had wrong, and the clause states the probed rule and nothing more. The forced path's wording
stands (it widens and keeps every row whether rows follow or not). The coverage walk is
otherwise clean.

## Refute round 7 (2026-11-09): refuted, the rule's two remaining errors

The round-6 rule tied the outcome to the file's length; it is the long row's line and what
follows it: a long row on any line up to 2 047 with a short row after it collapses the file,
numeric or text alike, whatever the file's length (line 1002 of a 3 000-line file collapses, it
does not refuse the sniff); long rows ending the file within its first 2 048 lines are kept, alone
of all its rows, and a trailing run of two is kept whole, not the last alone; a long row from
line 2 048 with a row after it, or on lines 2 049 to 20 480, refuses the sniff; one past 20 480
refuses the read with the line named. Three pins hold the two corrections, the round-6 pin's
comment says why line 2 048 refuses, and the clause states the probed cases and no rule beyond
them. The coverage walk is otherwise clean.
