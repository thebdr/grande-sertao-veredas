# C-250: veredas-oficina, the component

## Why it is shaped so (2026-11-25)
The architect's "start the oficina crate", after the own-shell spike's verdict
(`docs/oficina-plan.md`, "Verdict"; the spike's evidence is `.zen/evidence/P-015.md`).
- **Qt behind features.** The window links Qt 6.12 through cxx-qt and KDDockWidgets, the tests
  Spix and AnyRPC. Built by default, every member's build and pre-push run, the orchestrator's
  whole-suite run and GitHub's run would need all of them and `QMAKE`, and would compile the
  bridge's C++. Q370 asks the architect; taken meanwhile: `shell` and `driver`, off by default.
- **`QMAKE` in cargo's environment, not found by Oficina's build script.** A first build script
  set `QMAKE` for itself where the plan's install puts Qt; cxx-qt's own build scripts (cxx-qt,
  cxx-qt-lib) read it too, from cargo's environment, and failed ("Could not find Qt"). So a build of
  the window names it: `QMAKE=$HOME/.local/opt/Qt/6.12.0/gcc_64/bin/qmake`. The machine's cargo
  configuration (`~/.cargo/config.toml`, the orchestrator's) could name it for every run; asked of
  the orchestrator, not written.
- **What ships carries no test server.** Spix's server drives the window over a socket; the spike
  started it when `OFICINA_SPIX_PORT` named a port, in every build. Here it is compiled in only with
  `driver`, which only the tests ask for (the review's entry 33, loopback being no boundary, is
  unruled under Q31: the narrowest choice is taken).
- **Core without its default features** (C-073): the tree needs the header reader alone. With core's
  default, Oficina's graph held the OPC UA client, tokio and the rest.
- **cxx-qt-lib's `qt_full`, not `full`.** The spike took `full`, which brings cxx-qt-lib's
  integrations with chrono, time, url, uuid, image, http, bytes and serde; the component test's
  check of a plant's stack caught chrono in the window's graph. The bridge uses Qt's own types
  alone.
- **No `MAP` row yet.** L5 lets a component outside the map use core alone, and the first code
  does; the row (portal at least) is a contract change that comes with the first edge to portal.

green against seven mutants:

   the suite's graph is read with its dev edges.
2. Spix named under `#else` of `#ifdef OFICINA_DRIVER`, or after a closed inner frame inside an
   outer `#if 1`, passed the reading of `shell.cpp` (it knew no `#else` and reset at depth 0).
   Answered: a stack of conditions, `#else` and `#elif` moving a frame on, the two mutants and
   `#elif`, `#ifndef` and spacing pinned as fixtures of the reading.
3. `let driver = driver || …` after the asserted line put Spix into the shell-only binary (894
   `spix::` symbols, against none on the real tree), and an unconditional `SpixCore` or `anyrpc`
   would have passed. Answered: `driver` assigned once, every way of assigning counted, and each of
   the four names once, inside `if driver`'s block.
4. "Docked" was never asserted: the pane found by name wherever it sat. Answered: the docking area
   describes its dock (open, not floating, drawn in the main window) and the test reads it.
5. "The model builds with no Qt" was never compiled: every target the component test touches is

6. "No licence is stated" had no assertion. Answered: none in the manifest, no licence file.
7. The graphs were read for this host only. Answered: `--target all`.
What held: core's default features caught by the plant-stack check; the empty tree not vacuous;

## Refute round 2 (2026-11-25): refuted, six findings, all answered
The round-1 mutants were all caught. Six new ways through, the first on the real tree:
1. `CARGO_FEATURE_DRIVER=1` in the environment of a shell-only build gave a binary whose Spix
   server answered over loopback (cargo does not clear an inherited `CARGO_FEATURE_*`).
   Answered: the build script takes `driver` from the compiler (`cfg!(feature = "driver")`).
2. `driver` bound again through a pattern (a tuple, `let Some(…) else`) passed the count of
   assignments and shipped Spix.
3. `cargo check` passed with a Qt library linked unconditionally, where a build failed.
   Answered: `cargo build` of the library and its tests.
4. The pane laid over the window beside the docking area still read as docked (dock and pane
   paired by id). Answered: the pane's parents must reach the docking area.
5. `#define OFICINA_DRIVER` in `shell.cpp`, or Spix included from `shell.h`, passed a reading of
   `shell.cpp` alone, and nothing built what ships.
6. "One private seam" had no assertion. Answered: the sources read for it.
Findings 1, 2 and 5 rested on readings of the build script and the C++, which kept being evadable.
They are answered by building what ships: the window built with `shell` and without `driver`, in
a build folder of its own, with `CARGO_FEATURE_DRIVER` and `OFICINA_SPIX_PORT` set in its
environment against it; its bytes holding no name of Spix's or AnyRPC's (the window's own QML is
compiled in, so a comment of `Main.qml` naming Spix was reworded), and started with a port named,
nothing answering there. The readings and their fixtures are gone. The first build of that folder

## Refute round 3 (2026-11-25): refuted, four findings, all answered

   release tool, `tools/alforge`): a build script keyed on `PROFILE` shipped a working Spix server

   Answered: the dock closed takes the pane from view, opened brings it back.

   Answered: no `pub use` in the seam, and no file outside it names it but `lib.rs`'s one line.
4. A link search under `$HOME/.local/opt/Qt` passed the "no Qt" build, Qt being there.
   Answered: the build runs as a machine without Qt would: a fresh build folder, an empty home,
   no qmake on `PATH`, no library path.
