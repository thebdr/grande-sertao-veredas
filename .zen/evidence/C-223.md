# C-223 evidence - byte-faithful edits of a workbook Ábaco did not write

## The port (2026-11-22)

From Veredas 1's `crates/veredas-abaco/src/patch/` (`mod`, `package`, `sheet`, `refs`, `cached`,
`styles`, `xml`), its `a1` and the model half of its `workbook` (here `book`), with their tests
(`tests/patch.rs`, `patch_untouched.rs`, `patch_no_styles.rs` and the `no-styles.xlsx` fixture,
upstream IronCalc's `arithmetic.xlsx` without its styles part). Veredas 1 built it on the architect's
ruling AB9 (2026-11-04): a workbook Ábaco did not create is patched, never rewritten. There it was
proven against an older in-house tool's patcher and opened by a real Excel on two real systems with
no repair log; neither the workbooks nor Excel are on this machine.

Changed on the way:
- the model's workspace half (log, macros, preferences, history, the `.abaco` save) is left for
  phase 3; `Workbook::open` reads `.xlsx` and `.xlsm` and keeps the link log on the workbook;
- the source's "moved while patching" check compares the bytes read again with the bytes first read
  (Veredas 1 hashed them with SHA-256; no hash crate joins Ábaco's graph);
- the atomic write moved into `files`, shared by the patcher and `Workbook::export`;
- zip 9's entry names are fallible: an unnamed or undecodable entry is a refusal, not an empty name;
- the edits stay typed and JSON-valued as Veredas 1's tools sent them; an edit file comes with the
  command line, in stamped TOML, once core's header reader can be had without core's network layers
  (asked of core through the orchestrator);
- comments and test data that named the older tool, its files or a customer replaced (one custom
  property's value `PLANT-A`).

## The corpus test, and what it found (2026-11-22)

`tests/patch_corpus.rs` patches every workbook among the fork's test files, Excel's and the others',
twice: with nothing to do (every part must come out equal), and with the first plain number of the
first sheet that has one replaced (only worksheets may differ, and in them only that cell and
formula cells; the calculation chain at most dropped; the patcher's own verification on). It found
four defects of Veredas 1's patcher, each answered in `src/patch`:

1. `missing_r_on_row.xlsx`: a `<row>` without `r` (rows may leave it implicit) was always rewritten,
   so a sheet no edit touched came out with `r="1"` added. Now a row whose only change is that `r`
   gets it only when the part is rewritten anyway (a row inserted before it would shift what it
   implies); alone it is no reason to rewrite the part.
2. `example.xlsx`: a chart sheet (`chartsheet` relationship, no cells) made the patcher refuse the
   whole workbook, `no sheet named "Chart1"`. Sheet entries now carry their kind; only worksheets get
   a job or have their cells read; a chart sheet's part is copied as it is.
3. In the same file: a local defined name's `localSheetId` was written back from the engine's sheet
   order, which skips chart sheets, so a name scoped to a sheet after one would have pointed one
   sheet early. It is now the sheet's position among the file's `<sheet>` entries.
4. `DynamicArrays.xlsx`: `RANDARRAY` spills into cells that hold no formula of their own; the
   volatile measure (two evaluations compared) looked at formula cells only, so the patcher's
   verification failed on them. Spilled cells now count as computed; and since a random draw can
   repeat (one cell of a 0-to-100 array did, about one run in eleven), a cell whose own formula
   calls a volatile function, and every cell it spills into, is unstable by its text, the measure
   over three more evaluations covering what moves with them.

Result: nothing to do, 266 workbooks, every part equal; one number changed, 234 workbooks (32 hold
no plain number), every assertion holding.

`cargo nextest run -p veredas-abaco`: 79 tests, all passing (the crate's 30 unit tests among them).

Owed: Excel's acceptance of a patched file (Veredas 1's exit had it, on the Windows desk); the edit
file.

4. **A chart on a chart sheet was not re-spelled** (charts were reached through worksheets'

5. **Verification ran after the rename, and failed on deletes over the corpus** (49 workbooks of

6. **A volatile function behind a defined name counted as moved** (`R` = `RAND()`, a cell `=R`).

## Refute round 2 (2026-11-23): refuted, answered

2. **A volatile name of one sheet froze a formula of another**: names were read by name alone.
   Each formula's names are now resolved as Excel resolves them, by the sheet that qualifies them
   or the formula's own, the local name before the workbook's; the token reader carries the
   qualifying sheet. `a_volatile_name_of_one_sheet_…` and the resolver's unit tests.
3. **An array that changed size left the file wrong, and verification could not see it**: its
   spilled cells stayed (a 0 left as a constant when the anchor's row went: gap 1's leniency), the

   way round), a cell the array now reaches that the file lacks is written as a spilled cell (only
   where the edits made it reach it, or moved its value: a cell the file left out that the array
   reached already stays out), one it left goes; and verification reads back the cache of every
   cell whose value the edits moved. The corpus's one-number pass checks the converse itself, its
   evaluations seeded alike: every computed cell whose value moved holds the new value in the

4. **A format or validation that lost its first row turned `#REF!`**: its formulas are relative
   to the range's top-left cell; where a move deletes that cell and the range survives, they are
   now re-anchored on the cell that becomes the top-left, then shifted (`A2>5` stays `A2>5` on
   A2:A9). Excel's reading of it is owed with the rest.
5. **A volatile function called through a LAMBDA name, and a cell that only reads a random one,
   moved by chance** (13 and 12 rewrites, 16 and 15 refusals in 300 runs): a name called (`Coin()`)
   is now a name read, and every evaluation the patcher compares (before the edits, after them,
   verification's) is made with one seed and one pinned time, so a draw is the same in all of them
   unless an edit moved it; the measure of what moves with a volatile function compares
   evaluations with four other seeds on four other days. The host's clock pin comes back after a
   patch and the random functions go back to chance. Twenty runs, every cache kept, never refused.
6. **A refreshed cache kept the `vm` that marked a `#CALC!` or `#SPILL!`**: it is dropped unless
   the new value is that error (`FILTER_ERRORS.xlsx`, E1).
7. **Verification was off by default** while the clause promises it: `PatchOptions::default()`
   verifies; off, a patch writes what it computed unchecked.
8. **A text with a carriage return was always refused** (XML reads it as a line feed): it is
   written `_x000D_`, as Excel does; a literal `_xHHHH_` and control characters were already
   protected. Four texts read back exactly.

The critic also named, as safe but unpinned, 3-D references (`Data:Other!A5`) and the
intersection operator, which the engine does not evaluate: a move that reaches them is refused by
