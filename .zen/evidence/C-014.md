# C-014 evidence - the sort plan

## The port (2026-11-05)

From Veredas 1's `crates/veredas-telegram/src/sortplan.rs`, now `src/telegram/sortplan.rs`; its
inline tests are `tests/telegram_sortplan.rs`. Two tests read private fields (the compiled rules,
the sticky map); `SortPlan::live_rules` and `SortPlan::remembered` now answer them publicly, and
the sticky bound is asserted exactly (100 kept of 1 000, not "at most 100"). The module doc's
pointer to Veredas 1's `plansource` (trajetorias' loader) is a loader the bench will own.

## Refute round 1 (2026-11-05)

Refuted on three behaviours, each inherited from Veredas 1, and fixed:
- a plan of routing rules alone answered `EmptyPlan` before consulting its rules, against Veredas
  1's own design doc ("one with only routing.csv decides by content"); `EmptyPlan` now means no
  destination, no live rule and no reject chute;
- a remembered `@table` answer was checked against the main table only, so a chute that exists
  only in a named table was trusted over its own limits (a parcel remembered for chute 30 came
  back at 8 kg and got 30 again); every table is consulted now;
- an infeed written `01` did not match a row scoped to `1`, though the filter doc and Veredas 1's
  design doc say it should: two integers now compare as numbers.
Also fixed: the draw point was rounded to 6 decimals, skewing weights that sum below 1e-4
(1e-7 : 1e-7 drew 10 000 : 0); it is drawn unrounded from `Pcg32::next_f64`. A weight that is not
a finite positive number is never drawn (an infinite weight took every parcel). The clause
promised a cut on cycles of tables, which cannot occur (a table row names a chute, never a
table): the dead depth check and the phrase are gone.

Tests added on the critic's untested claims: first match among two, shares with a disabled and a
blocked heavy row and per infeed, one valid rule among broken ones routing, the sticky memory
keeping the newest (P999 and P900 sticky, P899 and P0 not), the named sticky key, every limit and
a value at its limit, the reject and undecided counters.

Held: stickiness recorded only on `remember`, weighted draws never sticky, a blocked chute leaving
the spread and the sticky memory until unblocked, the share tolerance (4.7 standard deviations,
failing both a uniform spread and a normalisation to 100), seeded replay.

## Refute round 2 (2026-11-05)

The round-1 fixes held. Refuted on four more, all fixed:
- a blank sticky key value, or a field value equal to another parcel's object id, handed one
  parcel's remembered answer to another; a blank value is no identity now, and field and object
  keys live apart;
- round 1 checked a remembered table answer against every table, so a chute unlimited in the main
  table but limited in its own let an 8 kg parcel back in; an answer now remembers the table it
  came from and is judged by that table alone. A rule's own chute is judged by the main table and
  trusted when unlisted there, as in Veredas 1 (round 1 had let a named table's filter or disabled
  row override an explicit rule, which no clause asked for);
- an answer remembered again kept its old place in the eviction order, so the oldest survived
  and the newest went; it moves to the back now;
- two weights of 1e308 summed to infinity and drew nothing; shares are taken relative to the
  largest weight.
Not established: whether GENIBELT sends tracking id 0 for an untracked parcel (every such parcel
would then share the key "0" when the plan keys on `id2`).
