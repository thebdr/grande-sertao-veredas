# C-027 evidence - message bodies written from named fields

## The design (2026-11-06, for the bench, kept for portal)

New in Veredas 2: Veredas 1's bench rendered a telegram body either as a text template (the
log emitters' engine, `{ts}` and drawn values) or as typed-in hex, and its typed catalog encoded
each message in code. With the catalog out of the suite (Q8), a body is written by rules:
`telegram::compose`, the inverse of `telegram::capture`, sharing its `BinaryField` and
`FieldType` so one field list serves both directions. A text template with `{name}` placeholders
(`{{` and `}}` literal), binary fields at offsets, a pad byte, a fixed length.

Choices, each pinned by the test:
- the template is parsed when the spec compiles (an unclosed brace, a stray `}`, an empty
  placeholder refused by character), not met on the first message;
- an integer is read from decimal text alone (no hex, no fraction), held to its type's range;
- text is padded with NUL to its length and refused when longer, never truncated; at length 0
  it is written as given, which is how an open-ended trailing text field is declared;
- hex is parsed as `framing::parse_hex` does and held to its length; at 0, as spelled;
- the body never grows past `MAX_BODY` (the framing's 16 MiB ceiling): an offset there is
  refused before any arithmetic grows the body, so a field at `usize::MAX` cannot wrap;
- `names` says what a body needs, so a rules engine can check a message's sources against it
  when a file loads rather than when the first message fails.
