# C-046 evidence - the project file

## The design (2026-11-08)

One TOML file for what Veredas 1 kept in a folder of nine JSON files, because a project is read
by the gateway and diffed by its operator, and one file diffs as well as nine when nothing in it
is machine-generated. What the gateway does not keep (the screens, the grep, the command
sequencer, the pages) is not in it: the apps own their screens, and a command is composed from the
write endpoint under the same gate.

The reader (`veredas_portal::project::load`) is the executable's `--check`: every rule compiled
once, every referenced file loaded, every path resolved against the file's folder, every table
name claimed once across the rules, the OPC rules, the catalogs' messages and the views, so a
project that loads is a session that can start. The OPC sources are compiled without their
secrets: the password is an environment variable the session reads when it starts (Q15), and the
check verifies everything but its presence.

The only older form is Veredas 1's JSON folder. `from_v1` reads it into this file as text the
operator keeps, naming in its notes what it did not carry and never guessing: a disabled part is
dropped and named, a telegram source (which had no catalog in Veredas 1) is named with what it
needs, a credential-store password becomes a variable name, a CSV-linked table becomes a view
over the engine's CSV reader. A later version of this file will migrate the same way: by rewriting
the file, never by guessing in memory.

The declarations the session reads (a log source, a timestamp rule, a capture rule) moved from
the session module into the project module, so the light build, which has no session, still
reads a project; the session re-exports them.

The law L7 over every file (every TOML file of the repository that is not a cargo manifest, and
every TOML block of a reference in `docs/`) holds each to the stamp with core's reader, so a
fixture or an example without one cannot land.

## Reconcile (2026-11-08): what loading proves

"A project that loads is a session that can start" was false for a backfill into a family without
a timestamp rule, a group name outside the shape, a message over the repeat cap and a reply rule
the channel refuses, all of which the session checked and the file did not. The file checks them
now, through the same functions the session uses (`Claims`, `channel::check`), and the clause names
the two things only the running pieces can tell: a view's SQL and the password in the environment.

## Found by the OPC clause's round (2026-11-09): a Veredas 1 tag with bits on a float

C-040's first round made compile refuse bits on a float tag (core never carved a float's wire
word). Veredas 1 accepted them and defaults a tag's type to float, so `from_v1` carried such a
tag as it was and the file it wrote no longer loaded, with no note saying why. A float-typed tag
with bits is now carried as an int word, and the note names the tag and the change; the import
test's folder holds one such tag, the file loads, and the note is asserted.

## Refute round 5 (2026-11-09): refuted, two gaps

The critic showed the hand-written reading of SQL leaking at both ends: a quoted table name and
a comma join slipped past the FROM/JOIN check (the gateway then refused the printed file), while
EXTRACT's FROM, IS DISTINCT FROM and a CTE with a column list were read as tables and cost
valid views. Fix: no reading of SQL at all. The session's table compilation (capture rules, OPC
rules with their secret from an environment, channel messages, the claims, the views' names)
became one function, `session::compile_tables`, that the session and the import both call; the
import loads the file it is about to print as the gateway would, compiles its tables with a blank
for every secret, and opens an in-memory store over them, so the engine that will run the file
judges its views over the very tables it creates. A view the engine refuses is left out with the
engine's own first line (a Catalog Error for a table nothing creates, a Binder Error for a
column no table has), and a view over one of those falls next. The engine then taught two more
things: a CSV-linked view fails here only because its file is on the plant's machine (an IO
Error), so such a view is set aside from the judging, carried as written and named, and so is a
view that reads it; and the test's own literal view had read the rule's key group as a column,
which the engine refused rightly, so the test now reads `key`. Tests: the import folder holds
fourteen tables, seven carried in order (the two CSV-linked ones named as not read here) and six
refused with the engine's reasons, twenty notes. Held by the critic: subqueries, CTEs and UNION
branches over a dropped table caught; the fixpoint in reverse order; dotted names, aliases,
outer joins and a table function carried; the law's ordered marks pinned by mutation.

## Refute round 7 (2026-11-09): refuted, one gap

The critic found a reader of a set-aside CSV view that also named a table nothing creates
