# C-046 evidence - the project file

## The design (2026-11-08)

One TOML file for what Veredas 1 kept in a folder of nine JSON files, because a project is read
by the gateway and diffed by its operator, and one file diffs as well as nine when nothing in it
is machine-generated. What the gateway does not keep (the screens, the grep, the command
sequencer, the pages) is not in it: the apps own their screens, and a command is composed from the
write endpoint under the same gate.

The reader (`veredas_portal::project::load`) is the executable's `--check`: every rule compiled
once, every referenced file loaded, every path resolved against the file's folder, every table
name claimed once across the rules, the OPC rules, the catalogs' messages and the views, so a
project that loads is a session that can start. The OPC sources are compiled without their
secrets: the password is an environment variable the session reads when it starts (Q15), and the
check verifies everything but its presence.

The only older form is Veredas 1's JSON folder. `from_v1` reads it into this file as text the
operator keeps, naming in its notes what it did not carry and never guessing: a disabled part is
dropped and named, a telegram source (which had no catalog in Veredas 1) is named with what it
needs, a credential-store password becomes a variable name, a CSV-linked table becomes a view
over the engine's CSV reader. A later version of this file will migrate the same way: by rewriting
the file, never by guessing in memory.

The declarations the session reads (a log source, a timestamp rule, a capture rule) moved from
the session module into the project module, so the light build, which has no session, still
reads a project; the session re-exports them.

The law L7 over every file (every TOML file of the repository that is not a cargo manifest, and
every TOML block of a reference in `docs/`) holds each to the stamp with core's reader, so a
fixture or an example without one cannot land.

## Reconcile (2026-11-08): what loading proves

"A project that loads is a session that can start" was false for a backfill into a family without
a timestamp rule, a group name outside the shape, a message over the repeat cap and a reply rule
the channel refuses, all of which the session checked and the file did not. The file checks them
now, through the same functions the session uses (`Claims`, `channel::check`), and the clause names
the two things only the running pieces can tell: a view's SQL and the password in the environment.

## Found by the OPC clause's round (2026-11-09): a Veredas 1 tag with bits on a float

C-040's first round made compile refuse bits on a float tag (core never carved a float's wire
word). Veredas 1 accepted them and defaults a tag's type to float, so `from_v1` carried such a
tag as it was and the file it wrote no longer loaded, with no note saying why. A float-typed tag
with bits is now carried as an int word, and the note names the tag and the change; the import
test's folder holds one such tag, the file loads, and the note is asserted.

## Q15 decided (2026-11-09): a sealed secrets file beside the project

The operator decided Q15: an encrypted secrets file in the project folder, committed with the
project, the key in an environment variable the project names; portal reads the key when the
session starts, decrypts in memory, and refuses a source whose secret is missing by the entry's
name, never a value. `password_env` gave way.

What changed, in this order:
- The project file: `secret = "<entry>"` on an OPC source in place of `password_env`, and a
  `[secrets]` table (`file`, `secrets.toml` beside the project by default; `key_env`, required),
  refused by name when a source names a secret without it, when its file or variable is blank,
  and for a misspelled key. `Project.secrets` carries a `SecretsSource` into the session
  configuration; the check needs neither the file nor the key, and the plan prints the file and
  the variable.
- The secrets file (`veredas_portal::secrets`): `veredas-secrets` version 1 through core's
  stamp reader (C-045; L7 covers its block in the reference), `[entries]` name to base64 of a
  96-bit nonce and the ChaCha20-Poly1305 ciphertext, the entry's name the associated data, so a
  value copied under another name does not open. The key is 256 bits, 64 hexadecimal characters
  in the variable, held in a type with no `Debug` of its bytes and zeroed when dropped. No error
  of the module carries a value or a key: the variable's name, the file's path, the entry's name.
- The executable: `--new-key` prints a fresh key and nothing else; `--secret <project.toml>
  <entry>` reads the value from stdin to its end (the final line break dropped), seals it under
  the key the project's variable holds, writes or replaces the entry (the file created stamped
  when none is there), prints the entry and the path, never the value; exit 2 for a project
  without `[secrets]`, a variable unset or not a key, a file that is not a secrets file.
- The session: `Session::start` opens the secrets file first, in memory, and hands
  `compile_tables` a lookup of an entry (C-040's compile takes the lookup unchanged, its parameter
  renamed from `env` to `secret`); the import's blank lookup stands. A variable unset or not a
  key, a file the key does not open, a source whose entry is not there: refused by name before
  anything spawns.
- The import: a credential-store password becomes `secret = "<source id>"`, the `[secrets]` table
  is written with the suite's variable `VEREDAS_KEY`, and the note gives the call that seals it.

Why a file beside the project rather than a credential store or a prompt: the project is
committed and diffed, and its secrets travel with it, sealed; the one thing kept out of the
repository is the key, which an operator sets where the session runs. Why the entry's name as
associated data: a sealed value is bound to the source it was sealed for, so copying a line in
the file gives another source nothing. Why `--secret` reads stdin rather than an argument: a
value on the command line lands in shell histories and process listings.

The proof is in `tests/project.rs` through the executable (the key made, the value sealed, the
file stamped on disk with the value nowhere in it, the four run refusals by name with exit 2

entry (C-040, its record re-recorded). The plan's note (`docs/portal-plan.md`) and the schema
(`docs/project-schema.md`, its REFERENCE mirror) moved with it.
