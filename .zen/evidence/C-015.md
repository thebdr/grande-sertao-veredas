# C-015 evidence - the decision path

## The port (2026-11-05)

From Veredas 1's `crates/veredas-telegram/src/decision_client.rs`, now
`src/telegram/decision_client.rs`. `decide`, `post_events` and `post_bin_state` returned
`Result<_, String>`; they return `DecisionError` now, one variant per failure, each displaying
Veredas 1's text. Veredas 1 tested its URL splitting and response parsing as private functions;
`tests/telegram_decision.rs` drives them through the public client against a one-shot loopback
service that answers raw bytes (a 500, a 302, a 204, no header break, an unreadable status line,
a body that is not the answer), so what is tested is what a real service would provoke.

On Windows a closed loopback port is retried by the stack before refusing, so an unreachable
service ends as `Timeout` within the client's bound there and as `Connect` on Linux; the test
accepts either and asserts the bound.

## Refute round 1 (2026-11-05)

The code held (a slow drip, a DNS lookup of 1.26 s, a held-open connection, each ended at the
bound); the tests did not prove three claims. Added: a reply dripping in one byte every 40 ms
ends in `Timeout` within the bound (and the silent service too), asserted against the bound
rather than "under 2 s"; a requeue onto a full queue keeps the bound and drops the oldest, in
both shapes; the stand-in service now reads each request whole by its Content-Length, as a real
service does, and asserts the announced length is the body's.

Not tested: a host name inside the bound (a DNS lookup on CI is not something a test controls).
Noted, not gaps: a 1xx answer is a refusal (the clause says non-2xx), and the parser is lenient
in ways a serde_json service never provokes (no `HTTP/` prefix check, a leading `+` in the
status). Operational trap: `http://localhost:<port>` with the service on 127.0.0.1 only tries
`::1` first, and Windows retries a refused loopback connect for about 2 s: name the address.

## Refute round 2 (2026-11-05)

The drip, silent-service, Content-Length and full-queue tests held against their mutants.
Refuted on the connect: CI (Linux) refuses a closed loopback port at once, so a client that dialled
before starting its timeout passed every test there, and on Windows the closed-port test caught it
by 12-25 ms of SYN-retry luck. Pinned with a listener that never accepts and whose queue is filled
(Linux drops the next SYN, Windows leaves it pending): `Timeout(300ms)` within [300, 900) ms.
