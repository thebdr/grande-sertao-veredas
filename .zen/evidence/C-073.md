# C-073 evidence - core's layers by feature

## The design (2026-11-23)

Ábaco's `.abaco` file reads its stamp through core's one header reader (C-045), and its component
clause (C-220) reviews every crate of its tree: a spreadsheet would carry an OPC UA client and a
runtime it never uses. `schema` imports serde, thiserror and toml and no other module of core;
`rng` imports nothing; `state` imports thiserror. So the plant-facing layers went behind a default
feature, `net` (the name ábaco's note offered), as the demo plant (`demo-server`) and the masters
(`modbus`, `enip`) already sat behind features of their own. Each master now names tokio itself, so
it stands alone; the demo plant names `net`.

What does not change: every member depending on core keeps the default, so a `--workspace` build
resolves core's features exactly as before. Measured on the change: the workspace's test build
compiled the suite's own crates and no database engine (the seed's dependencies untouched), and
supervisão's two tests that pin its dependency graph (`its_own_dependencies_are_core_portal_and_
the_servers_crates`, `the_plant_s_stack_reaches_supervisao_through_portal_alone`) pass unchanged.

The test asks cargo (`cargo metadata`, `cargo tree`, `cargo check`), as C-007's asks it what core
builds: what the manifest declares, what graph a component asking for no default features gets,
and that the library compiles in that form and with the masters alone, in a build folder of the
test's own (`CARGO_TARGET_TMPDIR`) so the run's folder is not shared.

## Refute round 1 (2026-11-23, run on e52e56d1): refuted, three gaps in the test, closed

The clause held (a scratch consumer worked; every one of the 12 feature combinations compiled with
no warning; each member's package set identical before and after the change, only core's feature
labels gaining `default,net`), but the test missed three ways it could become false:
1. the slim form's contents were never checked, only that it compiled: `schema`, `rng` and `state`
   gated behind `net` left an empty crate and a green test (core's own tests always see `net`);
2. the masters were compiled and graphed only together: a stray import of the other's framing in
   one passed;
3. build-dependencies escaped both the graph (`-e normal`) and the manifest check (kind null): a
   plant crate as a build-dependency passed.
Closed: a consumer crate of the test's own (its own `[workspace]`, core without default features,
the workspace's lock) is written and run, reading a stamp, refusing three, writing and reading a
state back and drawing the same numbers twice; each master is compiled and graphed alone, the
other's framing absent; the graph reads normal and build edges and the manifest check takes build
dependencies too. Each of the three mutants now fails. Not counted: `cargo doc` without `net` warns
of links to the gated modules.

## Refute round 2 (2026-11-23, run on 830cabb3): refuted, one gap in the test, closed

Round 1's three mutants fail. The gap: the default form was never compiled alone. Core's own tests
build it with the demo plant and both masters (the self dev-dependency), and the workspace adds the
demo plant through maquinar and the masters through mestres, so a layer of `net` standing on a
crate `net` does not hold (the demo server's, or a master's framing, imported into `opc` or
`telegram`) passed every test while every member keeping the default would fail built alone.
Closed: the compile check now builds the default form alone first; both mutants fail it.

## Refute round 3 (2026-11-23, run on ebba11ba): refuted, one gap in the test, closed

Rounds 1 and 2's five mutants fail. The gap: only the slim form was used by a consumer; the
default form, the demo plant's form and each master alone were only compiled, so `opc` gated behind
`demo-server`, `fieldbus` gated behind `net`, or a master's framing imported into the demo plant
passed while a member asking for that form alone (portal, a master's user, maquinar) would fail.
Every build of core inside the suite merges the forms, so only crates apart can see one. Closed: a
consumer for each form, asking for it alone and naming what it promises, is checked by cargo; each
of the three mutants fails.

## Refute round 4 (2026-11-23, run on 8a916e65): refuted, one gap in the test, closed

## Refute round 5 (2026-11-23, run on 1e80a456): refuted, one gap in the test, closed

Every earlier mutant fails. The gap: the gate audit read the source's text, so the opc layer's
re-export of the OPC UA value types (portal's `serve.rs` imports `opc::{StatusCode, Variant}`) put
behind `demo-server` passed when the gate was split by a line break or a comment, built by a macro
from tokens, written in a `#[path]` module outside `src/`, pulled in by `include!` from a file that
is not `.rs`, or set by a build script from the feature (m11 to m16); the critic's two controls, a
rustfmt-style multi-line `cfg(all(..))` and a `cfg_attr`, failed the audit as they should (m17,
m18). Hardening the text would chase forms without end, so the test now asks the compiler, as the
critic offered: rustdoc's pages of core and every `id` anchor on them, private items included, are
built for each of the twelve forms (the plant-facing layer off, on, or on with the demo plant; each
master off or on), and each of the twenty steps that adds one feature must lose nothing, add
something, and add only where that feature's layer lies. The text audit stays, its comment naming
what it covers. Two things on a page are not core's and are left out: the blanket impls, which
show whichever crates are in the graph (a master's framing brings tracing's `Instrument` onto
every type), and rustdoc's `notable-traits-data` tooltip script. Not reached, and said in the
clause: a `cfg!` built by a macro inside a function's body, which changes no item.

Measured on the new test (the critic's script, `~/.cache/veredas/core/c073-refute/r6pre-mutants.sh`,
on the round's export with the new `features.rs`): all eighteen of the critic's mutants fail, m11
to m16 on the compiler's view alone (`["net"] + demo-server adds outside its layer:
["opc/enum.Variant.html", ...]`), and so do three of mine for the reach inside a page and across
the masters: a master's constant behind `net` by a comment-split gate (m19, alone:
`["modbus"] + net adds outside its layer: ["fieldbus/modbus/constant.DEFAULT_PORT.html", ...]`), a
method of the state text behind `net` (m20: `[] + net adds outside its layer:
["state/enum.StateWord.html#method.from_number"]`, with the compile checks) and the OPC UA value
types behind `modbus` (m21, alone: `["net"] + modbus adds outside its layer`). The twelve forms'
pages take about 15 s once their dependencies are checked.

## Refute round 6 (2026-11-23, run on d9a0e546): refuted, five gaps in the test, closed

Round 5's view held for what it read (the critic's control n0, a root re-export behind the demo
plant, failed it), but it read names alone and rustdoc's own form. Five mutants, each gate split by
a comment so the text audit misses it, kept the test green while a member's real import line
broke: an item hidden from rustdoc (`#[doc(hidden)]` on the moved re-export, n1); rustdoc's own
cfg let through (`cfg(any(doc, ..))` on the OPC UA value types, n2); `Stamp::version`'s type
changed by `net` behind a private alias, its anchors the same (n3); a statement's gate inside
`schema::check` (n4); `schema::stamp` made `pub(crate)` by `net`, its page the same (n5). The
critic also judged the stated limit incomplete. Closed:
- the view now holds, by key, what each item renders: its declaration, each item anchor's header
  or field type, each row of a module's table with its visibility mark. It is built with private
  items and without, and every step must keep every key of the smaller form rendered the same, as
  well as add only inside its layer (n3, n5);
- each of the twelve forms gets a consumer crate naming every public path its view shows, checked
  by cargo against that form alone, so what rustdoc shows is what the build holds (n2);
- the text audit also requires that nothing hide an item from rustdoc, as ordinarily written;
  core has none (n1 as written);
- the clause states the two limits that remain: an item rustdoc does not see, however hidden; and
  a gate inside a function's body, which changes behaviour and not an item. That is the slim
  consumer's here and each module's own clause's in the merged form, where core's tests run (n4
  fails core's own unit test of the header reader there,
  `schema::tests::the_header_is_checked_format_first_then_version_with_the_pinned_texts`).

A trap met on the way, in the plan: a copy of the tree built into the worktree's target overwrites
the worktree's artifacts, since cargo keys a member's by its path relative to the workspace. My
round-5 mutant run and this round's critic shared the worktree's target, so the run recorded at
d9a0e546 may have linked a mutated core in some forms. The target was reset from the seed and core's
files touched before every run below.

Measured on the new test, in a copy with a target of its own seeded fresh
(`~/.cache/veredas/core/c073-refute/r7-mutants.sh`, `r7-mutants.out`):
- the base is green;
- n0, n3 and n5 fail the compiler's view: n0 adds outside its layer; n3 and n5 lose or change a key
  of the smaller form (the alias's declaration, `pub` to `pub(crate)`);
- n1 fails the text audit, its `doc(hidden)` as written;
- n2 fails both: the audit (its `doc` cfg), and the default form's consumer, with
  `unresolved import veredas_core::opc::NodeId`;
- m12, m16, m19 and m21, the earlier mutants only the view caught, still fail it;
- n4 passes the features test, as the stated limit says, and fails core's header-reader unit test
  in the merged form (`r7-n4-merged.log`).

The whole features file takes about 85 s once its dependencies are checked (24 doc builds, 12
consumers).

## Refute round 7 (2026-11-23, run on f6e0caea): refuted, four gaps in the test, closed

The critic worked on its own copy, in a target of the copy's own. Four mutants, each gate split
by a comment, kept the seven tests green:
- **o4a:** a glob re-export of `types` behind the demo plant, replacing the root's named one of
  `now_unix_ms`. rustdoc gives a glob line neither an id nor a link, so the view never saw it,
  and portal's real import line broke in the default form.
- **o4b:** raw HTML in the crate's doc, `<span id="blanket-implementations">`, so the scan cut
  the root page at it and lost every re-export.
- **o1:** `StateWord::ALL` with another value without `net`; rustdoc renders no constant's value.
- **o3:** `UnknownVersion`'s `#[error]` text changed by `net` through `cfg_attr`; rustdoc renders
  no derive's helper attribute.

The critic judged limit 2 too narrow: its class is what rustdoc does not render, not only a
function's body. Closed:
- every line of a table is a key: a glob's re-export by its text (o4a);
- a page with an id twice, or with the blanket impls' heading anywhere but once on a type's page
  as rustdoc writes it, is refused as holding an id from a doc comment (o4b);
- the default form's consumer names every path the members import from core today (45 paths, as
  grep lists them across `crates` and `tools`), functions and constants included (o4a again);
- a new test runs a behaviour probe of the slim layer in each of the twelve forms alone and
  requires all twelve to print the same (o1, o3). It prints every stamp and check of 14 headers
  with the refusals' texts, the state text's tables and lookups, the 107 state lines of core's
  state-text tests read and written back or refused with their texts, and PCG32 draws from five
  seeds, 458 lines in all;
- limit 2 is restated as what rustdoc does not render: held in every form for the slim layer by
  the probe, and for the plant-facing layer and the masters only in the merged form.

Measured on the new test, in the critic's copy with its own target (`r9-mutants.sh`,
`r9-mutants.out`):
- the base is green (8 passed);
- o1 and o3 fail the probe alone ("the slim layer in [] behaves otherwise");
- o4a fails the default form's consumer (the members' `now_unix_ms`) and the compiler's view
  (the glob line added outside its layer);
- o4b fails the page check ("an id in a doc comment") and the default consumer.

The features file takes about 125 s in the worktree once its dependencies are built.
