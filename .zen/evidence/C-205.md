# C-205 evidence - the executable

## The design (2026-11-23)

A shell over the library, as portal's and the bench's executables are: `check` (from phase 1,
now one command of three), `run` and `replay`. A run starts the plant's portal session from its
project file in this process (Q313 (a), taken meanwhile; supervisão's Q19 the precedent), waits up
to 30 s for the OPC UA sources and the channels to read live (a log reads when its lines come; the
binding and the waits say what is missing), runs, keeps the run and stops the session. The switch
stands where the project put it (C-200: the crate never arms it).

A replay needs the window in the session's store, and a fresh session holds only what its start
reads in: a log backfilled from a start in the past (C-037). It waits until the ingest's count of
lines holds still across two refreshes (600 ms apart) before it runs. Replaying a window of a
session that is no longer running needs a store opened read only, which is portal's (named in the
plan as later).

The exit codes tell a pipeline what happened without reading the output: 0 passed (or a sound
file), 1 failed (or a file with problems), 2 the command line, 3 aborted, 4 refused before
anything ran, or no session.

## Refute round 1 (2026-11-23): refuted, three findings, all closed

3. **An option's value that was another option** (`--project --runs`) was read as a path, and an

What held: an inverted window (4, the binding's text, nothing kept), a session that does not

## The architect's Q314 (b) (2026-11-25): the run arms the switch, once confirmed

Asked who arms portal's write switch for a run whose test writes, the architect answered "The run
arms and disarms": the run arms the switch at its start once the person has confirmed the list of
the test's gated writes, and disarms it at its end; the engine holds the power to arm. Built so:
`run::gated_writes` lists the test's writes and sends as written, `run::writes_fingerprint` gives
the list's fingerprint, and `RunOptions::confirming` carries the one the person confirmed; the
session's own arming, which only its owner can set, is handed to the run through
`LivePlant::with_arming` (the executable's `main.rs` alone names `set_writes_armed`, once); a run
confirmed for its own list arms the switch before its first step and disarms it on every way out,
a switch found armed left as found, a plant handed no arming refused as before. With no screen the
executable takes the confirmation as `--arm <fingerprint>`, printing the list and its fingerprint
when it refuses (Q320, taken meanwhile: the fingerprint, and a switch found armed left so).
