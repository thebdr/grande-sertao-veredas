# C-071 evidence - the Modbus/TCP client

## The design (2026-11-22)

The briefing names "existing crates" for the Modbus TCP client. tokio-modbus 0.17 (MIT or
Apache-2.0) frames the requests and answers, matches the transaction number and unit
(`verify_response_header`) and the function, and decodes the PDUs. Read before relying on it:
its typed `Reader` and `Writer` methods only `debug_assert!` that an answer holds the quantity
asked and echoes the write (a short register answer panics a debug build, and a release build
hands back fewer registers than asked). So the client calls the crate's `call` and checks every
answer itself: bits by their byte count (`ceil(n/8)`), words one by one, a write's echo whole.
The crate's decoder refuses a coil echoed as neither `FF00` nor `0000` and an MBAP length of 0;
both reach the client as a broken link.

What the client adds, each for a link a controller leaves running for years:
- the standard's bounds on every request (1 to 2000 bits read, 1 to 125 registers read, 1 to
  1968 coils and 1 to 123 registers written, 1 to 121 written by a read-write request, a range
  within the 65 536 addresses), checked before a connection is even opened;
- a bounded connect (`Timeouts::connect`) and a bounded answer (`Timeouts::response`), the
  connection closed on any answer not taken, as core's OPC worker ends a session whose call
  failed (C-022): no late answer is ever read as another request's;
- a write's outcome said as the plant may have seen it, as core's OPC writes say it (C-022):
  `Refused` and `NotConnected` never left, `Exception` is the device's no, `Unconfirmed` may have
  landed.

The client sits behind core's feature `modbus`, off by default. Without it, the first run of the
whole suite with the client turned supervisão's `the_plant_s_stack_reaches_supervisao_through_portal_alone`
red: that test pins supervisão's dependency graph, and `crc`, `crc-catalog` and `tokio-modbus` had
joined it through core. A component that only polls carries no fieldbus code; `cargo tree -p`
resolves features per package, so a feature switched on by the controller or a test crate does not
reach supervisão's graph.

The client is blocking, on a current-thread runtime of its own (a cyclic task calls it between
scans); a host name is not taken, only an address, so no lookup can hang a call.

## The peer the test drives

Core's tests cannot start the bench (L4). `tests/modbus_client.rs` runs a peer on loopback that
reads each request off the socket as bytes and answers with bytes: for the functions, the Modbus
Application Protocol specification's own example frames (V1.1b3), so the client is held to the
standard's bytes rather than to its own reading; for the failures, silence, a close, an answer
cut short, an answer too late, and thirteen answers that do not answer their request. A full
listen queue (backlog 0, filled) makes a connect hang without any network setup, so the connect
bound is measured on loopback.

## The bench (2026-11-22)

The whole device is the bench's Modbus server (maquinar, C-110), its frames maquinar's own code,
met from `tools/mestres`, a test-only tool crate that depends on core (feature `modbus`) and
maquinar (Q101, option taken). `tests/modbus.rs` reads what the plant side set and checks what
the plant side holds after each write; reads the server's own record of each request against the
specification's bytes (two implementations agreeing on the wire, neither the other's copy);
meets the device's exceptions (an address past a table, a unit not played); and turns its knobs.
A slow device applies a write before its late answer and a silent one never applies it: the client
calls both `Unconfirmed`, and the plant side shows why the word is "may have landed". A restart
(every connection dropped) ends the call with a broken link and the next connects again.

## Refute round 1 (2026-11-22): refuted, two gaps, fixed

Run on 19f9b80 exported whole, with scratch probes and mutants.

1. **A write's exception was always "not done".** The standard's exceptions 0x04 (a device
   failure while performing the request), 0x05 (acknowledge: accepted and still being processed)
   and 0x0B (a gateway's target did not answer, the usual answer of a TCP-to-serial gateway whose
   device timed out, the same physical case as a silent device) do not say the write was not
   carried out, yet the client reported them as the device's refusal, and the test pinned 0x04 on
   a write as one. Fixed: `refuses(code)` is true for 0x01, 0x02, 0x03, 0x06 and 0x0A alone; a
   write answered any other code (0x08 and codes the standard does not name included) is
   `Unconfirmed` with `Cause::Exception(code)`, the connection kept. A read's exception stays its
   no. Pinned: eleven codes on each of the six writes and on a read, one connection throughout;
   on the bench, a write to a unit the server does not play.
2. **The bounds test missed some functions' own bounds.** Three mutants survived both suites: a
   discrete-input read's limit raised to 65535, an input-register read's to 2000, a register
   write's range check removed. Fixed: every function with a quantity is refused at none, one past
   its limit and a range past the last address, each by its exact reason with no connection made,
   and each limit is taken at the last addresses it reaches. The three mutants now fail.

Held: 1500 random answers across the ten functions, no panic, every answer not taken closing the
link and every exception keeping it, a read never unconfirmed and a write never "no answer";
trailing bytes after a normal PDU and an MBAP length disagreeing with the byte count refused (the
crate's own decoder); a duplicated answer refused for its transaction; a peer dribbling a byte
every 100 ms cut at the bound; the bound covering the send, so a peer that never reads is bounded;
the limits the standard's, each largest request within the 253-byte PDU; the feature absent from
the normal graphs of supervisão, portal, controlador and entrega.

Seen and left, each within what the clause checks: an exception PDU with trailing bytes is taken
(the crate decodes the exception and ignores the rest; the MBAP length still bounds the frame, so
the stream keeps its place); bits answered with padding set past the quantity are taken (the
standard asks for zeros; refusing them would fail a sloppy device in the field for bits nobody
reads); a frame a peer sends at accept, before any request, with transaction 0 is taken as the
first answer (no earlier request exists on that connection, every failure closing the one before).

## Refute round 2 (2026-11-22): refuted, one gap in the test, closed

Run on 4594ebe (56b4e99 in it). Round 1's two gaps closed: its three mutants fail the bounds test,
and nine new mutants of the fix (an unconfirmed exception closing the connection, `refuses`
taking 0x0B or dropping 0x0A, a read's exception classed like a write's, mask and read-write left
out of `writes`, the bits check loosened, the truncation removed, the range check off by one)
each fail a test. Held: every code on every read its exception on one connection; a silent device
unconfirmed for the six writes and no answer for the four reads; a one-byte exception and a
protocol identifier of 1 refused; a stale echo after a kept exception never read as the next
answer.

The gap: the check that an exception answers its request (transaction, unit, function) was
tokio-modbus's alone, since the client's own `check` sees only normal answers, and no test sent
a mismatched exception. A copy of the crate whose `call` returned an exception before that check
left both test files green while a write answered by another request's exception read as "not
done", the connection kept. Closed by six rows of the mismatch table: an exception for another
function, transaction or unit, on a write and on a read, each refused, the connection closed and
the next call connecting again. The clause now names the ten functions the client speaks (Read
FIFO Queue, 0x18, is not one), and the bench test's largest requests are the registers' (the
coils' largest pass a bench table of 200; core's own test takes them at address 65535).

## Refute round 3 (2026-11-22): refuted, one gap in the test, closed

Run on e89700f. Round 2's gap closed at every level: the mutated tokio-modbus of round 2 (D1) and
six narrower ones (the header or the function check skipped for exceptions alone, the unit or the
transaction skipped for every answer or for exceptions alone) each turn the mismatch test red;
rounds 1 and 2's twelve mutants still fail. Removing the crate's read-buffer clear before a send
left the files green and is no gap: a stale leftover is then refused for its transaction.

The gap: the exception test sent eleven codes, so a `refuses` that also took 0x07 (the older
specification's negative acknowledge) or every code from 0x01 to 0x0A but the three "may have
done it" ones passed, reporting a write that may have landed as refused, the property round 1
fixed. Closed: every code from 0 to 255 is sent on each of the six writes and each of the four
reads over one connection, and `refuses` over the whole byte is exactly the five codes; both
mutants now fail. Not a gap but pinned with it: the feature is off by default, asked of cargo
(`cargo metadata`: no default features, `modbus` the one that brings the optional framing crate).

## Refute round 4 (2026-11-22): holds

Run on a9f1327. Round 3's mutants (0x07 taken as refused; 0x01 to 0x0A but the three "may have
done it" codes) fail at the pin on `refuses`, and two more that leave `refuses` alone (`call`
taking 0x07 as "not done" inline; an exception 0x09 closing the connection) fail the sweep over
the wire. Every earlier mutant, the client's twelve and the seven of tokio-modbus, still fails a
test. The feature test is live: a manifest with `modbus` among its defaults turns it red without a
rebuild. Looked at anew and held: the transaction number wraps (`wrapping_add`) and is checked,
then the function, for normal and exception answers alike; the clause's counts match the tests'
rows. Left as is: a non-optional framing crate added in a target-specific table would escape the
feature test, the client itself staying behind the feature's `cfg`, which is what the clause says.

## Core's features (2026-11-23)

With core's plant-facing layers behind a default feature (C-073), `modbus` names `dep:tokio`
beside its framing, so it stands alone without `net`, and core has a default feature. The test
`the_client_is_a_feature_off_by_default` asserted core had no default features at all; it now
asserts that neither the default features nor anything they switch on names the feature `modbus`
or `dep:tokio-modbus`, and the feature's exact list with tokio. A `tokio-modbus/<feature>` written
into a default list would switch the framing crate on (never the client, gated by `cfg(feature =
"modbus")`) and pass this test; C-073's exact lists of `default` and `net` and of the required
dependencies catch it (refute round on the change, 2026-11-23: holds).
