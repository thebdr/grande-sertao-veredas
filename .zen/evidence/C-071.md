# C-071 evidence - the Modbus/TCP client

## The design (2026-11-22)

The briefing names "existing crates" for the Modbus TCP client. tokio-modbus 0.17 (MIT or
Apache-2.0) frames the requests and answers, matches the transaction number and unit
(`verify_response_header`) and the function, and decodes the PDUs. Read before relying on it:
its typed `Reader` and `Writer` methods only `debug_assert!` that an answer holds the quantity
asked and echoes the write (a short register answer panics a debug build, and a release build
hands back fewer registers than asked). So the client calls the crate's `call` and checks every
answer itself: bits by their byte count (`ceil(n/8)`), words one by one, a write's echo whole.
The crate's decoder refuses a coil echoed as neither `FF00` nor `0000` and an MBAP length of 0;
both reach the client as a broken link.

What the client adds, each for a link a controller leaves running for years:
- the standard's bounds on every request (1 to 2000 bits read, 1 to 125 registers read, 1 to
  1968 coils and 1 to 123 registers written, 1 to 121 written by a read-write request, a range
  within the 65 536 addresses), checked before a connection is even opened;
- a bounded connect (`Timeouts::connect`) and a bounded answer (`Timeouts::response`), the
  connection closed on any answer not taken, as core's OPC worker ends a session whose call
  failed (C-022): no late answer is ever read as another request's;
- a write's outcome said as the plant may have seen it, as core's OPC writes say it (C-022):
  `Refused` and `NotConnected` never left, `Exception` is the device's no, `Unconfirmed` may have
  landed.

The client sits behind core's feature `modbus`, off by default. Without it, the first run of the
whole suite with the client turned supervisão's `the_plant_s_stack_reaches_supervisao_through_portal_alone`
red: that test pins supervisão's dependency graph, and `crc`, `crc-catalog` and `tokio-modbus` had
joined it through core. A component that only polls carries no fieldbus code; `cargo tree -p`
resolves features per package, so a feature switched on by the controller or a test crate does not
reach supervisão's graph.

The client is blocking, on a current-thread runtime of its own (a cyclic task calls it between
scans); a host name is not taken, only an address, so no lookup can hang a call.

## The peer the test drives

Core's tests cannot start the bench (L4). `tests/modbus_client.rs` runs a peer on loopback that
reads each request off the socket as bytes and answers with bytes: for the functions, the Modbus
Application Protocol specification's own example frames (V1.1b3), so the client is held to the
standard's bytes rather than to its own reading; for the failures, silence, a close, an answer
cut short, an answer too late, and thirteen answers that do not answer their request. A full
listen queue (backlog 0, filled) makes a connect hang without any network setup, so the connect
bound is measured on loopback.

## The bench (2026-11-22)

The whole device is the bench's Modbus server (maquinar, C-110), its frames maquinar's own code,
met from `tools/mestres`, a test-only tool crate that depends on core (feature `modbus`) and
maquinar (Q101, option taken). `tests/modbus.rs` reads what the plant side set and checks what
the plant side holds after each write; reads the server's own record of each request against the
specification's bytes (two implementations agreeing on the wire, neither the other's copy);
meets the device's exceptions (an address past a table, a unit not played); and turns its knobs.
A slow device applies a write before its late answer and a silent one never applies it: the client
calls both `Unconfirmed`, and the plant side shows why the word is "may have landed". A restart
(every connection dropped) ends the call with a broken link and the next connects again.
