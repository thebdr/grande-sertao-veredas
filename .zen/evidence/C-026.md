# C-026 evidence - the OPC UA server

## The port (2026-11-06)

From Veredas 1's `crates/veredas-maquinar/src/opcsim.rs` and `tests/opcsim.rs`, now `src/opc.rs`
and `tests/opc_server.rs`. The threading is core's `DetachedPlant`'s (a thread, a current-thread
runtime, std channels drained on a 20 ms tick, the runtime's drop as the teardown), the server
setup core's demo plant's (bind first, advertise the bound port, the namespace apart from the
application uri, `has_type_definition` on every variable).

Changed:
- `OpcConfig` reads from TOML (`deny_unknown_fields` on every table; `type` and `access` as
  words; `randomize` an optional table; `user` an optional table whose password is hidden in
  `Debug`; `max_nodes_per_read` and `max_sessions` as the knobs core's demo had);
- the vendor command handshake Veredas 1 hard-coded (a tag whose id ended in a product's
  trigger name written 100, answered 99 then 1 after 300 ms) is a configured **reaction**:
  `on_write`, an optional `equals`, an optional target `tag`, and `then` steps at `after_ms`
  from the trigger. Detection is by polling the watched tag each tick, edge-triggered (the
  stack calls a write callback instead of storing the value, under the address-space lock, so a
  callback could neither store the value nor be told apart from a plant-side set);
- errors typed (`OpcError`: a configuration refused with its place named, the bind with its
  address, and the startup failures core's demo names); a value that does not parse is refused
  at validation, not read as the type's zero (the file is the operator's, not a live field);
- `get` and `snapshot` answer within 5 s or not at all; a `status` counts draws and reactions;
- a `relay()` on the handle: core's `Relay` in front of a server bound on `127.0.0.1`;
- no fixed credentials: a user is configured or there is none.

The test drives the server with the raw client (as Veredas 1's did) and, once, through core's
own poll worker: the consumer's whole client path (connect, poll, gated write, the bench
vanishing) against the bench, which is the point of the bench.

## Refute round 1 (2026-11-06): refuted

- **An empty or inverted range was accepted** (core's draws swap reversed bounds quietly), and
  **int draws truncated fractional bounds** (`3.5..=5.5` drew 3) and clamped a range outside an
  int to its extreme. Now `low > high` is refused for every type; an int range is the whole
  numbers from the ceiling of `low` to the floor of `high`, refused when it holds none or
  reaches outside an int; pinned with draws over `3.5..=5.5` (4 and 5 only) and at the bottom of
  an int.
- **What a change is** was wider in the clause than in the code: the code hides every change
  made in a tick by a draw or by any reaction's step. That is the intent (a drawn watched tag
  would fire every tick; a chain of reactions is the plant's own doing, not a write), so the
  clause now says it and a test pins a drawn watched tag firing nothing and a chain stopping at
  the first reaction, the second firing on a plant-side set.

Held: a step that sets the watched tag does not refire it; a tag id with surrounding spaces;
the port free after a drop; the relay, the caps, the credentials, write-only and the TOML
defaults at the exact values the clause states.

## Refute round 2 (2026-11-06): refuted

A client can write any scalar into any typed tag: the stack's `validate_value_to_write` answers
Good for a scalar of another type (its own code returns Ok for every scalar mismatch; only
arrays and byte strings are refused), stores it, and `get` then returns an Int32 in a float tag,
a String in an int. A write callback cannot store a good value (the stack calls it instead of
writing, under the address-space lock), so the bench polices the type itself: every tick, a
tag holding a value of another type gets its last value of its own type back, the mismatch is
counted and named in the status, and the stray value is never compared by a reaction; a
plant-side `set` of the wrong type is counted and dropped. The clause says the stack answers
Good and what the bench does about it. Pinned on five wrong writes and a wrong set. Held: a
re-trigger while steps are pending fires a second sequence, stop closes an open session within
a few ms (the next read fails `BadConnectionClosed`), `low == high`, decimals beyond 15.

## Refute round 3 (2026-11-06): refuted

The put-back ran after the tick had answered queued `get`/`snapshot` requests, so the server
side read the stray value first; a right write followed within a tick by a wrong one lost the
right one; and the per-tick read of every tag made the tick about 50 ms at 4 000 tags. All three
go with one change: a write callback on every writable tag. The callback checks the wire type
and answers `BadTypeMismatch` (a ranged write `BadIndexRangeInvalid`), as a real controller
does; a right value it hands to a task on the server's runtime that lands it the moment the
address-space lock is free (the callback runs under that lock and cannot store it itself),
before the client's next request can arrive. Nothing wrong is ever stored, nothing is scanned
per tick, and the tick is an interval that keeps its period. The server-side read after a wrong
write is pinned plainly, with no waiting.

## Refute round 4 (2026-11-06): refuted, on the draw's clock

The round-3 findings held: 500 writes then reads on one session, none stale; two writes to one
tag in one call in order; a right and a wrong value in one call answered apart; a write-only tag
written and seen; the tick no longer slowed by the tag count (98 draws in 3 s at 0 and at 4 000
tags). The gap was the next due time, set from the tick's clock: a little past the tick, so just
past the next boundary too, and every interval stretched by a tick (a 20 ms tag drew 163 times
in 5 s, not 250; a 50 ms one 80, not 100). The next draw is now due an interval after the last
was due; a stall skips what it missed and keeps the phase. Pinned on a 100 ms tag drawing 19 to
21 times in 2 s and a 20 ms tag on every tick. Not promised, so not counted: a read pipelined
with a write in flight at the same time, a draw landing between a write and its read, the
source timestamp replaced by the server's.
The 20 ms tag then drew 63 times in 2 s here where it should draw 100: the tick itself lands at
the host's timer quantum (15.6 ms on Windows: a 20 ms wait ends about 31 ms later; the 50 and
100 ms gaps the critic measured, 62.8 and 125.8, are quanta too). The clause states it, the
rate pin holds on both platforms, the per-tick pin is per platform, and whether to raise the
resolution is the operator's (`docs/questions.md` Q13).

## Refute round 5 (2026-11-06): refuted on the last word

The schedule held for every interval of a tick or more (a 40 ms tag 101 draws in 4 s, 50 ms 81,
100 ms 41; the 100 ms pin robust to a late tick and a late status; the phase kept after a
stall; the reaction windows inside their bounds under the quantum). Below the tick a tag drew
once a tick and the draws between were dropped, while the clause said the tick adds nothing to
the interval. Now an interval below the 20 ms tick is refused by name when the configuration is
checked, and the clause says at most one draw comes per tick and what a host whose quantum is
longer than the tick does with an interval below the quantum. Pinned on 19 refused, 20 accepted.

## Refute round 6 (2026-11-06): holds

The sub-tick refusal reaches the TOML path (the checks run in `compile`, under `start` and
`validate` alike); 20 and 25 ms on Windows draw once a quantum as stated, 32 ms and up at the
configured rate within one draw; an interval that is not a multiple of the tick is served at
the first tick after each due, nothing skipped, the rate exact with jitter only. Every earlier
finding closed.

## Found by CI (2026-11-09): a draw read before it was drawn

The randomized-tags test read the float tag right after connecting, and on the Linux runner
(twice: 120c77d and 680553d) read the configured initial value, 0, before the first draw was due
30 ms after the start, so "0 escaped the range". The reference says the initial value holds until
the first draw; the test now waits for the three randomized tags' first draws (the status's
count) before it reads, and asserts the range from there. A test that reads what a clock moves
waits for the move it asserts (the portal session's trap list says the same of its snapshots).

## Q13 decided (2026-11-09): the bench holds the host's timer at a millisecond

The operator decided the bench raises the Windows timer resolution while it runs, so the tick
is 20 ms on both platforms. `timer::FineTimer` is the guard (`timeBeginPeriod(1)` on hold,
`timeEndPeriod(1)` on drop), held by the executable for its run and by the OPC server's and
each channel's thread for theirs, so the tests' processes tick fine too. A probe on this
Windows 11 host measured a 20 ms tokio tick at 30.9 ms bare, 29.9 ms with the request alone
(Windows 11 ignores it from a process without a foreground window), 20.0 ms with the request
and the process opted out of power throttling's timer coarsening (`SetProcessInformation`,
`PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION`), 32.2 ms with the opt-out alone; a plain
`std::thread::sleep(20 ms)` already landed at 20.4 ms in every case (Rust's sleep uses a
high-resolution waitable timer). The guard does both calls. The 20 ms tag's floor is 90 draws
in 2 s on every platform now (55 on Windows before), the two tick loops' pending notes are gone,
and the clause and the bench plan state one figure. The run was re-recorded after the change.

## Found by CI (2026-11-09, afternoon): the 20 ms floor under a loaded runner

The run for c9f39cc (records only; the run before it, holding the Q13 change, was green on the
same test) drew 81 times in 2 s on the shared Linux runner, under the floor of 90. The cause is
the host, not the timer: the tick is `tokio::time::interval(TICK)` with
`MissedTickBehavior::Delay`, so a wake-up a few milliseconds late lengthens that period and
the count falls with the load; `cargo test --workspace`, which CI runs, does not read the
nextest override that gives the test the machine to itself. The floor is 70 now, a bound
against the quantum and not a pace (a 31 ms tick gives 64 draws; two draws a tick would give
103, so the ceiling of 102 stands), stated in the assertion; the 100 ms tag keeps 19 to 21,
since a draw is due from its due time and a late tick costs it nothing. The claim did not
move: the tick is held at 20 ms on every platform; what moved is what a loaded host may do to
the wake-up. The run was re-recorded after the change.

## The ramp, for supervisão's layout (2026-11-09)

Supervisão's layout shows plant motion (parcels along a loop, outlets filling: the design's
layout overview), and its fixtures come from the bench first (CLAUDE.md, "fixture first"). A draw
jumps; a place along a loop must step. The OPC server's tag grew a `ramp` beside its `randomize`:
an int or a float stepping by `step` on an interval, scheduled exactly as a draw is (due an
interval after the last was due, a stall skipping the steps it missed), from what the tag holds,
wrapped by the range's width while past `high` (so a level reaches 100 and shows it, then
empties), rounded to its places, a value outside the range starting again at `low`; never on the
same tag as a draw. Stepping from what the tag holds lets a client's write or a plant-side set move
the ramp on, as supervisão's demo plant needs for its gated "release" write (a reaction setting the
level to 0, the ramp filling it again from there). The status counts steps apart from draws, so
the draw tests' counts are untouched. The bench file's reference (`docs/bench-schema.md`) gained
"A ramp" and the tag's key, held by `tests/bench_file.rs`'s copy and key walk (C-033's file).

## The ramp's refute round 1 (2026-11-10, at 8db48d9): refuted, two defects and seven gaps

Two defects in the code. With places, the wrap compared the unrounded float sum with the high:
0..=0.3 by 0.1 at one place went 0.1, 0.2, 0.0 (0.2 + 0.1 is past 0.3 by its last bit), never
showing its high and stepping back; 424 of 5050 (high, step) pairs at one place left the exact ramp.
And places, steps and ranges that do not fit were accepted: a step of 0.04 at one place never
moved, 0..=2.5 by 0.5 at no places emitted 3, a low off its places restarted off them, and a width
past what a float holds turned into NaN. Seven test gaps, each a mutation left green: the due time
taken from the tick (two 100 ms ramps at 30..=42 in 2 s admitted it), the ramp stepping from its
own last value rather than what the tag holds (only a plant-side set was tried), a restart that
never showed the low, a ramp step counted as a change, draws counted as steps, int ramps stepping
twice, and the infinite low and int-range checks.

The answers. With places, `ramp_next` counts in whole units of the last place (the value, the
range and the step rounded to them), so the ramp reaches its high and never steps back; validation
refuses by name a width past what a float holds, a low, high or step that is not a whole number of
the places, and one too large to count exactly at them. The tests pin 0..=0.3 by 0.1, a value
between places, and every high and step at one place from 0.1 to 10 (from 0 and from -1) against
the same ramp counted in whole tenths; read every step of the int ramp server-side, each exactly
the next; move the ramp on from a client's write (55 then 85), a plant-side set (25 then 55) and a
reaction's step (7 then 10), each timed just after a step so the value is read before the next;
restart at exactly the low after 250; keep a reaction watching the ramped tag silent; count a
100 ms ramp and a 100 ms draw apart (19..=21 each) and a 20 ms ramp at 70..=102, the draws' bounds;
and refuse the new texts. The critic's M1 to M7 were replayed against the new tests: all red.

Not claimed (argued from reading, left as the draws' round 4 left it): a set or a reaction's step
landing in the tick the ramp is due is stepped from in that tick, so a client may never read it.
