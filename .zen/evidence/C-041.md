# C-041 evidence - the session store

## The design (2026-11-07)

Veredas 1's `veredas-store` (`DuckStore`, its schema types, its errors, its CSV helpers) as it
was, in one module behind the `store` feature, with two changes. The `SeriesStore` trait is
gone: it was the seam for a second store that never came, and a trait with one implementation
is a surface to keep for nothing; the narrow methods are the store's own. The column type is
core's `SeriesType`, which core gives every protocol's rule, so a base table is shaped by any
rule without a mapping (Veredas 1 kept `GroupType` beside it and mapped at the session).

"Every protocol's data stored alike" is what the test's third case pins: a capture rule's
series, an OPC rule's columns (through the gateway's own `opc::compile` and `table_of`) and a
telegram message's table (through `MessageTable::of`) make three `BaseTableSpec`s the store
opens together, and their rows read back through one surface, listed, windowed, paged and
charted the same way. The session (phase 5) will feed the store exactly this way, from the
bench.

The CSV helpers stay: a reference table the operator keeps beside the plant (sensor labels,
limits) is read live through a view, which is the store's business, not a shell's; a shell's
concern (Veredas 1's SQL builder, templates, recents) is Q14's.

## Q17 decided (2026-11-09): the padded reader for any ragged file

The architect decided the padded reader takes any linked CSV the sniffer reads ragged, the
sniffer staying the first reader of a regular file. Raggedness is read off the file itself: the
first 2 048 lines counted in the sniffer's own delimiter (`sniff_csv`), quotes honoured, a blank
last line no row; unequal widths force `read_csv` with that delimiter and `null_padding`, where
only a file collapsed to one column was forced before. The engine's behaviour on the padded path
is C-042's to pin (a long row widens within the window, refuses by its line past it); the store's
choice is this clause's. The test reads a short row and a long row the sniffer would keep or
drop on its own terms with every row kept, leaves a regular file with a quoted delimiter and a
blank last line to the sniffer, and keeps a ragged row past the window out of the count. The run
was re-recorded after the change.

## A definition is one SELECT (2026-11-11, from C-054's seventh refute round)

C-054's critic found that `validate_definition` ran a definition's text: the pinned crate's
`prepare` runs every statement but the last, so `SELECT 1); COPY ... TO '<file>'; SELECT (1` wrote
a file through a validation documented as not running anything, and `CREATE VIEW ... AS (sql)` in
`execute_batch` did the same when the store opened. Every definition is now handed to the engine's
`query()` table function as a string, which parses it and refuses anything but one SELECT
("Expected a single SELECT statement"), at validation and when the views are applied; a sound
definition yields the same columns and types. The store test refuses four spellings of a second
statement (closing the parenthesis, after a `;`, inside dollar quotes, a COPY alone) at validation
and at open, checks the COPY's file was never written, and validates a `;` inside one SELECT's
string. The project reference and its test's copy now say a view's `sql` is one SELECT.
