# C-152 evidence - the controller's states

New in Veredas 2: Veredas 1 had no controller beside its demo host. Built on `docs/controlador-plan.md`
and core's state text (C-070); the readings the plan leaves are `docs/questions.md` Q228.

## Refute round 1 (2026-11-22): refuted, and two defects
Every mutant asked for was killed (the program starting or acknowledging, the switch skipped, a stop or
a start allowed in FAULT, default outputs in STOP, the program's clock handed to the plant, the old
program kept across a restart, a power-cycled start-up returned as STOP, each condition dropped, a crash
as STOP, the first scan a cycle late). Two probes showed the controller itself breaking the clause:
- **The exchange while no program runs repeated itself**: after an acknowledge at 10 ms of a fault that
  had exchanged at 0 and 10, and after a start and a stop at 20 ms, the next exchange ran again at the
  instant just served, because a stop or an acknowledge set the next exchange from the last cycle's end
  alone.
- **A stop between periods** (13 ms) made the next exchange run at 13 ms, off the target's periods.

The controller now places that exchange on the target's periods alone, at most once in each: the first
period not before the step and after the last exchange, the program's or its own. A stop right after a
scan at 10 ms therefore brings the safe outputs at 20 ms, not a second time at 10 (the first test said
"at once" and now says the next period).

Test gaps, each now pinned: a start refused in RUN; an acknowledge refused in STARTUP and in RUN; the
program stopping itself from RUN; a cold start refused from the program and with the switch off; refusals
compared against the whole state; `sim` and `no_realtime` each alone; a power-cycled start-up without real
time, and stepped to RUN with it; the watchdog's task name; a stop keeping the overruns; the exchange's
grid after a program that started off it. Wording: the clause said every refusal changes nothing, which
the real-time refusal does not; it now names the exception. Equivalent: removing the reset of `overruns`
at start-up (the first scan in the same cycle sets it).

## An interpreted program on the controller (2026-11-25)
The controller now runs a `TaskProgram` made by a `Source`: `Native<P>` makes a native program from its initial
values (the default type of `Controller<P>`, so every native use and test is as it was), and `Loaded<I, O>` makes an
interpreted one (C-155) from what its host hands in: the loaded program, its scan entry, its four regions' types, its
first state and its safe outputs (Q231, taken meanwhile). The source makes the program at power-on, the one whose
safe outputs apply while no program runs, once more there to check the task's configuration, and again at every
start, so every start runs it from its first state. Making is deterministic, so a program made at power-on is made
alike at a start; a program that cannot be made is refused when the controller comes up
(`PowerOnError::Program`, the adapter's reason), as a zero period is (`PowerOnError::Task`).

The fault: the engine's `Fault::Program` is mapped by the source. An interpreted program's own error,
`ScanError::Program`, is `FAULT program(at)`, 502, `at` the file and line its location names (`count.rs:2`, as the
plan writes a breakpoint's location); `ScanError::Host` and `ScanError::Outputs`, an image the machine refuses or
outputs read back as none, are the adapter's or the host's failures and the runtime's, `FAULT internal`, 507. A
native program's error is `Infallible`. The watchdog's fault is 501 for both.

How the tests stand (`tests/interpreted.rs`): a hand-lowered program that counts its scans from a first state of 40,
writing the count times a hundred plus its input divided by its divisor behind the division's assertion, beside its
native twin whose default is that count, 300 scans each with equal writes, exact; the divisor of zero on the sixth
scan giving `FAULT program(id=502, at="count.rs:2")`, the safe outputs handed in from that scan on, the exchange on
every period, an acknowledge and a warm start running it from its first state; an input image the machine refuses
and outputs that read back as none each giving `FAULT internal(id=507)`; the watchdog for the interpreted program;
the safe outputs while stopped; the refusals at power-on; a stop and a start running it again from its first state.
The program's location is in the second of its two files, so a fault names the file its location names. Four
mistakes tried by hand, each killed: the program's error as 507, the host's as 502, a stop keeping the program
where it stood, and the location always naming the first file.

The claim changed, so the clause returns to pending until its next refute round.

## The implications check (2026-11-25): a program that cannot be made, and which errors are the program's
The zen-implications check of the change found three contradictions and four omissions, each answered here:
- **A program that cannot be made refused the controller's coming up** (`PowerOnError`), leaving no state, no
  exchange and no FAULT, against the plan (an application that cannot be loaded is a FAULT reason, 506 `load`),
  Q36's ruling (a stored program failing its check at power-on is the FAULT 506, never a substitute) and its rule
  that a controller always comes up into a state. The program is now made at power-on as every load checks it,
  and one that cannot be made leaves the controller in `FAULT load(id=506, download=0)` whatever state it would
  come back to (a crash's `FAULT internal` first), exchanging the safe outputs, which the source now gives without
  making the program; a start's load that fails is the same 506, no longer 507. The adapter's reason is kept for the
  host (`Controller::load_error`). `download` is 0 while there are no downloads (Q233, new, taken meanwhile). Only
  the engine's check of the configuration still refuses the coming up, through `TaskConfig::check`, the engine's
  own rule, which a host can now ask before it has a program.
- **Which program errors are 502**: every `ScanError::Program` was 502, the machine's `Internal` and `Uninit`
  among them, against the clause's own "where Rust would panic" and the plan's 507, "the runtime's own failure".
  Now a failed check and an index past the end are 502; code marked unreachable reached, a value read before
  anything wrote it and an inconsistency the load should have refused, none of which safe Rust reaches, are 507,
  as the adapter's and the host's failures are. `docs/orcl/interpreter.md`, which had unreachable code as 502,
  says so. The mapping was written in C-152 and C-155 both; C-155 now points to C-152 for it.
- **What `at` names**: the interpreter's design names a file, a line and a column for a fault 502; `at` now carries
  the column (`count.rs:2:5`), as Rust's own panic message names a location. The plan's only example of a location
  is a breakpoint's, which is a line.
- Omissions: C-151's "every program controlador runs today" is now "every native program", in its Verification and
  `tests/model.rs`; Q231 names the controller's `Loaded`; C-152's Source cites the plan's "Execution", the
  interpreter's "Running", Q36, Q231 and Q233; and its model is stated as one of the states over a native program,
  the interpreted source covered by `tests/interpreted.rs`.

How the tests stand: the load test now asserts the 506 at power-on with the reason kept and the safe outputs
exchanged, a start's load failing again, the power cycles from RUN and STOP, the crash's 507 first, and a zero
period still refused; a new test runs a program that reads a value before writing it and one that reaches
unreachable code, each `FAULT internal(id=507)`. Three mistakes tried by hand, each killed: unreachable and uninit
as 502, only a first power-on checking the program, and a start's failed load as 507.
