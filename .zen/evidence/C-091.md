# C-091 evidence - recording to the drive

## The ruling and what is built (2026-11-22)

`docs/robustness.md`, "The store of a controller's embedded portal": the window in memory is the
default, and "the project can turn on recording to the drive, in files with a size limit" (given
with the ruling of 2026-11-19 and not objected to). Built: `record = { dir, max_mb, every_s }` in
the project, `SessionConfig::recording` in process.

## Decisions

- **A record is a second store on the drive.** The same tables and views as the session's store,
  opened with `DuckStore::open` on `Residency::Disk` (C-041's guard against a database already
  standing there holds for it), so a record is a database any tool reads, as a snapshot is. Its
  engine's memory ceiling is 64 MiB (`RECORD_MEMORY_MB`): it takes appends only, and the engine's
  default (a share of the machine's memory) is not one a controller should leave (Q41).
- **Written seldom.** The pump hands every row it stores to the recorder, which keeps them in
  memory and writes them in one batch every `every_s` seconds (10 by default) and at the stop: the
  arithmetic of wear in `docs/robustness.md` is per write, so a poll every 50 ms costs one write
  every ten seconds, not twenty a second.
- **At the limit the recording stops** (`// DECISION PENDING`, Q41, open: the oldest deleted, or
  recording stopping with a maintenance request). Stopping is the reversible answer and the one Q16
  decided for a project's disk store ("nothing is refused, deleted or merged"). The size is the
  database and its write-ahead log after a write, so a record passes its limit by at most one
  batch; the rows after are counted unrecorded. The maintenance request itself is controlador's to
  raise (its state, C-070); portal publishes why the recording stopped.
- **A write that fails stops it the same way**, with the engine's text (Q41's proposal "a full or
  failed data area never stops RUN": the session goes on). No drive fault is provoked (the record's
  file is held open by the engine, and no folder or file mode stops an open handle); a recorder
  whose record lacks a table fails its write instead (round 4, below).
- **Names.** `recording`, `write_every`, `limit_bytes`: supervisão's sources name `every` and its
  policy test refuses a public name of portal it also holds.

## Refute round 1 (2026-11-22, at b3380d9): refuted, four gaps

The critic held that the recorder keeps its own copies of the rows (the window never lets one go
before it is written), that nothing is written after the limit stops it, that the three file names
never collide, and the refusal of a record already there. It found:
1. **"Written seldom" unasserted**: a recorder writing on every 50 ms pass passed. A test now samples
   the rows recorded every 20 ms for six seconds against the plant: two to four changes, never two
   within 1.8 s, at one write every two seconds.
2. **"At a write" unasserted**: the limit test's first write carried all 20 000 rows to five times
   the limit, so a recorder stopping only at five times passed. A test now writes 500 lines at a
   time: several sizes under the limit, every one before the stop under it, the one at the stop at
   or past it.
3. **The size on the drive**: the engine's close folds the log into the file in blocks, and a
   record of 300 rows stood at 536 576 bytes against a 204 800-byte limit, its published size 28 451.
   The stop's last pass now folds the log in (a checkpoint) and publishes the size the drive holds;
   the clause says a closed record may stand above what its last write measured, and the test checks
   the published size equals the files on the drive.
4. **A failed write**: no test provokes one (the engine holds the file open), and the loop went on to
   the later tables after one failed. The loop now stops at the first failure; the clause no longer
   claims what no test shows.

## Refute round 2 (2026-11-22, at 5ff9097): refuted, two gaps in the test

1. **The write period had no upper bound**: a record written every 3 s for a setting of 2 passed
   (two to four writes in six seconds, a minimum gap alone). The test now looks until four writes
   and holds every gap to 1.8 to 2.6 s.
2. **The snapshot's size and unrecorded rows were never read**: after a stop at the limit the
   snapshot's `recording` is now asserted equal, field for field, to the session's status, its
   reason exact.

## The implications check (2026-11-22)

The gate flagged C-091 as a near-duplicate of C-043. The check found two distinct capabilities:
C-043 pumps rows into the store; C-091 is a second sink the pump hands the rows it stored. C-091
now names C-043, a store on the drive, C-041's snapshot and C-093's copy (6c7dbbe). It also found:
- **A record beside a store on the drive** was accepted, every row reaching the drive twice, a
  limited copy of an unlimited store; Veredas 1 offered its auto-export for a store in memory
  alone. Refused now by name before anything opens, in the project file and in the session, as a
  window on disk is; the record's file is asked before the store opens.
- **The size counted rests on the engine's log**: `<file>.wal` beside the file, folded in by
  `CHECKPOINT`, the file growing in blocks. C-042 pins it now.
- **"A file any tool reads"** holds once the session has stopped: the record stays open in the
  session's engine for the run.
- **The import's note on Veredas 1's auto-export** said "not on a timer", no longer true of the
  suite: it names `record` as the nearest form, which needs a size limit Veredas 1 never set.
- Q41's "taken meanwhile" and P-017's "built under P-019" are suite files, sent to the orchestrator.

Mutants, each red now: the write period 1.5 times the setting, the snapshot without its size, a
record beside a store on disk accepted by the session, and by the project file.

## Refute round 3 (2026-11-23, at e487a86): refuted, one gap

"The drive is written seldom" was measured on the status the session publishes, set by the same
pass that decides to write: a recorder writing on every pass and publishing every two seconds
passed (about 200 writes between two published changes). The test now watches the drive itself,
the record's file and its log (sizes and modification times) at every look: they change as often
as the status does (one fewer when the first look met a write midway) and as far apart, 1.8 to
2.6 s, never between two writes. C-090 and C-093 held the same round.

The critic's mutant, the record written on every pass and its status published every two seconds,
is red now: the drive changed 134 times for four published writes.

## Red beside the whole suite (2026-11-23, the orchestrator's run at a2aa921)

With 1 386 tests running beside it, the period test saw the fourth write on the drive as two
changes 20 ms apart, the first 20 ms before the write was published. The cause was the record,
not only the watcher: a batch appended every table's rows with an appender and a commit of its
own, so one batch reached the drive as several commits a few milliseconds apart, and a loaded
machine let a look fall between two. Once a period held; "in one batch" did not, on the drive.
A batch is now one transaction for every table (`DuckStore::append_wide_together`, the crate's
own): it lands whole or not at all, a failure rolling every table back, which a unit test pins
(a second table refused, the first table's rows gone with it). The watcher judges writes, not
every step a file's size or time takes: steps closer than 300 ms are one write, each done within
500 ms, as many as the published writes and 1.8 to 2.6 s apart. The write-through mutant is still
red (one write spanning the whole look for four published).

## Settled beside a load (2026-11-23)

The orchestrator's second red run (at 50a9fc7) came before the fix above landed (55dda4a). To
settle whether one batch reaches the drive in two steps or the watcher sees one write twice, the
period test was run beside a load (14 busy cores and two writers fsyncing 1 MB files, under the
suite lock), printing every change of the record's file and log with their sizes:
- With each table's own commit (the code before the fix): 3 of 16 batches showed on the drive
  as two steps 20 ms apart, the log growing in two increments (6 440 then 8 812 bytes; 20 049
  then 20 968; 12 278 then 14 717): two commits of one batch. The record touched the drive twice.
- With one transaction (the fix): 1 of 136 batches showed two steps, the other 135 one. A single
  commit can still reach the drive in more than one write; the test counts steps closer than
  300 ms as one write, each done within 500 ms. All 34 runs passed.

## Refute round 4 (2026-11-23, at 051d8b7f): refuted, two gaps of one cause

No test reached the recorder's own write: the batch's one transaction was proven on the store's
method alone, and no test made a recorder's write fail (the note above said none could, the engine
holding the file open). The critic found a failure needs no drive fault: a recorder whose second
table its record lacks fails at once. A test inside the crate now drives a recorder so: the
failed batch lands nothing of either table (the first table's rows rolled back with the second's),
counts its three rows unrecorded and stops the recording with its reason, and a row after it is
counted and never written. The critic's two mutants are red: each table its own commit (the code
before 55dda4a; the record held half a batch counted unrecorded) and a failed write counted as
recorded.

## Refute round 5 (2026-11-23, at a9610429): refuted, the record's rows counted, never read

Every assertion on the record compared counts: a recorder writing each flush's first row as many
times as the flush held, the right number of wrong rows, passed all of them. The tests read the
rows back now: the window's record holds every poll once, and the polls the window still holds are
the record's own, field for field (stamp, arrival, speed); the limit's record holds exactly the
log's first lines, each once, their temperatures exact (count, first and last seq, minimum,
maximum, sum); the recorder's good batch holds the very rows and values it took. Two mutants, each
red in all three: each flush's first row repeated, and the rows kept with their values lost.

## Refute round 6 (2026-11-23, at 854c0df6): refuted, the rollback never shown

The recorder's test read "nothing of the failed batch landed" through the store's query
connection, while the batch's transaction lives on the writer's: a transaction left open there is
invisible to that reader, so a recorder that never rolled back passed. Left open, it stops the
stop's fold ("Cannot CHECKPOINT: the current transaction has transaction local changes"), the
size the stop publishes is no longer the drive's, and the write's reason hides the fold's. The
test now does what the stop does after the failed batch: the record's log folds, the size
measured then is the drive's once the record is closed, and a connection of its own reads the
file holding the good batch alone. The mutant, the rollback removed, is red at the fold. Kept: a
fold that fails after a write already stopped the recording leaves the write's reason the one
published; with the rollback proven, the failed write itself no longer makes the fold fail.

## Refute round 7 (2026-11-23, at 00e4091e): refuted, two promises of the stop untested

No defect: both held, and a mutant breaking each kept every test green.
1. **The size and the fold at a normal stop**: only a recording its limit had already stopped
   compared the published size with the drive, and there the stop writes nothing, so a fold
   before the last write passed (427 799 bytes published, 536 576 on the drive). A record written
   every minute, so the stop's batch is the only one: all 3 000 rows written at the stop, the size
   published the drive's, the log folded.
2. **The record let go at the stop**: every read after the stop was an open in the test's own
   process, which a file lock held by that same process never refuses (and closing such an open
   drops the session's lock), so a record never closed passed. Another process, this test binary
   run again with the record's path, is refused the record while the session runs and opens it
   after the stop, counting every row.

Two mutants, each red: the fold before the last write, the record never let go.
