# C-029 evidence - the bench channel

## The design (2026-11-06)

A bench channel is core's channel (C-012) with a catalog (C-028) on top: the framing, the
sequence, the keep-alive and the link rules are the channel file's, and the bench adds nothing to
the wire a consumer could tell apart. A message is a name; the catalog says what id the frame
carries and how its body is written and read, and the channel puts the id where the catalog's
`id_field` names (a segment header field, or the envelope's in a layout without segments), which
is checked before anything binds.

The service loop waits at most a tick (20 ms) for a wire event, then handles requests from
outside (`send_now`, the controller's knobs), ticks the controller and the channel's own cyclic
messages, sends what is due, and mirrors the status; a knob is answered only after that mirror,
so a caller reading the status right after the call sees what it set. Every due time is
scheduled from the last due time, never from the tick, so the host's timer quantum (about 31 ms
on Windows, `docs/questions.md` Q13) does not stretch an interval.

The monitor keeps the newest 100 lines: what came and went by name with its fields, its body's
preview and its peer; connections and disconnections; what could not be built or decoded, and
why. The counts are by name on the bench's side and core's own on the wire's.

The test runs a listener and a dialer over real loopback sockets with the channel schema's worked
file and the controller schema's worked catalog, and a second pair whose catalogs disagree (an id
one lacks, a length the other reads differently), so the unknown and undecodable counts are
earned on the wire; the refusals at start, a taken port and a peer never there are pinned by
their text.

## Refute round 1 (2026-11-06): refuted

An unknown message was a note but set no last error (the test read the error after two heartbeat
failures and saw theirs); the `id_field` check asked only whether the field existed, so a
catalog naming the segment header's length field started and the wire carried the body length
as the id (the receiver logged unknown ids); the layout without segments and the 100-line cap
were unpinned (the code was right on both). Now an unknown message sets the last error, a
field the channel fills itself (the sequence, a length, a count) is refused with its role, the
three refusals are read one by one, a segmentless pair converses with the id in the envelope
and its two refusals are pinned by text, and 130 notes leave the newest 100, newest first.
Held: two messages in one frame, drop freeing the port, no knob waiting across a drop, core's
state words, the keep-alive and the sequence core's own.

## Refute round 2 (2026-11-07): refuted on one point

The round-1 fixes held, and the six questions asked (an envelope id with a default, an id field
not first, a tail field, the error never cleared, the cap's pin under a cyclic line a hundred
times faster, one stamp per pass). One gap: the id field's width was never checked, so a
catalog with an id of 300 over a one-byte field started, the message was counted as sent and
the framing refused the frame with nothing but core's wire error to show for it; a body over
the frame limit took the same path. Now every id must fit the field at start (the message, its
id and the width named) and a frame the framing refuses is a note and the last error before
anything is counted; pinned on the id and on a 70 000-character body, nothing reaching the peer.
Reconcile (2026-11-07): the id check, the frame's building and the ids' reading moved to core's
catalog (C-028, `check_framing`, `frame`, `messages_of`), the bench calling them; the clause
points at C-028, and a body that renders empty in a layout without segments is a note.
