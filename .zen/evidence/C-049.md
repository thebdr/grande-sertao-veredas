# C-049 evidence - the host

## The design (2026-11-09)

Q19 (the operator): supervisão starts the sessions. The host loads every project with portal's own
reader, starts every session through `Session::start`, and serves each session's portal router as
it is (`veredas_portal::serve::router`) nested at `/s/<name>/portal/`, so the page's tables,
series and writes are portal's routes and portal's answers, gate included; Veredas 1's
hand-rolled HTTP proxy is not carried. A project's own `[server]` address is not bound, and the
check's plan says so.

The address is bound before any session starts, so a port taken costs nothing; a session that does
not start stops the ones started before it and is named with portal's reason. Open event streams
never end on their own, so a stop aborts the server and the feeds and shuts the runtime down under
them, then stops the sessions (their workers first, as portal's stop does).

Several sessions side by side (the plan's scope) are several projects on one host, each under its
own path, its data its own: the test runs two benches and sets a value on one, seen by its session
alone.

## Refute round 1 (2026-11-10, at 647df50): refuted, four gaps in the test, none in the code

The critic found the host behaving as claimed (each session's dashboards and object stream its
own, a stop with streams open ending every source in 191 ms) and four claims the test did not pin,
each shown by a mutation that stayed green: the bind moved after the sessions (the taken address
was tried on a file whose only session starts), the object stream route swapped for the snapshot
(the host test read `objects.json` alone), a silent exit 0 when the executable cannot start, and
announcing only the first session. The test now refuses the taken address on the file whose second
session cannot start (the address answered, never the session), opens both sessions' streams and
reads each one's own first snapshot, runs the executable on a held address (exit 2, the address on
stderr, nothing announced) and, freed, on the failing session (exit 2, the session named), and runs
it on the two-plant file (both sessions announced in the file's order).

## Refute round 2 (2026-11-10, at 77c6737): refuted, six gaps in the test, none in the code

The critic found the host right at every point and six claims the test did not pin, each shown by
a mutation that stayed green: every session's dashboard route served with the first session's
state; every feed after the first given the first feed's event channel (each stream opened with
its own snapshot, then carried loop's changes); a graceful-shutdown refactor that waits on open
streams (the stop never returned with a browser on the page); every session started before the
bind (a refused bind still created the first session's disk store); the executable stopping on
the first line of stdin; and `--check` starting the host before printing its plan.

The answers, all in the test: both object streams are held open while each plant changes, each
carrying its own change and never the other's; both dashboards read their own plant (the levels'
outlet 1 at 0.4 and 0.7); the stop runs with an object stream and portal's stream open, returns at
once and ends both; a file whose first session keeps a disk store is checked (`--check`, exit 0,
the plan printed) and refused on a held address, and the store is never created by either; the
executable gets a line on stdin and keeps serving, then is closed with a stream open and exits 0
at once, the stream ended. The six mutations, replayed from the critic's snippets, each turn the
test red (the shutdown one by hanging the stop).

## Refute round 3 (2026-11-10, at 1095ad8): refuted, one defect and two gaps

The defect: the executable read stdin as text, so a line that is not UTF-8 (a Latin-1 "não" from
a terminal or a pipe) ended the read as if stdin had closed, stopping every session with exit 0. It
reads bytes now: only the end of stdin closes (or a read failing other than by an interruption). The
gaps: the page's type was checked at `/` alone (the session paths served as text would have passed)
and `/s/hall` without its slash never asked; and "at once" was bounded at 10 s, so a bounded
6-second drain on stop passed. The test asks all four session paths for their status, type and body,
writes the Latin-1 line after the ASCII one, and bounds both stops with a stream open at 3 s (a
stop takes about a quarter of a second; blocking tasks get 2 s).

## Refute round 4 (2026-11-11, at 4ff742e): refuted, two gaps in the test, the host right

The executable's stop was checked only by what ending a process gives for free (exit 0, the stream
closed, the address free): an executable exiting without stopping its sessions (no last pump pass,
the OPC sessions dropped, the store never closed) stayed green. And `--check` on the two-session
file was checked only for the first session's name: a plan of the first session alone stayed green.

The answers, in the test: the executable's first session keeps its store on disk, and after the
exit the store must exist with no write-ahead log left (a stop closes the store; a process ended
without stopping its sessions leaves the log); the check's plan must name both sessions, loop then
hall, each with its path and title. Both mutants turn the test red (the log left behind; hall
missing from the plan).
