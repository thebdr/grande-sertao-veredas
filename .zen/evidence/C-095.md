# C-095: Portal to portal, the reading side

## What is built and what is not (2026-11-22)

The briefing has two portals speak portal's own HTTP interface (C-044): Oficina's portal reads the
one embedded in a controller through SSH's tunnel on the controller's loopback, and carries the
commands on the same link. Built here: the reading side, `peer::PeerClient`, over the interface
as it is, with nothing added to the server. Not built: the commands (Q37 rules how they are made
robust and which switch they pass); a peer as a source of the reader's own session, storing what
it reads (Oficina has not said what it keeps).

## Choices

- **HTTP/1.1 spoken by the reader itself over tokio**, not hyper's client. The first draft used
  hyper's client side, the hyper axum serves on, and it built: then the reachable suite showed what
  turning a feature on in a shared crate costs. Every crate sharing hyper was built anew, the
  database engine's build script among them (a `--workspace` build compiled `libduckdb-sys`; the
  same tree without the change reused the seed's), and supervisão's graph without portal gained
  `try-lock` and `want`, which its review had not read. The reader needs one method, `GET`, on a
  connection closed after one answer: its head read line by line under a 64 KiB limit, its body
  framed by chunks (extensions and trailers read past), by its length, or by the connection's end,
  each case and each breakage tested against a peer the test plays.
- **A connection per call**, no pool: the link is a loopback through a tunnel, a call is a window
  or a page, and a dead connection reused would be one more failure to tell apart.
- **Bounded in time, size and silence.** A tunnel can die without a reset reaching either end, so
  every call has a timeout (ten seconds by default), every answer a limit (32 MiB, far above a
  page or a window), and the stream a silence (15 seconds, three of the server's five-second
  keep-alive comments).
- **Typed where the reader acts, raw where it shows.** The snapshot's name, running flag, clocks,
  window, switch and sources are typed; its health, vitals, counters and recording stay as the peer
  writes them (`raw`), so a newer peer's added field reaches a screen without a new reader.
- **An event of an unknown kind is skipped**, the stream's own convention: a newer peer may add one.
- **A stream that ends stays ended.** Resuming is the reader's: a new stream's hello says where the
  peer is, and the gap is read again by window, which is what a lag event already asks.

## Refute round 1 (2026-11-23, at b5c62c4): refuted, one defect and nine bounds untested

1. **A value that is no finite number ended the stream**: the real portal serves `null` for a
   NaN or an infinity (JSON carries neither), and the reader typed every value `f64`, so a plant
   tag stuck at NaN, a common sensor fault, ended the stream and refused every window over it. A
   value, and a window's point, is `Option<f64>` now: none where no finite number was served, the
   stream going on, the window whole. A test drives a log carrying NaN and `inf` through the
   whole path, the capture, the store, the server and the reader.
2. **The 32 MiB limit** was proven for a declared length only: an answer in chunks and one running
   to the connection's end are refused past it too, asserted now.
3. **The 64 KiB head** was proven for one long line only: two 40 KiB headers are refused together.
4. **The defaults** were never used: a peer that never answers ends a call at ten seconds and a
   silent stream at fifteen, with the default client, while a real portal's idle stream, kept by
   its five-second comments, stays open past seventeen (a default silence under five seconds
   would kill every idle stream).
5. **The timeout's address**, 6. **`Connection: close`**, 7. **which clock is which** (each now
   against the key the peer named), 8. **a page's window**, 9. **the event limit** (a module test):
   asserted now.
10. **A missing key read as none**: a field the interface always writes, `null` for none, is now
   required as a key (`present`), so a snapshot missing `window_ms` is refused, not read as "no
   window".

Ten mutants, each red now: the critic's nine (the timeout naming no address, no
`Connection: close`, the running answer limit off, the running head limit off, a default silence
of 4 s, a default timeout of an hour, the two clocks swapped, the event limit off, a page's window
dropped) and a missing key read as none.

## Refute round 2 (2026-11-23, at 7b8b71aa): refuted, a defect and four answers untested

1. **A dropped call broke a healthy stream**: a chunk's data was read and then its line end
   waited for in the same call, and a half-read line lived in a local; a caller's timeout dropping
   the call there lost the data, and the next call read the line end as a size line and refused
   the peer by shape. Over SSH's tunnel, which splits frames anywhere, that window opens in
   practice. The reader is cancel-safe now: a line's bytes gather in the body's own buffer, a
   chunk's data is handed over before its line end is waited for (owed, and read by the next
   call), and the trailers' reading is kept as state. A test reads a stream through repeated
   300 ms timeouts while the peer holds a chunk's line end back and cuts the next size line in
   two: both events, in order, then the end.
2. **The stream's opening under its time** was untested (unbounded, all green): a peer that takes
   `/events` and never answers is a timeout of the time given, naming the address.
3. **A chart's key and window** were untested: a chart over a window gives its ten exact points,
   one by key its 13.
4. **The keys required** were tested for `window_ms` alone: a sample missing its value or its key,
   a listing missing `last_ms`, a catalog missing `rows`, a tag read missing `value`, each refused
   by the field's name.
5. **A refusal on the stream** was untested: a 503 on `/events` is the peer's `busy`.

Six mutants, each red: a line's bytes lost with a dropped call, a chunk's line end waited for in
the same call as its data, the stream's opening unbounded, a sample's missing value read as none,
a chart's key and window dropped, the stream's refusal not read as the peer's.

## Refute round 3 (2026-11-23, at 58d61b41): refuted, a defect and one answer untested

1. **The silence measured from each call**: every `next_event` built a fresh timeout, so a caller
   dropping its calls more often than the silence (a UI tick, a 300 ms timeout) never heard
   `Silent`, and a tunnel dead without a reset hung the stream for good. The stream keeps when it
   last gave a byte now, and every call waits until that moment and the silence: read through
   300 ms timeouts, a peer gone quiet is `Silent` about 800 ms after its last byte.
2. **The trailers kept as state** was untested (read in a local loop, all green): a chunked
   stream's trailers, their blank line held back across dropped calls, end it cleanly now in a
   test.
Also asserted: a snapshot missing `start_ms` refused by name.

Two mutants, each red: the silence measured per call again, the trailers read in a local loop.

## Refute round 4 (2026-11-23, at 25ddbcb0): refuted, four promises untested

No defect: each of the four held, and a mutant breaking it kept every test green.
1. **A call dropped inside a chunk's data**: every test wrote a chunk's data at once, so a reader
   taking a chunk whole within one call, its bytes lost when the call is dropped, passed. A data
   event cut in its chunk, its second half 700 ms later, read through 300 ms timeouts, comes whole.
2. **A chunked answer cut short**: only a length-framed one was tested. A window answer without
   its last chunk and one cut inside a chunk are each a broken link with its words, and a stream
   cut between chunks a broken link after its event, never a clean end.
3. **A body stalling after its head**: every timeout test's peer sent no head, so a time limit
   around the head alone passed. A head then nine bytes of a hundred, the link left open, is a
   timeout of 500 ms naming the address, under 3 s.
4. **The snapshot's clocks, window and switch** were asserted only at values a default gives
   (the switch off, no window). A snapshot with each a value of its own reads every one as served.

Four mutants, each red at its own part: a chunk read whole within one call, a chunked answer cut
short taken as its end, the time limit around the head alone, the snapshot's start, window and
switch defaulted.

## Refute round 5 (2026-11-23, at 4c7ee117): refuted, three promises untested

No defect: each held, and a mutant breaking it kept every test green.
1. **An event of another kind skipped on the stream**: asserted only on the decoder's return, so
   a stream ending at a newer peer's first unknown event passed. A stream carrying an unknown
   kind and an unnamed event between two data events gives both data events, then its end.
2. **A sample's key** was never read at a value: every fake peer sent no key. The real stream's
   five samples carry the line's item as their key, and a fake peer's `A1` reads as served.
3. **A chunk longer than its size line says**: every chunked peer sized its chunks right. Bytes
   after a chunk's data, before its line end, are refused by shape, never dropped into an answer.

Three mutants, each red: an unknown kind ending the stream, every key read as none, the chunk's
line end unchecked.

## Refute round 6 (2026-11-24, at db469f4f): refuted, a defect and two promises untested

1. **Values a unit off**: the reader parsed its answers with serde_json, which without its
   `float_roundtrip` feature rounds a decimal twice, so about one double in seven read a unit in
   the last place off (112 686 of 799 996 scaled readings and roots): the peer serving
   `1.4000000000000001` (14 × 0.1, a scaled plant reading) gave 1.4, a window's points and a
   stream's samples alike. The tests' values were all exact in binary. The feature is not the
   fix: serde_json is a build dependency of the database engine's crate, so turning it on
   rebuilds the engine in every build folder, the trap hyper's client was, and changes every
   member's reading. The reader reads its JSON itself now (`peer::json`, a reader into
   `serde_json::Value`, each number through Rust's correctly rounded parse, serde typing the
   value after), every answer and every event. A window and a stream of seventeen-digit values
   read to the last bit; in the module, a hundred thousand doubles of six kinds, the integers,
   `-0`, the escapes, the nesting limit and twenty-two texts that are no JSON.
2. **A caller busy past the silence on a living stream** was never tested: correct only because
   tokio's timeout polls its inner read before its deadline. A caller away 1.5 s past an 800 ms
   silence, the stream talking every 200 ms, reads its next event.
3. **A `+` in a query value**, which the peer's query reader takes for a space, was never tested
   encoded: a tag holding `+` and `%` goes as `%2B` and `%25`.

Mutants, each red: serde_json's reading back in place of the reader's (the seventeen-digit
values), `Silent` before the read once the deadline is past (the busy caller), `+` left
unencoded (the tag).
