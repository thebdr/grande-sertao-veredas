# C-115: `reflexo`'s first half

## What was built, and why so

- **Models step on the scene's thread.** A conveyor sets a belt's speed and a sensor model reads a
  scene sensor between two of the scene's steps, so a model and the bodies it moves share one
  clock and a run repeats; `fisica`'s runner takes hooks for this (C-114). Without a scene (drives
  alone) the models run every 4 ms on a thread of their own.
- **Points by name, through a view of the device.** The Modbus server and the EtherNet/IP adapter
  each give a view of their points (`ModbusPoints`, `EnipPoints`) that another thread holds: the
  same lock and image as the handle, so a model's write is what a client reads next. EtherCAT's
  process data has no named points; binding it by byte and bit waits for the second half.
- **Checked at load against the configurations**: a point's kind (bool or number) is the type its
  server would give it (a bit table or a bit is bool), so a bench file that loads has models that
  can bind.

## What the test taught

- **A ramp summed in floating point lands a step late.** 0.4 added 125 times is
  49.999999999999886, so the 126th step clamped to 50: a 0.5 s ramp took 0.504 s. Within a
  billionth of a step's change of its goal, the ramp lands on it; the test pins 50 exactly at the
  125th step, and the descent at the 62nd.
- **A u16 point rounds before the drive arrives**: 19.68 reads 20. The no-scene test waits for the
  drive's own speed, then for the point.
- **Sensor delays count model steps**: the model reads the scene's sensor as the last step left it,
  so a 10 ms on-delay at 4 ms steps switches at the third step that sees the body (12 ms), 20 ms
  off-delay at the fifth; pinned exactly.
- **The reference's key lists**: a bullet's keys must all sit on its first line for the bench-file
  test's reader; the conveyor's shared keys became three bullets.

## The end-to-end run

The reference's sixth example (docs/bench-schema.md) started through `Bench::start` with the
worked scene of docs/cena-schema.md beside it, driven by `tokio-modbus` as a controller would: the
conveyor reached its setpoint of 50 after its half-second ramp, the carton broke the normally
closed barrier (the input to 0) and cleared it, the pusher reached its end after its half-second
stroke; no model error in more than 500 steps.
