# C-010 evidence - the telegram wire codec

## The port (2026-11-05)

From Veredas 1's `crates/veredas-telegram/src/codec.rs` and its inline tests, now
`src/telegram/codec.rs` and `tests/telegram_codec.rs` (the tests see the public API only).

Changed:
- `EncodeError` and `DecodeError` derive `thiserror::Error` (Veredas 1: a hand-written `Display`
  on the first, none on the second); `EncodeError`'s text is Veredas 1's, `DecodeError` gains one.
- `parse_hex` returns `HexError` instead of a `String`, same text. Two bugs found on the way:
  `u8::from_str_radix` takes a leading `+`, so Veredas 1 read `"+F"` as `0x0F`; and it chunked
  the text by bytes, so a two-byte character passed the even-digit check and was judged as one
  "pair". Digits are now characters and must be ASCII hex digits.
- `if digits.len() % 2 != 0` became `!is_multiple_of(2)` (clippy, no behaviour change).

Tests added beyond Veredas 1's: golden frames byte for byte in both byte orders (a "wire
fixture" written from the layout table of §2.2-2.4, not from the encoder), the keep-alive's 16
bytes, the size limits at their exact edges (`u16::MAX` body: segment fits, data area does not;
the largest frame `MAX_FRAME` admits; one byte more), exact resync distances (no SOM, broken EOM,
a LENGTH past `MAX_FRAME`), hex signs and multi-byte characters, exact previews and dumps.

## Refute round 1 (2026-11-05)

Refuted: `decode` checked the lengths only once the whole declared frame had arrived. A header
whose LENGTH is corrupt but under `MAX_FRAME` (LENGTH 60 000, one segment of 2 bytes) answered
`NeedMore`, holding every real frame behind it until 60 KB more arrived; the realistic case is the
one the function's own doc names, a controller restarting mid-frame: the resync lands on a SOM
inside the broken frame's body, whose bytes read as a 61 440-byte frame. On a link carrying a
keep-alive every 10 s that is hours of silence. Fixed: the segment headers are walked as they
arrive, and the frame is refused as soon as they show the lengths cannot add up (NUM DATA headers
that cannot fit LENGTH, a body past the data area, segments still to come with no room, the last
segment stopping short). A valid frame passes every check, and every prefix of one still waits.
Also refuted: the wrong-byte-order test passed on `NeedMore` without reaching the path it names;
it now asserts the exact answers (`NeedMore` for one frame, `BadFrame { resync: 27 }` from the
second segment header on, before the 2 832 declared bytes). The `MAX_FRAME` doc claimed the
ceiling sat well under what LENGTH can say; it sits 15 bytes under, now stated.

Held: the layout against §2.2-2.4 field by field; 300 000 fuzzed buffers in both orders, no
panic, every `Ok` re-encoding byte for byte; every strict prefix of 3 000 random valid frames
waiting; the `MAX_FRAME` edge the same in encode and decode; hex refusing signs, multi-byte and
full-width digits.

## Refute round 2 (2026-11-05)

The new decoder held against a feasibility oracle on 262 966 header-boundary prefixes in both
orders (`NeedMore` exactly when a valid frame could still follow, else the exact resync), 4 000
random valid frames cut at every byte, the largest-segment-count frame, and 400 000 fuzzed buffers
(a refusal stays a refusal as bytes are added). Refuted on: the clause's "asks for more only
while what has arrived could still be valid" claimed more than the code checks (a half-arrived
LENGTH or segment header can already rule a frame out; the wait is at most 2 bytes and holds no
frame behind it), so the clause now names the envelope and whole segment headers; and the
remaining-headers check was pinned on its strict side only (a loosened copy passed every test).
Pinned on both sides: 3 bytes left for a header is refused, exactly 4 waits.

## Reshaped (2026-11-05): content-agnostic

After the operator's decision (`docs/questions.md` Q8) the module names no vendor and cites no
vendor document; the clause states the same capability in generic words. Its shape (start and
end bytes, the envelope, the sequence and keep-alive rules) is still one device's layout, fixed
in code: Q9 takes keeping it, pending a configuration schema.
