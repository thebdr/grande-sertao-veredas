# C-010 evidence - the telegram wire codec

## The port (2026-11-05)

From Veredas 1's `crates/veredas-telegram/src/codec.rs` and its inline tests, now
`src/telegram/codec.rs` and `tests/telegram_codec.rs` (the tests see the public API only).

Changed:
- `EncodeError` and `DecodeError` derive `thiserror::Error` (Veredas 1: a hand-written `Display`
  on the first, none on the second); `EncodeError`'s text is Veredas 1's, `DecodeError` gains one.
- `parse_hex` returns `HexError` instead of a `String`, same text. Two bugs found on the way:
  `u8::from_str_radix` takes a leading `+`, so Veredas 1 read `"+F"` as `0x0F`; and it chunked
  the text by bytes, so a two-byte character passed the even-digit check and was judged as one
  "pair". Digits are now characters and must be ASCII hex digits.
- `if digits.len() % 2 != 0` became `!is_multiple_of(2)` (clippy, no behaviour change).

Tests added beyond Veredas 1's: golden frames byte for byte in both byte orders (a "wire
fixture" written from the layout table of §2.2-2.4, not from the encoder), the keep-alive's 16
bytes, the size limits at their exact edges (`u16::MAX` body: segment fits, data area does not;
the largest frame `MAX_FRAME` admits; one byte more), exact resync distances (no SOM, broken EOM,
a LENGTH past `MAX_FRAME`), hex signs and multi-byte characters, exact previews and dumps.
