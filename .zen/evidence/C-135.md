# C-135 evidence - the cyclic frame

## The codec (2026-11-22)

New in Veredas 2: Veredas 1's aranha had nothing of the cyclic exchange. Written for core's IO
controller and maquinar's PROFINET device (`docs/aranha-plan.md`, phase 3), to core's rules (no
member, no vendor, typed errors, total on input), checked against tshark 4.6.6's PN-RT dissector.

What the dissector settled while writing it:
- **The frame id ranges**: RT class 3 0x0100 to 0x0FFF; 0x1000 to 0x7FFF reserved; RT class 1
  0x8000 to 0xBFFF; "RTC1 (legacy)" 0xC000 to 0xFBFF; the alarms at 0xFC01 and 0xFE01.
- **"Ignore" is bit 7 of the data status**, not bit 6 as first written from memory; bits 3 and 6
  are reserved. The test that compares each named bit with the dissector's caught it.
- The dissector left the IO data of frame id 0xBBFF undecoded, saying so at warning severity; the
  dissected frames use ids it reads whole. (The third critic's scan of all 65 536 ids found 0xBFFF
  and 0xFBFF the same: the last id of each range the dissector names.) (First written here as "when the data is not valid, and
  for ids at 0xBBxx": the second critic tried 0x8001 under seven statuses, invalid ones among them,
  and 0xBB00, 0xBB01 and 0xBC00, and only 0xBBFF warned. Corrected.) A real exchange is read by the dissector through the
  connection that set it up, which this frame alone does not carry.

## Refute round 1 (2026-11-22): refuted, four test gaps, the code right

- "Another tag" was never written (the fourth frame used the cyclic tag): priority 5, VLAN 100 now,
  to the byte, read back and dissected.
- The status byte's good and extension bits were pinned on two values: each bit alone now, and the
  reserved bits.
- The alarm ids were bounded on one side: 0xFC02, 0xFDFF, 0xFE00, 0xFE02 now.
- The dissector's data status bits were compared with literals over statuses that could not tell
  two swaps apart: six statuses that set each bit apart, each of the dissector's bits held to the
  codec's accessor.

## Refute round 2 (2026-11-22): refuted, the codec agreeing with the dissector everywhere

The critic held the codec to the dissector on all 65 536 frame ids (the cyclic set is exactly the
codec's) and on 20 000 differential frames (every APDU field and status bit equal). What the tests
let through, now pinned:
- **The Ethernet addresses' order was never checked**: `frame` writing them swapped passed. Every
  written frame's destination and source are asserted, by this codec and by tshark.
- **The status byte constants were checked by their good bit only**: 0x80 and 0x00 exactly now.
- **"The messages" covered one refusal**: both now.
- `FrameClass::Other`'s doc names the ids the dissector knows and this codec does not read as
  cyclic (the alarms with security, the remote service interface).

## Refute round 3 (2026-11-22): refuted, one test gap, the codec agreeing everywhere

The critic held the codec to the dissector on all 65 536 frame ids (a cycle counter read on
exactly the codec's cyclic set), on every data status and IOxS bit by the dissector's masks, and
on every count; retried the earlier rounds' attacks (all killed) and ran 32 mutants (25 killed,
the rest equivalent or outside the clause's words, but one). Answered:
- **Data of 0 bytes was refused on decoding only through a payload too short for the status**: a
  mutant reading a frame id and its status with nothing between them as a frame of no data passed.
  That payload is now refused by test, and the noise takes every length up to 1599 bytes (it took
  multiples of 8).
- **The drop-eligible bit was never set** (a mutant dropping it in `frame` passed, the envelope's
  own test pinning it below): the "another tag" frame carries it now.
- **The evidence named one id the dissector leaves undecoded; there are three** (above).

## Refute round 4 (2026-11-22): refuted, the codec right, acceptance never asserted

The critic held the codec to tshark on all 65 536 frame ids and 3000 random frames (every field and
named bit agreeing) and found every count right, but a decoder refusing what it should take passed:
the tests decoded only two ids and one status, and the noise only checked what did decode. Two
mutants survived (the legacy range refused; any status but 0x35 refused). The noise now asserts that
a payload decodes exactly when its id is a cyclic frame's and its data 40 to 1440 bytes, whatever its
status, and each frame tshark reads is read back by this codec as written. Both mutants are killed.

## Refute round 5 (2026-11-23): refuted, the codec right, tshark reading some frames as secured

The critic swept every one of the 65 536 frame ids, every data and transfer status byte on five
ids, and every length from 40 to 1440 on six edge ids, through `frame` and tshark: the classes,
lengths, statuses and bits agree everywhere but in one place, now stated and pinned:
- **tshark 4.6.6 reads PROFINET security** in cyclic frames: when the data's bytes 6 and 7 are the
  data's length less 20 (reserved bits 0x0800 and 0x8000 clear), it reads data bytes 0 to 7 as a
  security header and, authenticated (bit 0 of byte 0 clear), the status from data bytes n-16 on
  and the rest as a checksum; encrypted, no status at all; with no expert entry and no malformed
  mark. Measured here again in four ranges at both lengths, with the four neighbours reading plain.
  Random data meets it about once in 65 536 frames, which is why the earlier differentials missed
  it. A frame carries nothing else that says it is secured (the connection does), so the codec
  reads every frame plain, and the clause now says it reads frames without PROFINET security,
  a secured one read as plain; the writer writes the connection's data as given. Pinned: 48
  frames.
- **A VLAN id past a byte** was never written (a mutant keeping its low byte passed): VLAN 4094
  is written and read back. Killed.
