# C-137 evidence - PNIO over connectionless DCE/RPC

## The codec (2026-11-22)

New in Veredas 2: Veredas 1's aranha read no PNIO record. Written first for what aranha itself
needs (phase 6 reads a device's port data and I&M by the implicit read), to core's rules, so that
core's IO controller can build its connect, control, write and release on the same header,
arguments and blocks (P-018). Checked against tshark 4.6.6's DCE/RPC and PNIO dissectors on
hand-made datagrams (Ethernet, IPv4, UDP to port 34964) before the tests were written.

What the dissectors settled:
- **PNIO's argument counts follow the header's byte order**, not the blocks': a big-endian header
  with little-endian counts was read as an args length of 1 073 741 824. (First written here as
  "the PNIO status and every block are big-endian whatever the header says": the status is not; see
  the first refute round.)
- **The PNIO layer is named after the interface**: `pn_io_device` for the device interface, its
  fields `pn_io_pn_io_*`, and the status's `pn_rt_pn_io_*` (a record read's refusal under
  `..._error_code1_pniorw`).
- **The dissector pairs an answer with its request** (`dcerpc.request_in`) by activity and
  sequence; an answer alone gets a note at chat severity ("No request to this DCE/RPC call found"),
  under the warning level the tests hold complaints to.
- **The record after a read answer's header is dissected by its own block type**: I&M0 (0x0020)
  and the port's data (0x020F) were read field by field, the padding of the port data aligned to
  four bytes from the block's start. Those records are the next clause's.

Before the first commit, 24 mutants of `rpc.rs` were run against the tests: 23 killed, one
survivor (the PNIO object's test never varied the `8271` bytes of its prefix), killed by four near
UUIDs added to the test.

## Refute round 1 (2026-11-22): refuted, the status's byte order wrong, the rest unproven

The critic found the header layout, the packet types and flags, drep's bit, the counts' byte
order, both read headers' layouts, block reading, totality and the messages holding. Found, and
answered:
- **A response's PNIO status follows the header's byte order** (the defect): the dissector reads it
  as a 32-bit value in it, so under a little-endian header the codec's refusal `DE 80 B0 00` read as
  error code 0, decode 0xB0, with two warnings, and a device's refusal written in its order decoded
  with error code 0. Measured here again with tshark 4.6.6 before the fix: the reversed bytes read
  whole. The status is now written and read in the header's byte order; the only status the tests
  had sent little-endian was all zeros.
- **The answer's identity, the blocks' UUIDs, two hints, flags2 and the authentication protocol,
  and the additional values were never seen apart** (every test used the nil AR, API 0, slot 0,
  0xFFFF hints and zeros): mutants swapping or zeroing them passed. A read under an AR with API 5
  and slot 3, non-nil UUIDs at their bytes, and a datagram with every header field distinct are now
  written byte for byte and read by tshark.
- **The target AR is padding under an AR** (the dissector reads it only under the nil AR): a
  request naming both is refused, the place read only when zero; an implicit read under an AR is
  refused (the clause had said the helper writes the nil AR; the request it was handed decided).
- **A datagram past what UDP over IPv4 carries** (65 507 bytes) is refused both ways; the clause
  had said 65 535 of body, which a datagram cannot carry with its header.
- **The dissector's claim** now names the one complaint a written datagram draws: a record that is
  not its index's block. A count said five other UUIDs where six were tested (seven now).
Before this commit, the critic's surviving mutants and this round's points, 17 mutants, were run:
all killed.

## Refute round 2 (2026-11-22): refuted, the codec right, six mutants and one message

The critic found the first round's fixes holding (the status's byte order among them), every
count right, and these, now answered:
- **A block of length 1 with its header whole was never read**: a mutant panicking on it passed
  (the tails tried were cut short before the length was read), and no noise reached the block
  reader. Two such tails are kept now, and the noisy bodies run through the block reader, both
  read headers and `split`, each written back.
- **The answer's interface and operation were never seen apart** (every answer was a device
  interface's, its operation unchecked): a controller-interface request is answered on that
  interface, and the read's operation asserted, by tshark too.
- **Drep's bit 0 alone** was never tried: big-endian now; **the object UUID's first bytes** were
  never varied (five near UUIDs more, one per byte of each field); **the response's refusal
  message** is asserted.
- **`split` named a length the data did not have** for a header block of the wrong length: it now
  names the block and its length.
Before this commit, the six surviving mutants and the new message's, seven, were run: all killed.

## Refute round 3 (2026-11-23): refuted, the codec right, five places in the tests

The critic found the codec right (the second round's fixes holding, every count and message
right, no panic in wide noise) and five boundaries the tests never touched, each a mutant they let
through. Answered with pins, no change to the code:
- **A datagram that is its header alone** (a ping, a working, an acknowledgement) was never
  written: `<` turned `<=` on the header's length passed. One of 80 bytes is written and read back.
- **Arguments with no data** were never written: `<` turned `<=` on their length passed. An empty
  request's and an empty response's arguments (20 bytes) round-trip in either byte order.
- **A read header of its own type and version but another length** was tried only a byte short
  for the request and a byte long for the answer, so `!=` turned `<` on one and `>` on the other
  passed. Both headers a byte long and a byte short, and of 0, 10, 27, 30, 57 and 59 bytes, are
  refused with no panic.
- **Drep's other bits** were tried in five values: reading the high nibble as one, or bits 1 to 4
  as any, passed. Seven more values hold bit 4 alone to decide.
- **An AR whose first half is zero** was never tried: checking half the AR for the explicit read
  passed. A target AR under it is refused, and a byte in the target's place under it.
- **Wording**: the clause said "three more read by tshark" before five items, one of them (the
  controller-interface answer) checked in bytes only. It now names what tshark reads and what it
  does not.
Before this commit, the critic's seven mutants were run against the tests: all killed.

## Refute round 4 (2026-11-23): refuted, the codec right wherever tshark dissects, arguments untested apart

The critic swept 2466 header datagrams (every packet type and flag byte in both orders, every value
of each data representation byte), 6720 status pairs, 900 read requests and answers and 776 read
header variants through the codec's writers and tshark. Found, and answered:
- **Datagrams Wireshark takes for no DCE/RPC** (the defect in what the codec read): a packet type
  past 10, a second flags byte with a bit past 1, a first data representation byte with a bit past
  the integer and character formats' low bits, or a float format past 3; tshark then reads UDP
  data, and the codec guessed a byte order. Measured again here. These are none of DCE 1.1's
  values (NDR's format label: integer and character formats 0 or 1, float 0 to 3), so they are now
  refused both ways by name (`RpcError::NotDceRpc`); the tests sweep every value of the three
  bytes and of the packet type, and show tshark eight refused and five kept.
- **The argument decoders were never tested apart**: every decoded argument was helper-shaped
  (maximum equal to the maximum count, length to the actual count, offset 0), and the noise never
  reached the decoders or `split` (the random actual count always overran), so six mutants
  reading a count from another's place passed. A request's and an answer's hand-written counts are
  now read back in either order, and the noise keeps most headers DCE/RPC's, fits the arguments'
  count and puts a read answer's header first in some (over two thousand arguments read, two
  hundred answers split, asserted).
- **Too few ARs and target ARs**: eight mutants comparing half an AR, or one byte of a target,
  passed. Three ARs (second half zero, one byte at either end) and two target ARs (one byte at
  either end) now hold every comparison.
- **The helpers' warnings**: a status the dissector does not know is warned of; the status is
  the device's to choose, now said, and one is pinned. "Headers of 0 to 59 bytes" counted bodies:
  reworded.
Before this commit, 23 mutants (the critic's 14 and the new rule's 9) were run: all killed.
