# C-137 evidence - PNIO over connectionless DCE/RPC

## The codec (2026-11-22)

New in Veredas 2: Veredas 1's aranha read no PNIO record. Written first for what aranha itself
needs (phase 6 reads a device's port data and I&M by the implicit read), to core's rules, so that
core's IO controller can build its connect, control, write and release on the same header,
arguments and blocks (P-018). Checked against tshark 4.6.6's DCE/RPC and PNIO dissectors on
hand-made datagrams (Ethernet, IPv4, UDP to port 34964) before the tests were written.

What the dissectors settled:
- **PNIO's argument counts follow the header's byte order**, not the blocks': a big-endian header
  with little-endian counts was read as an args length of 1 073 741 824. The PNIO status and every
  block are big-endian whatever the header says.
- **The PNIO layer is named after the interface**: `pn_io_device` for the device interface, its
  fields `pn_io_pn_io_*`, and the status's `pn_rt_pn_io_*` (a record read's refusal under
  `..._error_code1_pniorw`).
- **The dissector pairs an answer with its request** (`dcerpc.request_in`) by activity and
  sequence; an answer alone gets a note at chat severity ("No request to this DCE/RPC call found"),
  under the warning level the tests hold complaints to.
- **The record after a read answer's header is dissected by its own block type**: I&M0 (0x0020)
  and the port's data (0x020F) were read field by field, the padding of the port data aligned to
  four bytes from the block's start. Those records are the next clause's.

Before the first commit, 24 mutants of `rpc.rs` were run against the tests: 23 killed, one
survivor (the PNIO object's test never varied the `8271` bytes of its prefix), killed by four near
UUIDs added to the test.
