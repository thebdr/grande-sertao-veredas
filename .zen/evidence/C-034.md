# C-034 evidence - veredas-portal, the gateway

## The design (2026-11-07)

The component clause, promoted from P-002 as the bench's was from P-004: the role, the plan, the
borders. Three machine checks beyond the laws: the targets (one library, at most one binary of
the crate's name, tests: the shell is Q14 and the executable comes with the project file), the
content check (core's reader over every file of the crate folder; the bench's dep-info walk is
not repeated here, since portal pulls no file from outside its folder and the rule it pins is
the laws'), and the dependency graph of the light build.

The graph walk differs from the bench's in one way: the bench banned every member but core in
its whole graph, dev tables included, because its tests use nothing of the suite; portal's tests
dev-depend on the bench, which is the plant they run against. So the walk follows normal and
build edges only, reading `dep_kinds` on each edge, and the test pins both that the bench is
absent from the walk and that a planted dev dependency is skipped while a normal and a build one
are seen. `--no-default-features` is passed from the start, so when the `store` and `serve`
features land the same test still proves the embeddable build carries neither.

## Refute round 1 (2026-11-07): refuted

The code held (every target shape, every edge kind: a target-specific table, a rename resolved
by package id, an optional dependency behind a feature present with it and absent without, a
dependency in both a normal and a dev table followed). One claim was unproven: "cites no vendor
document" was read through `String::from_utf8_lossy`, so a section sign in a CP1252 file (the
byte 0xA7) or a UTF-16 file (A7 00, 00 A7) became U+FFFD and was never seen; this crate is the
one that reads such files for a living, and a fixture in a plant's encoding is a likely addition.
The reader now counts the 0xA7 bytes of a file that is not UTF-8 (unless the byte follows 0xC2,
the UTF-8 pair the text reading already counts), with planted samples in CP1252, UTF-16 in both
orders, the UTF-8 pair once, a lone first byte, two signs on two lines, and a 0xA7 continuation
byte of a valid UTF-8 letter not counted. The same hole is in core's reader (C-007) and the
bench's (C-024), noted for their owners; neither crate holds a non-UTF-8 file today.

## Refute round 2 (2026-11-07): holds

The fix held: a valid UTF-8 file through the text reader alone (the pair counted once), any
other file read lossily for the names and its 0xA7 bytes counted unless after 0xC2, the planted
samples in CP1252 and UTF-16 in both orders, the names still found in those encodings, the
false positives pinned absent. Noted below the bar by the critic: a UTF-16LE sign right after a
character of U+C200..U+C2FF would be missed (its A7 follows a C2), and a UTF-16 hit's line
number counts every 0x0A byte as a line break (the label, not the hit).

## Found when supervisão arrived (2026-11-09): the workspace's resolve is not the light build's

The light-build walk asked `cargo metadata --no-default-features` and walked the gateway's node.
`cargo metadata` resolves the whole workspace; once supervisão (C-047) depended on the gateway with
its default features, the resolve unified `store` and `serve` into the gateway's node and the walk
found the engine and the server (`duckdb`, `axum`, `hyper`), though `cargo build -p
veredas-portal --no-default-features` compiles neither. The walk now asks `cargo tree -p <package>
-e normal,build --target all`, which resolves the package alone, as a build of it alone does; the
planted packages go through the same function, so the walk's own test still pins it.
