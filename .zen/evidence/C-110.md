# C-110 evidence - the Modbus server

## Built (2026-11-22)

The first bench device of P-020 (the briefing of November 2026: bench devices for the four
fieldbuses, in Rust, inside maquinar), `src/modbus.rs` and `tests/modbus_server.rs`. Nothing is
carried from Veredas 1, which had no Modbus device (its scanner only named the protocol as a
probe to come).

How it is built, and why:
- **The bench's own code, not a library's server.** The protocol is small, and what the bench
  must show (the exceptions in the protocol's order, a frame of another protocol dropped, a length
  no frame has closing the stream, answers delayed or withheld, every connection dropped) is the
  server's own behaviour, which a library's server would decide for it.
- **The threading of the bench's OPC UA server**: a thread, a current-thread runtime, the
  runtime's drop as the teardown. The tables sit behind one lock the connections and the handle
  share, held for one request, so a request sees the tables whole and a plant-side set lands
  between two requests, never inside one.
- **Answered the moment it is read**, in order per connection, not on a tick: a Modbus device
  answers a request, it does not publish on a period, so the server has no tick and no timing
  bound of its own.
- **The checks in the protocol's order**: the function (01), then the request's length, quantity,
  byte count and value (03), then the addresses (02). A PDU of the wrong length for its function is
  answered 03, as a value the function does not take.
- **A unit other than the configured one is answered 0B** (gateway target failed to respond):
  what a TCP gateway answers for a device that is not behind it; without `unit`, every unit is
  the device, as most devices on TCP behave.
- **Points name the tables, the tables hold the truth.** A point is a name over addresses; a
  write of any address in a table's size lands, whether a point covers it or not, and a point
  reads whatever its registers hold (half a two-register point written raw included).
- **No draws, ramps or reactions**: `reflexo`'s models will drive any bench device's points through
  its handle (docs/maquinar-plan.md, "P-020: the bench devices, as they land").
- **`drop_connections` by generation**: each connection belongs to the generation it was accepted
  in and waits for the watched generation to pass its own (`wait_for`, which sees a call made
  before its subscription too); the call returns when every connection of an earlier generation
  is closed, so one accepted meanwhile is neither closed nor waited for.

Found while writing the test: a write of 124 registers cannot be asked at all (its PDU would be 254
bytes, one past what a frame holds, and its length field 255 is no frame's), and the server
closed the stream as it should; the test asks one past each limit inside the largest frame there
is (docs/maquinar-plan.md, "Traps").

The independent client is `tokio-modbus` 0.17 with its `tcp` feature only, a dev-dependency of the
bench (and a workspace line, so core's Modbus TCP client may take the same crate).

## Refute round 1 (2026-11-22): refuted

Found by the critic, each answered:
- **`drop_connections` missed a connection the client already had** (300 of 300): a client's
  connect returns once the kernel completes it, before the accept loop takes it, so the late accept
  stamped it with the new generation. Now the call goes to the accept loop, which takes every
  connection waiting in the listen queue straight from the socket (`socket2`), closes them, and only
  then moves the generation on. Pinned: fifty connections dropped right after their connect.
- **A connection blocked on a client that reads nothing held the call for 5 s**: the answer's
  write was the one wait not raced against the drop. Now it is. Pinned: a client that pipelines
  125-register reads until its sends block, dropped within a second.
- **The delay was pinned on one answer only** (a delay applied to the next answer alone passed).
  Pinned now on two answers in turn and two pipelined, the second after the first.
- **"A refused request writes nothing" was pinned for 02 only**: every 03 case carried the bytes
  the accepted write before it had left. The tables are now set to values no request carries
  before the 03 cases, coils, registers, the mask and the read-and-write.
- **The hundred exchanges were never exceeded.** Pinned: 150 exchanges, the last hundred kept.
- **Silence set while an answer waits out a delay** let that answer out. Now the server looks
  again after the delay and withholds it, counting it; the clause says "every answer not yet sent".
- **Units 0 and 255 under `unit`** get 0B, which a client addressing a device on TCP directly
  (255, the implementation guide's rule; tokio-modbus's `tcp::connect`) meets on every request.
  Kept as the gateway behaviour it is and said in the clause and the reference: such a device leaves
  `unit` out.
- **"All counted in a status"** said more than the status counts; the clause now names what is
  counted.

Checked and holding by the critic: every worked example's bytes, the exception order against the
specification's state diagrams (the mask's length before its address, as the clause orders it),
the quantity limits, byte counts and coil packing, the framing, silence never sent later, the
limit, stop and drop freeing the port, every configuration refusal's message, the executable's
first status line.

## Refute round 2 (2026-11-22): refuted, answered

The round-1 answers held under the critic's probes: the listen queue's drain (5000 connect-drop-send
cycles, none answered; 7200 connections from 24 threads with 580 listen-queue overflows, every one
closed), the write raced against the drop, the new pins. What it found, each answered:
- **Silence switched on and off inside a delay let the waiting answer out**: the server read
  `silent` once, when the delay ended. Now `set_silent(true)` counts each time silence begins, and
  an answer that waited is withheld when the count moved, even if silence is off again. Pinned: 50
  ms of silence inside a 500 ms delay, the answer never sent, the next one the next request's.
- **A withheld answer, and one whose connection was dropped during its delay, counted as
  answered**: the count was taken when the answer was computed. Now an answer is counted when it is
  sent, and the exchange shows it from then on (each exchange numbered, so a late answer fills its
  own, never a pipelined twin's). The request still takes effect when it is read, as a device does
  what it is asked before it answers. Pinned: the counts unchanged across both cases, the dropped
  one's exchange showing none.
- **Reading a point as text was claimed and not pinned**: every point's value read as text now,
  a NaN as `NaN`.
- **A plant-side span with a huge count overflowed** (`registers(table, 1, usize::MAX)` panicked).
  Now the end is checked, the refusal naming it. Pinned.

Also from the critic: `a_client_that_reads_nothing_is_dropped_at_once` once ran out its 20 s
under 18 parallel tests before the buffers filled. It now writes a hundred requests a write
(keeping its place across partial writes) and allows 60 s: it cannot pass on wrong code, and a
loaded machine fills the buffers sooner.

## Refute round 3 (2026-11-22): refuted, answered

The critic's mutants of rounds 1 and 2's answers all turned the test red, and its probes found:
- **An answer counted and shown before it was sent, and kept so when its write failed or a drop
  cut it.** The critic's own fix counted after the write; a client then reads its answer before
  the status counts it, and core's test of its client (`tools/mestres`) reads the status right
  after an answer. So the answer is counted, and shown in its own exchange, as its write begins,
  and taken back when the write fails or a drop cuts it; the clause says so. Pinned with a client
  that resets during the delay and one that reads nothing, dropped.
- **Silence withholds what is not yet handed to the socket**: a write already begun cannot be held
  without tearing its frame. Wording; pinned. Silence is now set before its epoch moves, so a
  request read between the two sees silence on (a window of nanoseconds the critic could not hit).
- **Unpinned claims, now pinned**: 03 before 02 for 0F, 10, 16 and 17 at an address past the
  table; 03 for a wrong length on 01, 02, 06, 10 and 17 and a zero quantity on 10 and 17; a refused
  05 writing nothing; the delay holding exceptions; two delayed answers on two connections each
  shown in its own exchange.

The critic's probes are kept in the test as its `round_3` module; core's tests of its client pass
against the change.

## Refute round 4 (2026-11-23): refuted, answered

Round 3's answers held (one count and at most one take-back per answer, final when a drop
returns). What the critic found besides:
- **A client that closes the ordinary way during the delay** (a FIN, as a client's timeout closes,
  which core's own test does) kept its answer counted and its connection open until the delay ended:
  a reconnecting client under a limit of one was refused. The delay is now raced against the read
  half's end: the client gone, its answer counted as none, its place freed at once.
- **Silence could let one answer out after `set_silent(true)` returned** (7 of 300 trials, 55 with a
  status reader on another thread): the request's "not silent" was read without the lock. Silence is
  now decided under the lock an answer's count takes, and the knob sets it under that lock.
- **Answers a drop's reset discards** from the socket's buffer stay counted (11419 counted, 487
  whole answers received): the server cannot see what a client received. Wording: the count is of
  answers handed to the socket, and the status's doc comments say so.
- **An exception's take-back** was unpinned. The critic's probes are kept as the test's `round_4`
  module.
