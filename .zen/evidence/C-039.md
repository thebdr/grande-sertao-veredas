# C-039 evidence - a portal telegram channel

## The design (2026-11-07)

Veredas 1's telegram source (`veredas-desktop/src/telegram.rs`) was the plant's external unit
for one vendor: it decoded one catalog in code, asked a decision service over HTTP and answered
with a destination or a reassignment. None of that is carried (Q8). The gateway's channel is
the bench channel's twin on the other side of the wire: the same channel file, the same catalog,
core's `check_framing` before the bind, `frame` and `messages_of` for the ids, `decode` and
`encode` for the bodies. What is the gateway's own is small: reply rules (a constant or a copied
field per name the reply writes), the message tables, the gate, and the events a session pumps
into the store.

Three decisions, each reversible:
- A message's table is typed by the catalog's field types (`U8`..`I32` ints, `Ascii`/`Hex`
  text) and payload groups and repeats are text; a repeat adds `name1..name<max>` columns, and a
  repeat over 64 columns refuses the channel rather than widen a table without end.
- The reply rules are the gateway's, not a controller file: a controller file is the bench's
  (what a machine does); what the gateway answers a device is a decision the apps will make
  through the write surface, and until an app does, a rule copies and constants. The project
  file (phase 6) carries them.
- Every reply and every send obeys the one master switch, core's `WriteGate`, the same gate the
  OPC handles consult: the operator arms the plant once, for every protocol.

The payload's group names are read by compiling the payload pattern again in the gateway (the
catalog validated it when it loaded); core's `Message` keeps its groups private. A
`Message::read_names` in core would be the generalisation when a second consumer needs the list
(the plan, "Adding a component", 2).

What the first run against the bench taught: the machine's rules file faults one item in ten
(`noread`), so a row-by-row check of the announcements must accept the fault's flag and empty
code; the wire reports a failed dial in its status (`retrying`, with the error) and not as a
`Trouble` event, which core keeps for a bind failure, so the link state reads the wire's state.
