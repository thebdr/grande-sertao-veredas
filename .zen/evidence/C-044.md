# C-044 evidence - the server

## The design (2026-11-07)

Veredas 1's `veredas-server` as it was (its router, its SSE feed, its windowed REST with the
largest-triangle-three-buckets downsampler), over the session's `Live` instead of a feed the
desktop published into: the `serve` feature, on by default, needing the store it serves. Not
carried: the embedded dashboard and its layout endpoints (the apps own their screens, the plan),
and the command sequencer with its handshake wait (a plant-specific procedure; the apps compose it
from the write endpoint when they need it, under the same gate).

The write surface is the handles' own gates seen over HTTP: the switch is checked early for a
better answer (a 403 before anything is coerced), the whitelist by the handle, and no endpoint arms
the switch, which the shell or the project does in process. A write the plant never saw and one
it may have seen answer different codes (503, 504) because the operator must know which.

The test client is raw TCP, not an HTTP crate: what reaches a browser is what is asserted. The
stream test flaked once at ten seconds with the hello received and no data frame; five reruns
passed in under a second each and the frames are the same path the session test proves, so the
flake is recorded here and watched, not explained.
