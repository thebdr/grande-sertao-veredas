# C-295: the component list

The component list Q31 entry 38 asks for ("(b) Security file, component list"), with the security
file Q447 ruled on 2026-11-26 (GitHub's private reporting, no address published).

## How it reads a commit (2026-11-26)

The first reading listed every crate of the lock file a component's version names (C-290's inputs).
At this repository's HEAD that held entries cargo's own resolve never reaches with any feature on:
`cxxbridge-cmd 1.0.205`, behind a dependency's feature no member turns on, had no licence cargo
would read. The list follows cargo's resolve for the release's target with every feature of every
member on: 394 entries at 24eda7bc, 380 of them crates, every one stating a licence, none of
Windows alone, every one a lock entry a version names.

A commit holding no `Cargo.lock` (packages by path alone, as the cut's own tests build) is resolved
without `--locked`: cargo writes its lock in the scratch tree, which nothing reads back.

## Refute round 1 (2026-11-27): refuted, at 3d1592a9

Real forms, three of them sharing one cause: `cargo metadata`'s `resolve` is the dependency
resolver's graph, not what cargo builds.
- **Features from another platform:** it unifies features across platforms. At HEAD it listed
  `const-random`, `const-random-macro`, `tiny-keccak` and `crunchy`, which only a wasm32 build
  compiles: `arrow-array`'s `cfg(target_arch = "wasm32")` dependency on `ahash` turns
  `compile-time-rng` on.
- **Weak features:** it counts a weak feature (`dep?/f`) as turning its dependency on. At HEAD that
  listed 26 packages no build compiles, `rust_decimal`'s `borsh?/std` among them.
- **Test features:** it keeps the features a test's dependency asks for (`serde`'s `derive` for a
  dev-dependency listed `serde_derive` and its tree).
- **Dependency kinds:** a dependency of another platform that is also a dev-dependency kept its
  normal edge (the kind's `target` unread).

Besides:
- A commit with no `Cargo.lock` that uses a crate got a document that depended on the machine's
  cache. C-290 and the cut refuse that commit.
- The serial number was a version-8 UUID, which CycloneDX 1.6's pattern (versions 1 to 5)
  refuses.
- Qt's CPE sat in a property of the suite's own, not CycloneDX's `cpe` field.
- `alforge components --release` took the flag for a commit (exit 2, not 1).

Answered (this commit):
- **Graph:** the graph is cargo's own feature resolver's (`cargo tree -e normal,build --target`,
  every feature of the components on), each node mapped to cargo's metadata by name, version and
  source. At HEAD the list holds 367 entries, 350 crates, none of the forms above.
- **Unread inputs:** a commit whose components' inputs do not read is refused.
- **Serial number:** an RFC 4122 version-5 UUID (SHA-1 of the URL namespace and
  `urn:veredas:components:<release>:<commit>`, which Python's `uuid.uuid5` gives too). `sha1` is a
  workspace dependency for it, already locked.
- **Qt's CPE:** in the `cpe` field.
- **The CLI:** a flag in the commit's place is a usage error.

## Refute round 2 (2026-11-27): refuted, at 693be961

At HEAD the list's 365 packages matched cargo's own unit graph exactly (`--unit-graph` under a
nightly override), with every package URL, checksum and licence right. Four real forms remained:
- **Edges cargo never builds:** `cargo tree -e build` prints a package's build-dependencies when it
  has no build script. pest_meta 2.8.3 (`build = false`) printed `sha2` and its tree, and indoc
  2.0.8 printed `rustversion`, whose edge `indoc → rustversion` was in HEAD's list. A member's
  build-dependency with no `build.rs`, and a dependency on a path package with no library, did the
  same.
- **A proc-macro by path beside its namesake of the registry:** cargo prints it
  `name vX (proc-macro) (path)`, the mark before the source, and the parsing gave up.
- **A signed commit under `log.showSignature`:** git's verdict on the signature joined the
  timestamp, three documents for one commit and release.
- **A lock of format 1** (cargo writes one for a `rust-version` below 1.41): its checksums sit in
  `[metadata]`, and the crates came without one. The same lock reader is C-290's, whose lock
  identities were empty for such a lock.

Answered (this commit):
- **Edges never built:** an edge to a build-dependency of a package with no build script, and an
  edge to a package with no library (or one cargo's metadata does not hold), is dropped.
- **Marks:** cargo's marks are stripped wherever they stand.
- **Signatures:** every git command runs with `log.showSignature` off (`git::command`).
- **Format 1:** the lock reader takes a lock of format 1's checksums from `[metadata]`.

`what_cargo_prints_and_never_builds_…` holds each form, the signed commit made with a key of the
test's own.

## Refute round 3 (2026-11-27): refuted, at 214242eb

At HEAD the list held: its 365 packages and its edges were cargo's unit graph's for the 13
components (`cargo build --unit-graph` under `RUSTC_BOOTSTRAP`). Three real forms in workspaces of
the critic's own:
- **What lies below a dependency no build compiles was listed.** Round 2 dropped the edge alone: a
  member with no build script whose build-dependency asks serde's `derive`, serde also used without
  it, listed `serde_derive`, `syn`, `quote`, `proc-macro2`, `unicode-ident` and the edge serde →
  serde_derive, merged by package into serde's real node.
- **What a build compiles was lost** when `cargo tree` printed it whole first below a dependency
  cargo ignores (a fork with no library using serde, sorted first) and then as `serde (*)`:
  `serde_core` and the edge serde → serde_core were missing.
- **Two git sources of one repository** (its default branch, and `branch = "main"`) both matched
  the printed `url#8a2f5f93`, part of each; the list exited 2.

Answered (this commit):
- `cargo tree --no-dedupe --charset ascii`: every node printed whole where it stands (HEAD's 13
  components print 156,000 lines in about a second), and a package's build-dependencies under
  their mark at the depth of its children. A node no build compiles is left out with everything
  printed below it, and nothing a build compiles is printed there alone.
- A printed source is held to its package's whole: a path to its folder, a git source's URL and
  reference equal and its commit starting with the printed digits, a registry's URL or name.
- Two sources of one repository at one commit share their package URL (`vcs_url` names the
  repository and the commit) and make one entry, the same code.
- HEAD's test holds the list to cargo's unit graph, package by package and edge by edge, so an
  entry missing fails it; round 3's three forms are a test of their own, each held to the graph.

## Refute round 4 (2026-11-27): refuted, at 58868179

At HEAD the list held: 367 entries, every checksum the lock's, the path packages right, no
absolute path. Three real forms, from two causes and the caller's machine:
- **A git reference cargo URL-encodes:** `cargo tree` prints a source `dep?branch=fix%2Fx#c9522213`
  where `cargo metadata` holds `git+…/dep?branch=fix/x#c952…`, so no package fitted and the list
  exited 2 on a commit cargo builds: a branch like `fix/x`, a tag like `release/1.0`, a `rev` of
  `refs/pull/1/head`, a name holding `+`, `@` or `~`. Round 3's form used `branch = "main"` alone.
- **A folder whose name ends in `)`:** the reader took off every closing parenthesis, the folder's
  own with cargo's, so a twin by path in `forks/itoa (twin)` matched no folder (exit 2).
- **The caller's cargo configuration:** `CARGO_HOME`'s `config.toml` holding `build.rustflags =
  ["--cfg", "rustix_use_libc"]` (rustix documents it) changed HEAD's document under one serial
  number: rustix → errno and → libc added, edges the builder never compiles.

Not counted: a configuration in the commit (C-290 refuses it), a `[replace]` to a package no member
uses (refused), two path packages of one name and version (cargo refuses them), legacy licence
expressions (`MIT/Apache-2.0`) written as the manifest states them.

Answered (this commit):
- The reader takes `name vX`, then `(proc-macro)`, then the source with its parentheses alone
  taken off.
- A git source's reference is compared as cargo prints it: its metadata's value form-encoded
  (letters, digits and `*-._` as they are, a space `+`, any other byte `%XX`).
- The list's two cargo runs set `CARGO_ENCODED_RUSTFLAGS` empty (which outranks every rustflags of
  a configuration), `RUSTC` to `rustc` and the wrappers empty. A `links` override in a
  configuration leaves `cargo tree` as it is (checked: its build script's dependency printed),
  which is what the builder compiles. The suite's own runs keep the machine's configuration (its
  `[env]` finds Qt).
- Tests: round 3's git test holds a third source on `branch = "fix/x"`; round 2's twin lives in
  `forks/itoa (twin)`; a cargo home whose configuration sets `--cfg rustix_use_libc` gives the same
  bytes, while cargo's own tree under it prints errno.
