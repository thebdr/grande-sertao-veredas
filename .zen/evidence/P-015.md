# P-015 evidence - Oficina's own-shell spike

The spike's plan, its seven points and how each is judged are in `docs/oficina-plan.md` ("The
own-shell spike"). This file holds what was observed: no clause rests on it yet.

## The toolchain, measured on the Linux machine (2026-11-22)

Checked against the upstream servers by their metadata and by HEAD requests; no Qt downloaded.

- The machine had no Qt, no CMake, no Xvfb, no clang. It has gcc/g++ 15.3, ninja, Rust 1.100,
  whose default linker on `x86_64-unknown-linux-gnu` is `rust-lld` (cxx-qt's cargo-only build
  refuses GNU ld.bfd, so this matters), GL and EGL headers, Mesa 26.2.4 with llvmpipe, and every
  library Qt WebEngine needs at run time. Qt's X11 plugin lacks seven libraries here
  (libxcb-cursor0, -icccm4, -image0, -keysyms1, -render-util0, -xinerama0, -xinput0; 0.09 MB from
  the distribution, which needs sudo); Wayland and `offscreen` need none of them.
- Qt 6.12.0 (2026-09-28) through aqtinstall 3.3.0 from Qt's own archives, no account: the spike's
  modules (base, Quick 3D, ShaderTools, WebChannel, Positioning, WebEngine) are 374 MB to download
  and 2.46 GB on disk. WebEngine now sits in Qt's extension repository; for 6.12.0 it has a build
  of 2026-07-08 and a second of 2026-11-11 under `61400/`. Qt 6.12.1 (2026-11-18) has no WebEngine
  published yet. `aqt list-qt linux desktop --modules 6.12.0 linux_gcc_64` lists every module.
- aqtinstall 3.3.0 cannot read Qt 6.12's Windows repository: `aqt list-qt windows desktop --arch
  6.12.0` fails on `Updates.xml`. Qt now splits the Windows repository by compiler
  (`qt6_6120_msvc2022_64/`); aqtinstall's master merged Qt 6.12 support on 2026-11-22, unreleased.
- The distribution's route: Ubuntu 26.10 ships Qt 6.11.2 and KDDockWidgets 2.4.1. The private
  headers KDDockWidgets' Qt Quick side needs on Qt 6.10 and later cannot be installed on this
  machine: `qt6-base-private-dev` depends on `libinput-dev`, which wants `libinput10
  1.31.3-1ubuntu1` where the machine runs a patched `1.31.3-1ubuntu1+touchpad1`.
- Upstream versions: cxx-qt 0.10.0 (2026-08-24, MIT OR Apache-2.0); KDDockWidgets 2.5.1
  (2026-10-23, GPL-2.0-only OR GPL-3.0-only, bundles nlohmann JSON and KDBindings, both MIT; its
  Qt Quick side needs Qt's `QuickPrivate` on Qt 6.10 and later); Spix 0.14 (2026-01-05, MIT) over
  AnyRPC 1.0.2 (MIT, unchanged since 2022); CMake 4.5.1; Monaco 0.57.0 (101.7 MB unpacked);
  rust-analyzer not installed (a rustup component).
- Hypervisors here: QEMU/KVM through libvirt only. No Hyper-V, VMware or VirtualBox.
- Installed in the home folder for the survey: `uv` 0.13.9 (Astral's release, SHA-256 checked),
  to run aqtinstall, since the system Python has no pip.

## What the TOML editing library does (toml_edit 0.25.20, probed 2026-11-22)

- An LF text parses and renders back byte for byte.
- A text with CR LF endings renders with LF: the line endings are not kept.
- A leading byte-order mark is accepted and dropped from the rendering.
- A value's trailing comment and the spaces around it live in the value's decoration: replacing
  the value with `doc[key] = value(x)` loses them (`port = 504`); replacing it with the old
  decoration carried over keeps them (`port = 503  # the port`).
- Spans are kept by `toml_edit::Document::parse` and dropped by `into_mut`, so the document is
  edited as a `DocumentMut` and parsed again for the form's lines.
- A parse error carries a byte span; the library's own text gives the column in characters
  (`a = "😀" x` fails at column 9), where both views count UTF-16 units (column 10).

The document (`spikes/oficina/model/src/document.rs`) answers each: it works on LF text without
the mark and writes both back as read (a file with both endings is written with the one more
lines use, LF on a tie), carries the old decoration onto every edited value, and reports columns in
UTF-16.

## The Rust side's tests (2026-11-22)

`cargo test --manifest-path spikes/oficina/Cargo.toml`: 18 tests, green (11 for the document, 7
for the tree, three of them Unix-only: links, unreadable entries, a name that is not UTF-8).

- The corpus: every TOML text the laws hold to the stamp (`leis::Suite::read(..).stamped`: every
  TOML file that is not a cargo manifest and every TOML block of a reference under `docs/`) opens
  and comes back byte for byte; its formats are exactly the nine of the tree's table. Every scalar
  of every text that is not the stamp nor a date-time was set to another value of its type, 544
  edits: each one read back, every other value and every comment unmoved, the line count the same
  and only the value's own line changed.
- Comissionador's `veredas-test` and `veredas-functions` files open with a stamp but are not TOML
  (`docs/test-schema.md`, their own grammar): the corpus test found them missing and they left the
  tree's table of TOML formats.
- Three faults planted, each alone, each failed a suite: the old decoration not carried onto an
  edited value (the document's tests); the byte-order mark not written back (the document's); the
  folders-first order dropped (the tree's).
- The laws (`cargo test -p leis`) are green with `spikes/oficina` present: L1 leaves a crate
  outside `crates/` and `tools/` that is not the suite's alone, and the spike's own `Cargo.toml`
  makes it a workspace of its own.

## Building the shell (cxx-qt 0.10.0, cargo alone)

- cxx-qt-build warns "Neither mold, lld, nor gold linkers were found": it looks on `PATH`, and the
  link succeeds with Rust's own `rust-lld`, the default linker of this target.
- KDDockWidgets' headers need `KDDW_FRONTEND_QTQUICK` and `KDDW_FRONTEND_QT` defined, which its
  CMake package passes to its users; a cargo build passes them itself.
- The build script's links reach every target of the package, a test's included, and the generated
  C++ calls the bridge's Rust side and cxx-qt's initialisers: the shell is a library with a thin
  `main`, and each test links the library, `cxx_qt` and `cxx_qt_lib`.
- An inherited signal is declared with its whole C++ signature (`dataChanged` with its roles list);
  without it the generated code does not compile.
- QML's `TreeView` over a `QAbstractItemModel` written in Rust: `index`, `parent`, `rowCount`,
  `data`, `hasChildren`, `canFetchMore`, `fetchMore`, `roleNames` overridden in Rust, `createIndex`
  and the row announcements inherited. No C++ beyond the one start-up file.

## Driving it with no display (Spix 0.14, Qt's `offscreen` platform)

- Spix answers an action before it lands: a property read straight after a click read the value
  from before it (`clicked 1` after a second and third click). Every check of the tests waits for
  its value and fails with the last one read.
- A property holding an enum reads back by its name (`textFormat` reads `PlainText`).
- A `TapHandler` in a `TreeView` delegate never saw Spix's click; a `MouseArea` did. The tree's
  delegate uses a `MouseArea`.
- A `TreeView` keeps delegates for reuse, and a delegate kept aside keeps its object name: a test
  reading `row14` by name read a row that had left (the rows appeared shifted by one after a
  refresh). With `reuseItems: false` the names are the rows drawn.
- Items inside KDDockWidgets' docked panes are found by name below the window (`oficina/hello`).

## Point 2 (2026-11-22): passed

`cargo test -p oficina-spike-shell --test document`: 3 tests green, and the spike's 29 tests green
together under nextest (the release-only timing aside). The document is a `QAbstractListModel`
written in Rust: its rows are the form's fields, its properties carry the text, the stamp, whether
the file changed, and where a refused text fails.
- From the form: `link.port` retyped `5029` (click, Ctrl+A, the text, Return) came back in the text
  view as `port = 0x13A5  # 5028`, every other character of the file equal.
- From the text: `2000` selected and typed over with `3000` showed in its field; `yes` typed into a
  boolean field was refused as "`link.keepalive`: `yes` is neither `true` nor `false`", the text
  untouched.
- A text that does not parse (`timeout_ms = = =`): a marker at line 9, column 14 over the failing
  character, the form disabled and showing the last text that parsed, Save disabled; mended to
  `timeout_ms = 2500`, the field followed, the marker went.
- Saved: a file read with CR LF and a byte-order mark was written back with both, `0x13A5` the one
  change.
Learnt on the way:
- A property `text` gives the generated class a `setText`; an invokable of that name does not
  compile (an ambiguous overload in moc's code). The text view's edit is `editText`.
- Spix reaches items only: the document object is not one, so where a text fails is shown as a
  marker in the text view, which is also what a person needs, and the test reads the marker.
- Spix types by posting one key event holding the whole text to the window's focus item: a test
  clicks the field and waits for `activeFocus` before it types.
- AnyRPC sends a string as an untyped XML-RPC value; the tests' client trimmed those, and lost a
  text's last newline. It keeps every character since.
- Two TOML formats reached `main` from other members meanwhile (`veredas-abaco-oracle-baseline`,
  ábaco's; `veredas-machine`, the releases'), and the corpus test failed until the tree's table
  named them: the test is the table's guard. Ábaco's 53 KB baseline made the edit-alone test take
  259 s; it now edits at most 40 evenly spaced values of each text (6.8 s).

`cargo test --release -p oficina-spike-shell --test table -- --test-threads 1`, three runs, three
tests green each (the same, the timing aside, in debug). The table is a `QAbstractTableModel`
written in Rust over the model's `Synthetic` table (a size and a seed; each row draws from its own

- Not measured yet: scrolling frame times, with a GPU and without. On the `offscreen` platform

## Point 4, its language-server half (2026-11-22): rust-analyzer on an ORCL file, nothing run

The client is the model's (`lsp`): framing, the inline project, the settings, the server's messages
read. `cargo test -p oficina-spike-model --test lsp`: 3 tests green, one against the real
rust-analyzer 1.100.0 (the toolchain's own binary). Installed for it: the `rust-src` component
(rustup, 83 MB), rust-analyzer's source of the standard library.
- An ORCL program using `orcl-std`'s on-delay timer, an unknown method planted (`self.timer.scna`):
  marked 5.4 s after the client started, cold, as `E0599 no method \`scna\` on type \`Ton\`` at
  line 22, columns 35 to 39 (zero-based, UTF-16), the place the editor draws it; completion after
  `self.timer.` offered `scan`, `q` and `et` with the traits' methods.
- Nothing of the folder ran. Planted beside the program: a `build.rs` named by a `Cargo.toml`, a
  `.cargo/config.toml` naming a compiler wrapper, and a `rust-toolchain.toml` naming a toolchain made
  of scripts (`rustc`, `cargo`, `rust-analyzer`); each writes a marker if run. None was written.
- The two controls, run by hand once: rust-analyzer started as a careless editor starts it (rustup's
  proxy, in the project's folder) ran the project's own planted `rust-analyzer` script, rustup
  honouring the folder's toolchain file; the toolchain's real binary with its default discovery of
  `Cargo.toml` ran the planted `cargo` and `rustc` the same way. Opening a project does run its code
  unless the client prevents it (the review's entry 32). What prevents it here: the project given
  inline (`linkedProjects`, so cargo is never asked about the folder), build scripts and procedural
  macros off, the toolchain's own binary, started in a folder of Oficina's.
Learnt on the way:
- rust-analyzer pushed only empty diagnostics and answered every pull with none while
  `cargo.autoreload` was `false`; its own command line (`rust-analyzer diagnostics`) found the
  error. Bisected with a probe client: that one key, nothing else. The settings leave it out.
- The diagnostics of an unknown method or name are rust-analyzer's experimental ones: off unless
  `diagnostics.experimental.enable`.
- rust-analyzer loads no source under a folder whose name begins with a dot (a `tempfile` folder);
  the test's project lives in one named `orcl-*`.
- The client asks for diagnostics (the protocol's pull model, retried while the server is not
  ready) and still takes those pushed.
