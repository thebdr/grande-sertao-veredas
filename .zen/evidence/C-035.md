# C-035 evidence - the file tail

## The design (2026-11-07)

Veredas 1's `tail/single.rs`, `tail/cursor.rs` and `encoding.rs`, as they were, on core's
`SourceHandle`, `SourceId` and `now_unix_ms`; the line event and the source set move here from
Veredas 1's core (`source.rs`), the handle itself being core's. `LineEvent::index_ms` is new, the
same rule `Sample::index_ms` applies, so a line and a sample land on one axis.

One test expectation of Veredas 1 was wrong and found so here: the owner-never-blocked test
expected the new file's line alone after the owner's appends, truncation and rename; the tail,
reading from the beginning, emits the owner's three lines, then the eight bytes the truncation
left (flushed as a torn line when the file was renamed away), then the new file. The test now
pins that exact sequence, which is the stronger claim: everything the owner wrote meanwhile
reached the tail.

Added over Veredas 1's tests: a bare carriage return kept and an empty line a line, a start at the
end of a file ending in a newline, a deleted file drained and the reappearing one read whole,
20 000 lines from a flat-out writer, a torn final byte as U+FFFD, the exact index of a stamped
and an unstamped line, the failed worker's exact text kept across remove, and three files tailed
at once with the content checked against the tag and the sequence.

## Refute round 1 (2026-11-07): refuted

Four gaps, all Veredas 1's and never seen there (noted for its owner):
- A UTF-16 LE file tailed from its end lost its first new line: the mid-line check read the
  file's last byte alone, and a UTF-16 line feed ends in 0x00. The attach now reads the file's
  head (up to 4 KiB) to decide the encoding, which the bytes appended after the attach point
  never would, and compares the last code unit with that encoding's line feed.
- A file that opened with plain ASCII lines was committed to UTF-8 at its first bytes, and a
  CP1252 byte later (a degree sign) read as U+FFFD: a live log's normal case, a header first.
  Plain ASCII now tells nothing: it streams through, and the first byte beyond ASCII decides
  (a valid UTF-8 sequence, else CP1252), however far in; the clause says so.
- A watcher that could not be set up (a parent folder not there yet, a path that cannot be
  watched) dropped the wake channel's only sender, and the wait returned at once every tick:
  a full core spun. The loop keeps a sender of its own; a tail with no watcher polls at its
  interval, pinned by the process's CPU time over a window.
- A rewrite in place that is back at or past the read offset by the next poll is not a
  truncation to a length check, a limit every poll-based tail shares: the clause now says a
  truncation is the file seen shorter than what was read, and the rewrite read as a
  continuation, rather than claim past it.

## Refute round 2 (2026-11-07): refuted

Three gaps, all in the start-at-end path and the ASCII state the first round added:
- A file holding its mark alone (a logger writes it when it creates the file; the tail attaches
  right after) ends on the mark, not on a line feed, so the attach took it as mid-line and the
  first line written after it was skipped. A start at or before the mark is a clean start now.
- An attach whose raw length fell inside a UTF-16 code unit (the writer caught mid-unit) set the
  offset there, and every unit after decoded a byte out of step: no line feed ever showed, the
  source went silent for good. The start offset is rounded down to the unit boundary, counted
  from the mark; the torn-line skip covers the half-line, and an attach one byte into the first
  unit of a line reads that line whole.
- A UTF-8 lead held in the ASCII state when the stream ended (a stop, a truncation, a rotation
  drain) was decided as CP1252 and printed as an invented character; the clause promised U+FFFD.
  A valid prefix cut short decides UTF-8 whether or not the stream is ending, and the decoder
  finishes the torn sequence as U+FFFD; a byte no sequence starts stays the CP1252 character it
  is, which the clause now says in those words.

## Refute round 3 (2026-11-07): refuted

One gap, the UTF-8 twin of round 2: a tail attached at the end of an ASCII-headed file (the head
leaves UTF-8 and CP1252 undecided) inside a two-byte UTF-8 character handed the decoder the
continuation byte alone, a byte no sequence starts, and the file was CP1252 for good. The bytes
that decided belonged to the fragment the clause says is skipped. While the head leaves the
encoding undecided, the fragment is now dropped raw, up to the first line feed, before the decoder
sees it; a committed head (a mark, the UTF-16 pattern, a byte beyond ASCII) keeps the decoded-text
skip. The owner test change of round 2 was judged a correction, not a weakening.

## Refute round 4 (2026-11-07): refuted

One narrow gap: a head of one to three bytes that is no complete mark (the writer caught inside
its mark, or one UTF-16 character in) was decided alone, with less evidence than a start from the
beginning demands (four bytes or a line feed): a lone FF committed CP1252, a lone `a` and NUL
committed UTF-8, and nothing recovered. Such a head is pre-fed to a fresh decoder and votes with
the bytes appended after it; a torn mark is no text yet (the first line written is whole), one
character is a torn line (its completion skipped once decoded). The round-3 fix and the four
suggested probes (the raw skip across reads, before a truncation, before a stop, an attach on a
line feed) held.

## Refute round 5 (2026-11-07): refuted

Two contrived gaps, both files under four bytes at the attach: a byte that begins a mark but is
CP1252 text (a thorn) was taken for a torn mark and opened the first line emitted with text from
before the attach; and a UTF-16 file without a mark opening on a bare line feed (0A 00) decided
UTF-8 on the line-feed shortcut, from the beginning as from the end. The short head now decides its
skip once the encoding is known (a mark is a clean start, anything else text skipped with the torn
line unless it ended on the line feed of the encoding decided), and the shortcut waits for four
bytes while a NUL rides with the line feed. A stop reaching a short head undecided emits nothing.
The five suggested probes held.
