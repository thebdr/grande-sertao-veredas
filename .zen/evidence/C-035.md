# C-035 evidence - the file tail

## The design (2026-11-07)

Veredas 1's `tail/single.rs`, `tail/cursor.rs` and `encoding.rs`, as they were, on core's
`SourceHandle`, `SourceId` and `now_unix_ms`; the line event and the source set move here from
Veredas 1's core (`source.rs`), the handle itself being core's. `LineEvent::index_ms` is new, the
same rule `Sample::index_ms` applies, so a line and a sample land on one axis.

One test expectation of Veredas 1 was wrong and found so here: the owner-never-blocked test
expected the new file's line alone after the owner's appends, truncation and rename; the tail,
reading from the beginning, emits the owner's three lines, then the eight bytes the truncation
left (flushed as a torn line when the file was renamed away), then the new file. The test now
pins that exact sequence, which is the stronger claim: everything the owner wrote meanwhile
reached the tail.

Added over Veredas 1's tests: a bare carriage return kept and an empty line a line, a start at the
end of a file ending in a newline, a deleted file drained and the reappearing one read whole,
20 000 lines from a flat-out writer, a torn final byte as U+FFFD, the exact index of a stamped
and an unstamped line, the failed worker's exact text kept across remove, and three files tailed
at once with the content checked against the tag and the sequence.
