# C-113 evidence - the emulated EtherCAT segment

## Built (2026-11-22)

The fourth bench device of P-020, `src/ethercat/` (`esc.rs`, the ESC core and the SII image, pure;
`mod.rs`, the configuration, the segment on a raw link, the handle) and `tests/ethercat_segment.rs`.
New in Veredas 2: Veredas 1 had no EtherCAT device. The review's entry 27 named the honest limit
(a slave controller written in software is functional, never exact in time; no open emulator
exists) and the clause states it.

How it is built, and why:
- **An ESC as a memory**: 8 KB, every register answered as stored, so a master's blanking of FMMUs,
  SyncManagers and DC registers, its SyncManager configuration and its station address all work
  without code of their own; behaviour only where the standard gives one (the read-only registers
  kept, the AL state machine, the SII interface, the DC latch and system time, the FMMUs).
- **The EEPROM from the bench file**: identity words, one string, General (the string as both order
  number and name: ethercrab names a device by its order string), FMMU usage (outputs, inputs),
  SyncManagers (SM2 outputs at 0x1000, SM3 inputs after), the TxPDO and RxPDO; no mailbox, so the
  master maps the process data from the EEPROM, no CoE needed.
- **The frame back on the wire it came from**, the source's locally administered bit set as a first
  device sets it: ethercrab drops frames still carrying its own source address. The segment never
  reads its own answers back (aranha's link leaves outgoing frames out); a first form that also
  skipped frames whose source already had the bit took a veth's locally administered address for
  an echo, and was dropped.
- **Clocks**: each device's local clock starts 1 µs after the one before (devices powered at
  slightly different instants); system time is local time plus the offset the master writes.

Proof: ethercrab 0.7.1, the crate core's EtherCAT master stands on (docs/controlador-plan.md),
finds, reads, addresses, transitions and exchanges with the segment, and reports a faulted device
with its code; hand-built frames pin each command's data and working counter; tshark reads the
frames with no complaint. ethercrab and futures-lite join the workspace as maquinar's
dev-dependencies.

## Refute round 1 (2026-11-22): refuted, answered

The critic ran 16 mutants switched by a variable of one build: 15 kept the test green, and the
one it killed was the standard's own behaviour (an LWR counted 1), which the test had pinned the
wrong way. Its probes, each asserting what the standard says, failed on 12 points. What changed:
- **An LWR counted 2 a device.** ETG.1000.4 and the ESC count a write 1 and only an LRW's write 2
  (SOEM's note says as much). Now so; the wire test and the clause corrected.
- **FMMUs ignored their bits** (logical start and end bit, physical start bit) while the features
  register (0x01FC, bit 0 clear) says the ESC maps bit by bit, so a master packing 1-bit terminals
  into a shared byte (SOEM, IgH, TwinCAT; ethercrab maps whole bytes) read and wrote wrong bits.
  Now each mapped bit is moved alone, and an FMMU that reads and writes under an LRW writes what
  the datagram brought, returning what the device held.
- **The clock's values were asserted nowhere, and its difference was two's complement.** An ESC
  states the system time difference as sign and magnitude (bit 31 set when its own time is the
  smaller); a device 1 µs behind read 0xFFFFFC18, which a master reads as about -2.15 s. Now sign
  and magnitude, held to 31 bits, and a plain write of the system time compared too. The ESC core
  is pure, so the test calls it with its clock handed in and pins every value to the nanosecond.
- **Read-only registers**: only four ranges were kept, and an EtherCAT write changed the alias.
  Now the alias, each SyncManager's status and PDI control bytes, the receive times and the
  system time difference are kept as well; eleven are pinned.
- **8 KB of RAM stated, 4 KB held**: the memory now ends at 0x2FFF.
- **The alias**: matched once the master sets DL control's bit 24.
- **A fault raised a device in INIT to SAFE-OP**: now from OP to SAFE-OP, below it the state kept.
- **A PDO of 300 entries was accepted** and broke ethercrab's EEPROM read (its count is a byte):
  over 255 entries a way is refused, and the EEPROM's size word follows the image.
- **The General category's port byte** was at a reserved offset; now at bytes 0x10 and 0x11.
- **Unpinned**: the acknowledge rule, BRW, APRW, BWR, the returned position address, the vendor,
  the configuration refusals and the bench-file route (the reference said this test ran its block;
  now it does, through `Bench::start`).
- **Stated, not built**: no SyncManager watchdog, no SyncManager direction or buffer rules, the
  IRQ field never set, the outputs readable whatever the AL state, a frame of another type
  unanswered.

The critic's probes, run against the answer from a copy outside the repository: twelve of
thirteen pass; the thirteenth starts a 300-entry device, which is now refused.

Checked and holding by the critic: the frame and datagram headers, the source's bit, position
and configured addressing, broadcast reads, the read-write commands' old bytes, ARMW and FRMW
per device, LRW per device, the order of processing, the AL transitions, the SII layouts, the DL
status, no panic on a malformed frame, the handle's atomicity, and ethercrab end to end.

## Refute round 2 (2026-11-23): refuted, answered

Round 1's answers held and were pinned; the critic's eleven mutants all kept the test green, and
each failed a probe written from the standard or the clause. The code was right on seven of its
eight probes; what changed:
- **A broadcast's position field** is advanced by every device, as the ESC datasheet's addressing
  table has it (BRD, BWR and BRW come back with 3 for three devices); it was left alone.
- **BOOT is never taken**: the EEPROM states no bootstrap mailbox, so INIT to BOOT is refused with
  0x0013 (bootstrap not supported), as a slave stack refuses it.
- **Pinned now** (the critic's probes, kept as the test's `round_2` module): a frame of another
  type unanswered and counted unreadable (the old check was vacuous: its header stated a length
  with nothing behind it), every transition ETG refuses, the physical start bit, the EEPROM bytes
  IgH reads (the name index, the SyncManagers' direction bits, the alias word), all eight
  SyncManagers' read-only bytes, the difference ahead held at 0x7FFFFFFF, a BRD of the system time.
- **Wording**: an EEPROM write or reload is answered as done with no effect; the test runs on
  Linux, so the refusal elsewhere is not run here; the reference's refusal paragraph lists every
  EtherCAT refusal.

## Refute round 3 (2026-11-23): refuted, answered

Round 2's answers held, each killed by its pin. Nine more gaps (`~/.cache/veredas/critic-c113-r3`),
each now a pin in the test's `round_3` module or in the test it belongs to:
- **A 32-bit system time was compared without its wrap**: a 4-byte write (and a 4-byte FRMW, as a
  master distributing 32-bit time sends) compared the low halves as plain integers, so a device
  512 ns ahead across the wrap read the most behind there is. The low halves are now compared the
  short way round, modulo 2^32.
- **A write running past the RAM's end was dropped whole** (counted, nothing stored); an FMMU
  likewise. An ESC writes byte by byte as the datagram passes: the bytes inside its memory are now
  stored, those past it not.
- **Unpinned claims, each with a surviving mutant**: the EEPROM's FMMU usage and PDO entries (ethercrab
  reads only the bit lengths; IgH registers entries by index and subindex), no SyncManager watchdog,
  an EEPROM write or reload done with no effect, a fault in SAFE-OP, the missing interface's whole
  text, ports 2 and 3's receive times, the IRQ field never set.

Noted by the critic, not claimed by the clause: the transmission delay (0x0928) is stored but not
added to the received time before the comparison; ethercrab 0.7.1 refuses device names over 64
characters while the bench takes 255.

## Refute round 4 (2026-11-23): refuted, answered

Round 3's answers held, each pinned. The critic's probes and mutants are in
`~/.cache/veredas/critic-c113-r4`; each finding is a pin in the test's `round_4` module.
- **The system time was compared on the wrong writes**: the ESC datasheet compares a written system
  time if at least its first byte (0x0910) was written; the code compared writes lying inside
  0x0910..0x0917 (the high half alone among them) and not a longer one from 0x0910. It now compares
  a write covering 0x0910, over the low 32 bits when none of the high four is written.
- **Unpinned behaviour, each with a surviving mutant** (the code right): a logical datagram starting
  or ending inside an FMMU, as ethercrab splits an image (dropping the offset left every output byte
  wrong at the 1024-byte bound; a bad end panicked the segment's thread); an acknowledge in the
  device's own state (SAFE-OP 0x14, PRE-OP 0x12), the usual recovery from a plant fault; OP to
  SAFE-OP and SAFE-OP to PRE-OP (ethercrab's own way down); the working counter by device, not by
  FMMU; the FMMU's activation bit.

Noted by the critic, not claimed by the clause: the SII header's CRC, DL control's loop bits stored
but ignored, a datagram whose more bit is clear followed by bytes within the header's length, SII
control bit 7 clear for an image past 16 Kbit.
