# C-200 evidence - veredas-comissionador, the component

## The design (2026-11-22)

The plan (`docs/comissionador-plan.md`) and the grammar (`docs/test-schema.md`) came first
(b2ed0d1), with the questions Q310 to Q317 and the option taken meanwhile for each. The crate
followed on the orchestrator's word of the same day: phase 1, the reading and the check.

A library and one executable, like portal and supervisão: the executable is a shell over the
library (`veredas-comissionador check <file>` today; `run` and `replay` with the engine, C-205).
No build script, no feature.

Its members: core alone for now (the header reader, `veredas_core::schema`). Portal joins the
manifest with the engine (phase 2), when the engine reads a session; the test admits core and
portal, L5's row, and requires core.

## Never arming the switch (Q314)

Q314 is taken as (a): comissionador never arms portal's write switch; a live run of a test that
writes will be refused while the switch is off. The guard reads every Rust file of `src/` as
`proc-macro2` tokens, the pattern of supervisão's writes test, smaller: the only ways to arm a
session's switch from outside portal are `Session::set_writes_armed` (the gate itself is
crate-private in portal) and a gate of one's own (`WriteGate`, core's type), and a method or a
type can only be reached by naming it, so a name absent from the tokens is a call absent from the
code. `include!`, `include_str!` and `include_bytes!` are refused too: they would bring tokens
from a file the reading does not walk. A raw identifier (`r#set_writes_armed`) is read as its
name; a comment and a string are not tokens of code.

Limits written into the clause: a dependency's macro could expand to such a call without the
name in this crate's tokens (the crate has no such dependency); the tests are not read, since a
test of the engine will hold a session and arm it, as portal's and supervisão's tests do.

## Refute round 1 (2026-11-22): refuted, three findings, all closed

1. **Code the reading never opened.** The test read the `.rs` files under `src/`; a
   `#[path = "gate.txt"] mod gate;` brought in a file it skipped, and `[lib] path = "outside/lib.rs"`
   in the manifest built the library from outside `src/` while `src/` stayed clean. Both armed a
   gate with every test green. Closed: every non-test target's `src_path` (cargo metadata) under
   `src/`, every file under `src/` Rust, and `path` refused inside any attribute (`#[...]`,
   `#![...]`, `cfg_attr` within them).
2. **A gate without its name.** Core's `WriteGate` derives `Default`, so `Default::default()`
   handed to `veredas_core::opc::spawn` arms a worker of comissionador's own with no `WriteGate` in
   the text. The clause's rule is wider than the switch: comissionador drives machinery only
   through portal. Closed by refusing what reaches past the session: `spawn` (every worker that
   writes takes a gate, so a gate by `Default` serves nothing), the protocol layers' paths (`opc`,
   `telegram`, `fieldbus`), std's sockets (`net`) and processes (`Command`); the normal
   dependencies held to a reviewed list with no OPC UA, socket or HTTP crate. Asking core to drop
   `Default` was the other way; it is not needed.
3. **A project's text in a literal.** Once portal is a dependency, a `[session]` text with
   `writes_armed = true` loaded by `project::load` would start an armed session. Closed: a
   literal holding `writes_armed` is refused. The guard is stated as Q26's: against accidents,
   not deliberate hiding (an encoded or computed text is outside it).

The critic found sound: the rule of targets (a missing or second binary, other library types,
examples, benches, a build script), the member edges with L5 alongside, raw identifiers, macro
bodies, comments and the `include` macros.

## The architect's Q314 (b) (2026-11-25): the run arms the switch, once confirmed

Asked who arms portal's write switch for a run whose test writes, the architect answered "The run
arms and disarms": the run arms the switch at its start once the person has confirmed the list of
the test's gated writes, and disarms it at its end; the engine holds the power to arm. Built so:
`run::gated_writes` lists the test's writes and sends as written, `run::writes_fingerprint` gives
the list's fingerprint, and `RunOptions::confirming` carries the one the person confirmed; the
session's own arming, which only its owner can set, is handed to the run through
`LivePlant::with_arming` (the executable's `main.rs` alone names `set_writes_armed`, once); a run
confirmed for its own list arms the switch before its first step and disarms it on every way out,
a switch found armed left as found, a plant handed no arming refused as before. With no screen the
executable takes the confirmation as `--arm <fingerprint>`, printing the list and its fingerprint
when it refuses (Q320, taken meanwhile: the fingerprint, and a switch found armed left so).
